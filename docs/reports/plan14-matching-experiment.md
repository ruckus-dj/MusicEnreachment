# План 14: сравнение автоматического сопоставления

[План 14](../plans/todo/14-two-stage-automatic-matching.md) разделяет
исследование (T01–T03) и изменение рабочего потока (T04–T06). Этот отчёт
относится только к исследованию. Контракт, порог `0.70`, группировка, ручная
authority и условия публикации не меняются.

## Метод

Исходная ревизия: `c62e5a6871aca669a511f5ee27636a72de34bffd`,
политика расчёта: `matching-rapidfuzz-v1`. Данные берутся из сохранённого
анализа, каталога Local и кэша MusicBrainz. Извлечение — транзакции PostgreSQL
`REPEATABLE READ READ ONLY`. Офлайн-повтор читает JSON; он не открывает базу,
провайдер или исходное аудио, не пишет оценки и не подтверждает связи.

- **Контроль.** Для сохранённого набора кандидатов отдельно показываются
  наблюдавшееся решение и повтор действующего release-first ядра. Ручной
  разбор не подменяется автоматическим прогоном. Сохранённый список ID не
  считается порядком ранжирования, если журнал хранит его канонически.
- **Поиск.** Рассматриваются только заголовки изданий: название, полный
  release artist и известное число позиций. Число файлов — мягкий сигнал;
  несовпадение количества не исключает издание. Эксперимент применяет этот
  сигнал после равенства текстового ранга и точного DATE/CATALOGNUMBER:
  точное число, неизвестное число, затем известное число с меньшей разницей.
  `-stage shortlist` не
  загружает треклисты в типизированное представление и не считает пары.
- **Раскладки.** Local и MusicBrainz проходят один расчёт пар на тех же
  сохранённых сведениях анализа. Действующая проверка release-профиля
  видна отдельно от пригодности всей раскладки. Для эксперимента
  сопоставляется точная сумма оценок выбранных пар, прошедших `0.70`; равные
  суммы не разрешаются ID. Неполная раскладка не участвует в сравнении
  полных. Уникальность внутри издания и равенство между изданиями — разные
  результаты.
- **Повтор.** В отдельном проходе на тех же оценках разворачивается порядок
  неупорядоченных входов; результат сравнивается без учёта времени. Это
  переиспользование только внутри одного запуска, не постоянный кэш.
  Исправления тегов в памяти проверяют раскладку известного издания
  отдельно, не считаются свидетельством качества поиска по исходным тегам.

Четыре неизменяемых JSON-среза лежат в
[`testdata`](../../backend/cmd/matching-experiment/testdata/). `-input`
принимает абсолютный путь или путь относительно `backend/`.

```sh
case_file=cmd/matching-experiment/testdata/punk-o-mania-2.json
task matching:experiment -- -input "$case_file" -stage baseline
task matching:experiment -- -input "$case_file" -stage shortlist -limit 10
task matching:experiment -- -input "$case_file" -stage all -limit 10
```

Время — длительность этапов офлайн-повтора. Чтение треклиста — декодирование
сохранённой проекции, не задержка HTTP MusicBrainz. Полный прогон включает
отдельные контроль и повтор; его время не равно задержке рабочего запроса.

В срезах с сохранённым решением ни одна из использованных пар не имела
MusicBrainz search score или AcoustID score: в сохранённом evidence эти факторы
равны `null`. В обоих неполных случаях не заполняли отсутствующие теги из пути
или названия файла. Порядок заголовков для ручного и fallback срезов —
сравнение на сохранённом пуле, а не повтор сетевой последовательности запросов.

При лимите 1 на обоих срезах с известным изданием команда `-stage shortlist`
не декодировала ни одного треклиста и рассчитала **0 пар**. Три прогона
`-stage all -limit 10` на каждом JSON дали один и тот же отчёт без полей
времени. Сохранённые решения совпали с повтором во всех трёх доступных
случаях; только у положительного MusicBrainz случая были сохранены назначения
для прямого сравнения. `fixture_sha256` в выводе фиксирует точный вход.

## T03: раскладки и время

- **Punk, исходные теги.** У Local есть полная структурная раскладка 21/21,
  но нет полной раскладки из пар, прошедших `0.70`; release-профиль тоже
  не проходит. Конкурент с 16 позициями структурно неполон в этой одной папке.
- **Punk, контроль в памяти.** После обратного декодирования испорченных
  кириллических тегов Local даёт единственную полную раскладку по порогу
  пар: сумма `17.80438`, среднее `0.84783`. Действующий release-профиль её
  всё ещё не пропускает. В частности, credit `Various Artists` не совпадает
  с исполнительскими `ALBUMARTIST` отдельных файлов. Это результат проверки
  solver, не разрешение менять теги или принимать сопоставление.
- **MusicBrainz.** `Жечь электричество!` — единственная полная раскладка,
  прошедшая порог пар и release-профиль, сумма `52.0`. Все 52 файла получили
  назначения на 26 позиций: позиции повторно используются только между двумя
  разными папками, как разрешает текущий solver. У трёх других изданий полное
  покрытие возможно, но не на пороге `0.70`; шесть структурно неполны.
- **Два файла с неполными тегами.** У `5a82173d…` — две или более раскладки
  на оптимуме `1.50397`; варианты `19d437c3…` (`1.52705`) и `efbd0b22…`
  (`1.48479`) имеют уникальную раскладку и проходят оба порога. Это отличие
  от действующего выбора, но без подтверждённого издания более высокая сумма
  не доказывает качество. Равенство **между** изданиями проверено тестом на
  равных точных суммах; в сохранённых прогонах равного максимума не было.

## Граница перед T04

При имеющихся данных разумно сравнить два варианта: оставить ручной разбор
для ничьей в действующем release-first результате либо экспериментально
допустить конкуренцию полных раскладок, прошедших **оба** действующих порога.
Для второго варианта стартовое предложение: top-10, точная сумма выбранных
пар, равенство между изданиями и внутри издания — ручной разбор, ID только
задаёт порядок отображения. Присутствие корректного издания в двух известных
случаях не подтверждает пригодность меньшего лимита. При отсутствии полного
shortlist или незавершённом доказательстве оптимума результаты вычисленного
подмножества нельзя считать окончательными. Нужен выбор владельца, особенно
для случая, где по текущему правилу — ручной разбор, а другой полный вариант
получает более высокую сумму.

Проверка стенда: `/downloads` смонтирован `rw=false`; после чтения SHA-256
срезов строк группы Punk, состава, location, текущей оценки и инвентаря
совпали с исходными. Во время эксперимента приложение не запускало ни
подтверждение, ни публикацию; данные стенда и исходные файлы не менялись.
