# Оптимизация проверок: исходные измерения

База: `58eec59ad857dd6bb3a59c9ade89cf8010a93d9f`. Первый инфраструктурный
этап закоммичен как `b00d5be5`; последующая консолидация тестов ещё не
прошла полный gate. Результаты и ограничения этапов разделены ниже.

## Измеренная база

- Успешный локальный `task verify`, Node 24: около 227,6 с по времени жизни
  файла полного лога. Временно включённый Go JSON-вывод затем удалён.
- Go: persistence 189,316 с; service 68,232 с; jobs 37,905 с;
  migrations 33,902 с; settings 13,615 с. Пакеты выполнялись параллельно:
  складывать эти времена нельзя. Зарегистрировано 3728 успешных test events,
  включая вложенные subtests, а не 3728 независимых верхнеуровневых тестов.
- Frontend: 465 тестов; прототип: 296 тестов. Их сходство не доказывает
  дублирование покрытия и не служит основанием удаления.
- CI `41804912247`: Windows 29:16 (native SDK 8:19, backend 15:56),
  macOS x64 18:01 (backend 10:55), macOS arm64 10:35,
  Linux arm64 3:41. Лишняя Linux amd64 matrix job: 4:41.
- Linux verify упал на двух frontend timeout по 5000 мс; frontend под
  одновременной Go-нагрузкой занял 158,50 с против примерно 40 с отдельно.

## Изменения и границы

- Отдельный application+River template вместо повторных River-миграций;
  каждый тест сохраняет собственную БД. Настоящие upgrade/rollback-тесты остаются.
- Успешно удалённые БД исключаются из резервного process cleanup;
  неудавшееся удаление остаётся для повторной очистки.
- Minimal WAL применяется только к disposable embedded PostgreSQL;
  внешний `TEST_DATABASE_URL` и настройки приложения не изменяются.
- Устранены лишние JSDOM-окна для Storage, дополнены явные HTTP-fixtures,
  уточнены response/UI и live-stream handshakes без повышения timeout.
- Go/frontend/tools suites выполняются последовательно, внутренняя
  Go-параллельность сохранена. Эффект на общий wall time требует замера.
- Дублирующая Linux amd64 matrix job удаляется. Владелец отдельно разрешил
  полный JSDOM-suite один раз в Linux verify; все native Go-проверки и
  production-сборки на поддерживаемых платформах сохраняются.
- Windows SDK получает точный кэш с проверкой источников, лицензий и ABI;
  реальный cold build и warm cache hit требуют подтверждения CI.
- Полный commit hook остаётся. Не повторять идентичный ручной gate рядом
  с hook на неизменившемся дереве; это не кэш успешных тестов и не обход hook.

## Пока не доказано

Коммит инфраструктурной оптимизации `b00d5be5` прошёл нормальный полный hook
за 244,82 с против базовых 227,634 с: полный gate оказался примерно на 7,5%
медленнее. Это не измерение только тестов и не подтверждение ускорения.
Владелец уточнил бюджет: все тесты не более 60 с без компиляции и скачиваний,
с сокращением избыточных наборов, а не только оптимизацией инфраструктуры.

CI `41815181954` завершился неуспешно. Windows validator не раскрывал
`${libname}` в `MagickCore.pc` и ошибочно отвергал import library;
исправление требует повторного Windows CI. macOS x64 persistence превысил
10 минут: все восемь активных leaf-слотов находились в создании/удалении БД,
четыре DROP ожидали PostgreSQL, ещё три DROP и один CREATE — admin pool.
Это подтверждает amplification clone/drop, но не доказывает конкретную
причину серверного ожидания (lock/checkpoint/I/O) без PostgreSQL wait events.

Следующий этап уменьшает число самостоятельных fixtures: retry-schema
сокращён с 15 до 1, отрицательные SQL-изменения откатываются между случаями.
Независимое ревью этой консолидации не выявило дефектов; полный gate нового
дерева пока не выполнен. Более крупные cleanup/publication lifecycle-наборы
объединяются отдельно; планируемое сокращение не выдаётся за измеренный результат.

Статически подтверждённые изменения следующего этапа (до полного gate):

| Участок | До | После | Что считается |
|---|---:|---:|---|
| Retry schema | 15 | 1 | Выполнения полного fixture по раскрытым случаям |
| Manual lyrics preparation | 6 | 1 | Выполнения DB-fixture; clone tags вынесен без БД |
| Delivery tools/support | 7 | 2 | DB-fixtures и верхнеуровневые lifecycle-тесты |
| Obsolete output | 9 | 1 | DB-fixtures; proof-поля проверяются без БД |
| Normal cleanup | 40 | 12 | Верхнеуровневые тесты |
| Normal cleanup | 38 | 15 | Статические места вызова fixtures, не runtime-счётчик |

Суммировать разные виды счётчиков как число фактически созданных БД нельзя.
Wrapper-only группировка с неизменным количеством fixtures была отклонена.
Проверки, не требующие PostgreSQL, переводятся на реальные валидаторы с
in-memory данными; SQL и транзакционные свойства не заменяются имитацией.

Консолидация закоммичена как `099e8c69`: нормальный полный hook прошёл за
209,67 с (−7,9% к исходным 227,634 с; −14,4% к инфраструктурному 244,82 с).
Persistence выполнился за 166,444 с против исходных 189,316 с (−12,1%).
Go subprocess wall — 171,10 с **с компиляцией**; его нельзя называть временем
только тестов. В persistence зарегистрировано 574 тестовых БД и 2 шаблона,
суммарно 500,519 с CREATE и 456,757 с DROP; это перекрывающиеся затраты работы,
не последовательное wall time. Бюджет 60 с ещё не выполнен.

Исходный полный JSON-лог более недоступен; baseline сохраняется по ранее
извлечённым измерениям. Новые прогоны сохраняют `build/test-results/go.jsonl`
и `go-summary.json`, чтобы не зависеть от временного tool-log. Артефакты
gitignored и не являются кэшем успешной проверки.

Следующий подтверждённый коммит `85f2d9cb` прошёл полный hook за 211,98 с;
persistence — 165,683 с, 518 тестовых БД (−56, или −9,8% к `099e8c69`).
Это почти не изменило время пакета относительно 166,444 с предыдущего этапа;
уменьшение allocations нельзя автоматически выдавать за такое же ускорение.
К исходным 189,316 с persistence выигрыш составляет 12,5%; полный gate к
исходным 227,634 с — 6,9%. Service остаётся дорогим: 80,781 с и 88 БД.

В `41819877480` (`099e8c69`) прошли Linux verify/arm64, обе macOS и Compose;
Windows упал после native-сборки из-за отсутствующего `cmp`. Сравнение
toolchain manifests переведено на Bash builtins в `85f2d9cb`; полный Windows
результат и warm cache hit остаются неподтверждёнными до нового CI.

Обновление: CI `41823037002` для `85f2d9cb` полностью прошёл, включая
Windows x64 (28:19), обе macOS, Linux, Compose и публикацию image. Cold native
SDK build, link/load validation и сохранение кэша подтверждены; warm hit ещё
не измерен. Последующие незакоммиченные service/mock и retry-консолидации
этот зелёный прогон не проверяет.

`d8e4202c` прошёл полный hook за 223,74 с. Service: 70,822 с и 64 БД
(было 80,781 с / 88 БД); persistence: 176,848 с и 497 БД (было
165,683 с / 518 БД). Уменьшение allocations подтверждено, устойчивого
ускорения полного gate этим прогоном не подтверждено. Промежуточный
141,250-секундный persistence-прогон не сопоставим: service тогда не
скомпилировался и не создавал конкурентную PostgreSQL-нагрузку.

Следующий этап рассматривает consumer-owned repository interface executor
для проверки оркестрации без PostgreSQL и более крупные domain lifecycle
группы. Сокращение маленьких матриц само по себе пока не обеспечивает 60 с.

Первый прогон оптимизированного дерева остановился на порядке импортов;
второй прошёл весь backend, но остановился на трёх ThemeSelect spies:
Storage-fixture хранит методы на экземпляре, а старые spies искали их в
прототипе. Исправлены только цели spies; узкая диагностическая проверка после
падения gate подтвердила все 5 ThemeSelect-тестов.

Второй прогон: 241,81 с до остановки, persistence 209,735 с, service 83,282 с,
frontend 11,20 с (462 успешных, 3 упавших). Это не полный gate и не доказательство
ускорения. После прогона обнаружена существенная сторонняя CPU-нагрузка IDE,
Arc mount и системных процессов; сравнение одного прогона с базой ненадёжно.
Пользовательские процессы не останавливались.

Итоговое ускорение локального gate и CI ещё не измерено. Успешная базовая
проверка не подтверждает оптимизированное дерево. Проверки не удалялись только
из-за длительности; приоритет — устранение повторной инфраструктурной работы.

### Фазовая диагностика и embedded teardown

Диагностический прогон до изменения очистки: persistence 173,209 с.
MusicBrainz source-scoped snapshot: 7,74 с, из них сценарий 0,406 с,
подготовка БД 2,103 с и DROP с ожиданием соединения 5,231 с.
Enumeration/tombstone: 1,08 с, сценарий 0,036 с, подготовка 0,667 с,
DROP 0,382 с. Ранее эти же leaf-тесты занимали 10,75 и 9,48 с:
инфраструктурная вариативность не является ускорением логики сценария.

Следующий диагностический прогон с cluster-scoped очисткой embedded PostgreSQL:
persistence 126,533 с (−26,9% к предыдущему прогону), 484 изолированные БД,
0 SQL DROP, 486 ресурсов освобождены при остановке owned-кластера.
Последний тест завершился примерно за 97,84 с от начала пакета; затем
измерение объёма заняло 5,628 с, а остановка и удаление — около 23,06 с.
Объём всех 489 БД кластера по `pg_database_size`: 7 220 063 575 байт.
Это логический объём БД, не измерение пикового физического использования диска.
Дорогой диагностический запрос удалён после получения этого замера; время
реального teardown остаётся внутри бюджета выполнения тестов.

Оба прогона не являются успешными полными gate: новый stale-result mock-тест
ещё не достигал нужной проверки из-за некорректного native fixture.
Не заявлять достижение 60 с или устойчивое ускорение полного набора по ним.
Внешний `TEST_DATABASE_URL` сохраняет немедленные SQL DROP и повторную
очистку при ошибке; cluster-scoped удаление разрешено только для реально
созданного disposable embedded-кластера. Проверки изоляции, миграций и
транзакционных границ сохранены.

Успешные полные hook-прогоны после cluster-scoped очистки:

В последнем прогоне подтверждён native CLONE по startup-диагностике.

## 2026-11-05: замена fallback pipeline прямыми SQL-контрактами (в работе)

Проверявшееся дерево: незакоммиченные изменения поверх `71f40bba`.
Удалены невызываемые recovery helpers и повторный wrapper. Empty-plan
HTTP/provider/worker pipeline заменён прямым admission, delivery settlement
и frozen-review publication. Отдельные короткие контракты проверяют accepted
receipt после cache refresh, неизменность seal и rollback настоящего River
INSERT с идемпотентным replay. Отрицательные проверки выполняются после
успешного baseline; CURRENT metadata capture проверяется явно.

Выборочный диагностический прогон пяти сценариев прошёл за 3,632 с вместе
со стартом PostgreSQL. Это не время всего набора и не доказательство ускорения.
Предшествующий полный `task verify` завершился ошибкой за 120,25 с:
persistence 109,126 с, 401 БД. При удалении инертного boolean-параметра были
пропущены два positional-вызова: unique и exhausted-review. Исправления
сверены с исходными сигнатурами всех потребителей; exhausted-review после
последнего исправления ещё не проверен. Для таких сокращений необходимо
проверять смысл variadic boolean-аргументов, а не только компиляцию вызовов.

Qualified pipeline и его внешние callback-потребители пока не заменены.
Новые SQL-fixtures добавляют код: объём удалённого старого файла сам по себе
не является чистым сокращением набора. Цель ≤60 с не достигнута; успешный
полный gate и новый полный CI для этого этапа ещё не получены.

## 2026-11-05: удаление избыточного покрытия без замены

После `a4daac3e` владелец отдельно потребовал только удалять избыточные
тесты: не добавлять новые тесты, replacement-fixtures или перенесённые
сценарии. Следующий срез удаляет 1855 строк тестового кода и 10 верхнеуровневых
PostgreSQL-тестов, без добавления тестового кода:

- отдельный 1109-строчный hydration-комбайн с повторными сквозными lifecycle
  и подробными матрицами отказов; основные fallback lifecycle, handoff,
  lookup receipt и SQL rollback остаются в существующих тестах;
- HTTP-комбайны authority и frozen manual confirmation в persistence,
  configuration-rotation сценарий на полном fallback fixture;
- три повторных baseline/parking/unique fallback-прогона и отдельный
  exhausted-continuation wrapper;
- повторное удаление managed tool после завершённого перемещения.

Это намеренное сокращение объёма покрытия, а не обещание эквивалентности
каждой удалённой проверки. Удалённые подробные матрицы не воспроизводятся
в другом месте. Production-код и продуктовые решения не меняются.
Полная проверка этого среза на момент записи ещё не выполнена; выигрыш
времени из числа удалённых строк не выводится.

## Следующий срез после `605fab29`: дальнейшее удаление

`605fab29` прошёл локальный hook за 156,02 с (persistence 108,399 с) и
полный CI `42007374336`. Цель ≤60 с этим не достигнута.

Следующий срез удаляет ещё 18 верхнеуровневых тестов и подробные состояния

матрицы не заменялись; production-код не менялся. Полный gate и измерение
этого среза на момент записи ещё не выполнены.
