# Чистый повторный прогон: baseline до пересборки image

Дата: 14 августа 2026 г.  
Среда: disposable `test_stand`, PostgreSQL и in-process worker.  
Поверхность проверки: `POST /api/reconciliation/scan`, `GET /api/library/records`,
`GET /api/workers/queue` из контейнера `music-ingest`.

## Методика

1. Выполнен `test_stand/scripts/reset-library.sh`. Скрипт очистил только
   импортированные таблицы и managed output; source roots и исходные аудиофайлы
   сохранены.
2. Через live API поставлен `reconciliation_scan`:
   `reconciliation-scan-4493ad0657444f50b290ecb3935cfdea`.
3. Scan обнаружил 1 093 новых source observations и поставил 1 093 jobs.
4. Дождались терминального состояния всех worker jobs, затем собрали каталог,
   provider outcomes и latest-event cohort из PostgreSQL.

## Важное ограничение результата

Этот прогон выполнялся на уже запущенном Docker image, который не содержал
изменения `reassociation` и `reassociation_recovery`. Это установлено
инспекцией runtime source после прогона: обе строки отсутствовали. Поэтому
результат ниже является полезным baseline чистого scan, но **не доказывает
эффект recovery metadata**. После пересборки `music-ingest` тот же Noize MC
record успешно восстановил final revision и managed publication через штатный
`selection_refresh`.

## Итоговый API-снимок baseline

| Показатель | Результат |
| --- | ---: |
| Library records | 1 497 |
| Manual Actions (`needs_review`) | 648 |
| Analysis errors | 13 |
| Активные/ожидающие worker jobs | 0 |

Для сравнения, clean run в документе 04 содержал 1 443 records, 796 Manual
Actions и 14 analysis errors. Новый прогон уменьшил абсолютную очередь ручной
проверки на 148 строк (18,6 %), хотя охватил на 54 records больше. Это не
сравнение одного и того же snapshot-а источников, поэтому процент нельзя
трактовать как изолированный эффект одного изменения.

## Cohort ручной проверки

| Latest event | Новый прогон | Clean run 04 |
| --- | ---: | ---: |
| `selection_refresh_no_final_revision` | 372 | 256 |
| `analysis_ready_for_review` | 150 | 283 |
| `stored_candidates_auto_selected` | 126 | 257 |
| **Всего** | **648** | **796** |

Рост `selection_refresh_no_final_revision` ожидаем для первого импорта: у
переассоциированного source нет предыдущего `final` revision, который можно
append-only восстановить. Новый recovery path предназначен для случаев с такой
историей и не имеет права синтезировать final metadata для чистого первого
наблюдения.

Десять `musicbrainz_analysis` jobs завершились как `blocked_infrastructure`;
они остаются reviewable и не были auto-selected. Три source observations были
quarantined на стадии filesystem scan. Ни один incoming source не изменялся:
reset и worker затронули только импортированное PostgreSQL state и managed
output/staging flow.

## Вывод

Чистая переобработка старого image прошла через фактический API и worker до
пустой очереди и показала меньше ручных действий, чем прошлый измеренный clean
run. Для измерения recovery metadata требуется отдельный clean rerun после
пересборки image. Основной оставшийся массовый cohort — безопасно
неавтоматизируемые отсутствие final metadata на первом импорте и MusicBrainz
ambiguity; их нельзя убрать выбором случайной release edition.
