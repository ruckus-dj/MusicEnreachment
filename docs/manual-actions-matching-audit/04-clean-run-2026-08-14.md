## Исправленная блокирующая причина

До этого прогона в старой базе было 330 `musicbrainz=malformed`, хотя snapshot
содержал HTTP 200 и валидный JSON. Mirror
`https://musicbrainz.fdev.me` возвращает search summaries с `media[].track-count`,
но без `media[].position`. DTO требовал position, поэтому один неполный optional
field отбрасывал весь response как malformed.

`Medium.position` теперь optional. Regression test подаёт два валидных release
c `media` без `position` и проверяет, что адаптер возвращает `Ambiguous`, а не
`Malformed`. В чистом прогоне `malformed=0`, то есть полезные candidates теперь
сохраняются и могут быть использованы следующими resolver-ами.

Это исправление повышает качество evidence, но сознательно не превращает 647
реальных ambiguous responses в произвольные auto-selection.

## Почему 99–100% сейчас небезопасно и недостижимо одной настройкой

1. 344 AcoustID responses rate-limited. Понижение порога не создаст fingerprint
   evidence, а повторные bulk retries только усилят rate limit.
2. MusicBrainz возвращает несколько editions для одной записи. Текущая модель
   смешивает recording identity и release edition; выбор первого кандидата дал бы
   неверные CD/Digital/compilation/live варианты.
3. `selection_refresh_no_final_revision` раздувает UI queue, но скрывать эти
   строки не исправляя публикационный переход означало бы потерять нужное
   workflow evidence.

Проектный safety contract требует оставлять ambiguous, stale, unavailable и
low-confidence результаты reviewable. Поэтому целевая метрика должна быть
«99–100% precision среди auto-selected», а не «99–100% auto-selection любой
ценой».

## Следующие изменения, отсортированные по ожидаемой пользе

### Исправление provider rate limiting

`LiveTransport` раньше резервировал durable schedule только для hostname текущего
MusicBrainz. Если MusicBrainz направлен на локальный mirror и его delay установлен
в `0`, это не ограничивало AcoustID вовсе: официальный endpoint
`api.acoustid.org` обходил limiter. Это и объясняет cohort `acoustid=ratelimited`.

Теперь hostname AcoustID резервирует независимый schedule `acoustid`, а
MusicBrainz — `musicbrainz`. Каждый provider читает только свой runtime key:

| Provider | Runtime setting | Default |
| --- | --- | ---: |
| MusicBrainz | `providers.musicbrainz.request_delay_seconds` | 1,5 s; `0` допустим для локального mirror |
| AcoustID | `providers.acoustid.request_delay_seconds` | 1/3 s (не более 3 RPS по официальной policy) |

В UI Settings добавлено отдельное поле задержки AcoustID. Чистый runtime API
подтвердил независимые текущие значения: local MusicBrainz `0.0`, AcoustID
`0.3333333333333333`. Не устанавливать AcoustID в ноль для официального endpoint.

1. **P0: recording отдельно от edition.** При единственном высоком AcoustID
   recording выполнить direct MusicBrainz lookup по recording MBID и подтвердить
   artist/title/duration. Это снимет recording identity с review, не выбирая
   неоднозначный release.
2. **P0: починить selection refresh.** Переносить/создавать append-only final
   metadata revision для выбранного source после reassociation, затем запускать
   existing staged atomic publication. Только после этого 256 workflow rows
   перестанут быть Manual Actions без сокрытия проблемы.
3. **P0: rate-limit-aware scheduling.** Ограничить и отложить AcoustID retries
   по `Retry-After`/schedule, сохранять provider outcome отдельно от matching
   review и повторять только после окна провайдера.
4. **P1: ReleaseResolutionGroup.** Ранжировать album edition по подтверждённым
   recordings, disc/track layout, полному наблюдаемому tracklist, duration,
   catalog/country/date и top-second margin. Включать auto-selection только
   после shadow-mode precision audit.
5. **P2: text/ISRC fallback.** Для AcoustID `nomatch` искать recordings по
   artist/title, затем album/track, и подтверждать ровно один candidate с margin.
