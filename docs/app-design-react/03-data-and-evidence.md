# Данные для интерфейса: evidence и опубликованные теги

> Примечание актуальности (2026-11-03): этот файл сохранён как письменная спецификация. Описанный ранее статический runtime удалён; текущий графический эталон находится в соседнем React-макете. Продуктовый контракт задаёт `../design/decisions.md`.

Этот документ описывает необходимые будущие UI-контракты, а не существующие API.
Утверждённые инварианты находятся в `docs/design`; физическая SQL-схема появится
только в плане соответствующего этапа.

Уточнение владельца 2026-11-01 о медиатеке и публикациях — актуальный продуктовый
контракт в [`decisions.md`](../design/decisions.md#решение-владельца-от-2026-11-01-публикации-в-контексте-медиатеки).
На момент написания графическим эталоном был интерактивный prototype с его
JS/CSS; этот runtime удалён по решению владельца 2026-11-03; браузерная функциональная и визуальная проверка проводится без
сохраняемых screenshot-артефактов. Письменные решения имеют приоритет.

## 1. Объяснение confidence в статическом макете

`docs/design/decisions.md` — авторитетный источник утверждённой matching policy:
там определены текстовая метрика RapidFuzz `token_set_ratio`, версия
`matching-rapidfuzz-v1`, применимость по совокупному confidence ≥0.70,
automatic retrieval policy, top-1 artist-fit и сохранение итоговых assignment
profiles. Этот статический UI-макет не рассчитывает confidence и его вклады:
fixture-verdict и сравнения строк здесь демонстрационные, числовые результаты не
подставляются. Макет не заменяет и не пересматривает утверждённую policy. В v2
удалены иллюстративные проценты v1.

### Что оператор должен получить от matching

| Данные | Назначение в UI |
|---|---|
| Итог confidence `[0,1]` и версия алгоритма | Показать нормализованное значение, не объявляя его калиброванной вероятностью |
| Решение и порог | Почему можно автоматически привязать или нужна ручная проверка |
| Raw source и provider value | Конкретные сопоставленные значения |
| Нормализованные значения и правила | Например, совпало после нормализации регистра, а не буквально |
| Признак и его применимость | TITLE/ARTIST/duration/fingerprint/MBID/позиция/релиз; missing и not-applicable различаются |
| Weight, contribution, penalty | Откуда взялся итог. Значения предоставляет алгоритм, не frontend |
| Причина veto/конфликта | Live vs studio, разные recordings, несовместимое аудио, неоднозначное издание |
| Время и scope расчёта | Позиция, recording либо издание; track confidence не выдавать за release confidence |

Frontend должен проверять непротиворечивость объяснения: если итог взвешенный,
показывать формулу агрегации и полный набор вкладов/штрафов; если иной,
показывать соответствующий путь решения. Не суммировать произвольные признаки
до 100%. Отсутствие fingerprint — «не использован», не «совпал». Fingerprint,
tags и duration являются evidence формулы, а не отдельными decision methods.

**Что реально делает макет:** показывает демонстрационные сравнения строк,
длительностей и номеров; высокий/низкий verdict берётся из fixtures для проверки
двух веток flow. Confidence, его вклады и итоговый score макет не вычисляет и не
моделирует; числа в качестве результата matching не показываются.

Подтверждённая связь хранит только `decision_method=automatic|manual`, а не
confidence. Automatic link может быть пересчитан новой policy; manual link
защищён от автоматического перевыбора. Ручной выбор не меняет confidence
кандидата и может не совпадать с текущей автоматической рекомендацией.

## 2. Частичность — несколько независимых чисел

### Availability и publication completeness

На позиции availability-filter «В наличии» истинно при доступном source ИЛИ
существующем published audio; «Не хватает» — при отсутствии обоих; «Все» включает
весь отображаемый каталог, в том числе provider-only. На уровне артиста/альбома
«В наличии» требует хотя бы одну позицию с аудио, «Не хватает» — хотя бы одну
позицию без аудио; частичный объект попадает в обе выборки. Альбом при открытии
показывает полный track-list: match-state отдельно от publication/metadata state,
строки с совпадением могут быть акцентированы, без совпадения — приглушены, но
читаемы и активны. В «Не хватает» совпадение означает отсутствие; в «Все» строки
не разделяются по match-state. Информация не должна зависеть только от цвета.

Счётчики **«Есть аудио»**, **«Есть исходники»** и **«Опубликовано»** независимы;
правило availability «Есть аудио» как source ИЛИ существующий published audio не
меняется и не тождественно публикации. В компактной сводке артиста допустимы
отдельные числа альбомов и позиций для аудио и публикаций, например
`Есть аудио:5альбомов—2полностью3частично·48треков` и
`Опубликовано:4альбома—1полностью3частично·39треков`, с возможностью перейти к
подробностям. Это не обязывает добавлять метрику на каждый экран. Для каждого
показателя альбом входит в число альбомов, если хотя бы одна его позиция отвечает
показателю. Полным он считается лишь если известен полный track-list издания и
все позиции отвечают; частичным — если есть хотя бы одна отвечающая и одна не
отвечающая позиция. Когда полнота track-list неизвестна и известные позиции не
доказывают частичность, состояние остаётся `unknown`, не выводится из отсутствия
каталога. Пустой `0/0` не full. Трековый счётчик считает позиции релизов, не
файловые варианты и не уникальные recordings между релизами. Счётчик исходников,
если отображается, считается аналогично, но не обязателен.

Provider count показывается только когда scope cache известен и обозначает именно
этот partial scope, не полную дискографию. Решение считать provider release-group
или конкретные издания остаётся открытым. Для provider-linked альбома total известен
из конкретного издания, для альбома без provider он не выдумывается. Незагруженный
cache и неизвестный total — unknown, не 0, отсутствие или полная дискография.
Default фильтра не задан. Общее UX-вдохновение для артиста — гармоничный компактный
overview полезных чисел с drilldown без перегруза; SoulSync не задаёт обязательный
дизайн, parity или набор функций.

Уточнение владельца 2026-11-01 задаёт каталог, но **не** разрешает сводить
несопоставимые единицы в числовой агрегат: provider/tracks denominator артиста,
если рядом есть как release-group entries, так и конкретные editions, остаётся
открытым. Не считать молча группу одним изданием, не суммировать unrelated units и
не переименовывать total в число позиций. Issue 9 counts остаются числом позиций
каждого конкретного издания и не меняются из-за группировки missing entries.

Идентичность группы — MusicBrainz release group ID, не равенство названий и не
межпровайдерное сходство. Все конкретные издания со связанными sources или текущими
publications показываются по отдельности и без дополнительного уровня группы;
их track-lists, assignments, publications и metadata независимы. Если в группе
нет ни одного такого издания, отображается одна отсутствующая group entry. При
наличии фактического издания missing alternative editions группы не добавляются.
Издание, уже имеющее source/publication, ведёт прямо к своему полному track-list.

В missing group detail выбирается конкретное издание по году, стране, формату,
числу позиций, disambiguation или доступным признакам. Без выбора track-list
отсутствует, unknown missing-track count отображается как `—`, а не `0` и не
полный edition total. После выбора показывается только его список; смена выбора
заменяет его, не создаёт union. Автоматического first/standard/recommended/
canonical выбора нет. Выбор только для просмотра, он не создаёт collection entity
или publication, не запускает download и не обещает audio. Существующие
availability-filter правила остаются: частичный объект в обеих выборках, а
позиции без аудио в существующем издании не скрыты.

Presence для этой группировки относится к linked sources и identity текущей
publication. Является ли динамическая доступность файла/output дополнительным
критерием, остаётся открытым вопросом. Удаление source не удаляет publication;
издание сохраняет отдельную строку при другом связанном source или текущей
publication, иначе применяется правило отсутствующей группы.
Новые persistence/API/table, cross-provider grouping,
canonical-edition policy, metadata copy, synchronization и default выбора не
вводятся.

Выбор нескольких артистов/альбомов/позиций даёт единый контекстный preview
`create/update/unchanged/unprocessable/skipped` с причинами до позиции. Выбор
артиста разворачивается по его существующим альбомам/позициям. Используются
имеющиеся источники/существующие публикации; отсутствие файла — пропуск с
причиной, без создания collection entities или автоматического fallback.
Просмотр provider catalog не означает mass library creation. Массовое
подтверждение не обходит matching ambiguities, protected manual tags,
identity/authority guards; новая all-or-nothing/partial atomicity/cancel policy
не задана.

Индикатор «Метаданные изменились» — независимо от publication completeness:
полный published track может иметь changed metadata. Он сравнивает эффективные
metadata для явного обновления с фактическими тегами, встроенной обложкой и lyrics
последней успешной CURRENT-публикации, с учётом действующих merge, защиты ручных
полей и `absent`. Provider cache и технические версии сами по себе не сравниваются.
Альбом может агрегировать число изменившихся треков с раскрытием конкретных полей.
Audio source/quality/path и filesystem drift/missing — отдельные состояния.
Успешная новая публикация (включая recovery-регистрацию) заменяет baseline;
произвольный внешний drift — нет. Алгоритм/hash, периодичность и цвет не заданы.
Отдельная подсветка новых provider-значений защищённых полей остаётся открытым
вопросом и не снимает защиту/не применяет их автоматически. Provider cache/local
metadata обновляются отдельно от записи в опубликованный файл; получение provider
данных не меняет опубликованные файлы. Правила распространения provider-данных в
локальные metadata этим решением не меняются.
Metadata update уже опубликованных artifacts выполняется только после выбора
объектов, preview и явного подтверждения. Automatic quality improvement остаётся
AUDIO-only и сохраняет CURRENT tags/cover/lyrics; автоматическая первая публикация
eligible matched complete releases не затрагивается. Действуют защиты ручных полей
и `absent`, matching ambiguity и identity/authority guards; explicit cover/lyrics
workflows сохраняются. См. [уточнение владельца от 2026-11-01](../design/decisions.md#уточнение-владельца-от-2026-11-01-подтверждённое-обновление-metadata-публикаций).

Для группы нужны: количество уникальных файлов, доступных путей/вариантов, целевых позиций, позиций хотя бы с одной связью, позиций с явно выбранным аудиоисточником, выбранных для публикации, уже опубликованных и оставшихся свободных файлов. Число связанных вариантов и число использованных уникальных файлов — разные величины.

Один файл в двух позициях: две связанные позиции, один использованный уникальный файл. У позиции может быть несколько связанных вариантов, но для публикации используется только один явно выбранный; добавление связи не удаляет другие связи и не меняет текущий выбор. Связь без выбранного источника не становится источником публикации. Снятая галочка исключает действие публикации, но не удаляет связи. Пустая позиция не удаляет её старую managed-копию. Повторное добавление существующей связи идемпотентно.

Удаление source root удаляет его locations: `track_source` остаётся при наличии
другой location variant и удаляется для всех связей variant при удалении последней
location, даже если SHA-256 analysis cache сохраняется. Удаление выбранной связи
очищает selected source без автоматического выбора другого. Это изменение
назначения не переписывает отдельный snapshot текущей публикации и не запускает
fallback/republish; существующее автоматическое улучшение качества сохраняется,
но равное или худшее качество автоматически не подставляется. Ручное понижение
требует явного предупреждения и подтверждения.

Preview должен передавать текущие/ожидаемые версии метаданных, источника и публикации. Backend перепроверяет версии, доступность файлов, права, совместимость и коллизии непосредственно перед применением; client-side preview не гарантирует безопасность.

## 3. Теги в публикации — не metadata_version

В DBML `track_publication` хранит путь, формат, snapshot качества/аудио и версию, **но не полный набор реально записанных тегов**. `published_version` подтверждает предполагаемую актуальность, а не буквальное содержимое файла, который мог измениться извне.

 Для запрошенного UI потребуется операция чтения managed artifact:

- идентификатор публикации и путь;
- наблюдаемые теги в нормализованной форме с массивами значений;
- время чтения и наблюдаемый digest/состояние совпадения с ожидаемым;
- статус: прочитан / отсутствует / недоступен / ошибка разбора / изменён извне;
- отображение container-specific tags в общие поля, при необходимости raw namespace отдельно.

Это **предложение контракта**, не выбранная стратегия хранения. Можно возвращать наблюдаемое актуальное состояние без истории; кэш/инвалидацию нужно определить при реализации. Нельзя записывать ожидаемые локальные теги в колонку «сейчас в файле» до чтения и проверки реального результата.

В макете `track.published.tags` — независимый fixture-snapshot. Локальная правка не меняет его. Демонстрационная публикация создаёт новый snapshot в памяти. Реальное чтение контейнеров здесь отсутствует и не заявляется.

## 4. Артисты и альбомы

У локального артиста/релиза есть свои значения и связи с провайдером. Входные и опубликованные значения ARTIST, ALBUMARTIST, DATE и других полей живут **в файлах**, могут различаться по трекам и не агрегируются произвольно. Raw source tags остаются evidence и не используются как источник жанров.

Для overview нужен read-model множества значений: значение → количество файлов → раскрыть конкретные файлы. Для точного сравнения всегда можно выбрать один файл и увидеть все четыре источника значений. Множественные артисты сохраняются упорядоченными; массивы не сворачиваются в потерянное первое значение.

Уточнение владельца от 2026-10-29: `ALBUMARTIST` формирует артистов релиза,
`ARTIST` — исполнителей recording/позиции. Композитор, автор текста и иные
ролевые значения остаются метаданными и не порождают сущность артиста или
дополнительный link. Например, упоминание «текст Иван Алексеев, музыка Иван
Алексеев» не добавляет Ивана Алексеева к исполнителям NoizeMC. Отображаемый
credit/описание роли не является идентификатором и не создаёт дополнительную
связь.

Решение владельца от 2026-11-03 требует отдельное необязательное собственное
`sort_name` артиста, не подменяемое display name, и сохранение artist
disambiguation, genres, tags и provider links. `sort_name` редактируется только в карточке артиста; сортировочные значения ordered credits производны от него без fallback на display name и без исключений для альбома/трека. Для полного пользовательского
набора Navidrome metadata действует сквозной контракт: поле модели → подходящий
scope UI (видимо readonly и редактируемо) → перенос из выбранного источника →
соответствующий опубликованный тег → readback/проверка результата. Канонический
перечень и источники его проверки находятся в
[`navidrome-metadata.md`](../design/navidrome-metadata.md); этот список не
сужается по текущим API, backend-модели или fixtures. Исходные и опубликованные
колонки остаются track-specific и не выдаются как атрибуты артиста/альбома.
Жанры выбираются multiselect из общей библиотеки MusicBrainz, не свободным
текстом; genres не являются generic tags и не наследуются между scopes.
Редактирование артистов и конкретных изданий постоянно видно: read-mode и
редактирование используют те же поля/место, «Отменить» и Escape отменяют ввод,
ошибка сохранения сохраняет введённое, после сохранения значения остаются
видимыми readonly. См. [решение владельца от 2026-11-03](../design/decisions.md#решение-владельца-от-2026-11-03-полнота-редактируемых-метаданных-и-имя-сортировки).

## 5. Сборник, recordings и provider links

`collection_track_provider_link.provider_release_track_id` уникален. Позиция 01 локального сборника не обязана быть эквивалентом позиции 01 исходного альбома провайдера.

Связи записей provider-графа могут быть межпровайдерными: принадлежность
`provider_id` и native key остаётся у самой записи и не наследуется от её
связей. Правило и открытые последствия обновления/удаления таких записей описаны
в `docs/design/decisions.md`; этот UI-документ не задаёт отдельного поведения.

Разные provider Recording ID остаются разными `collection_recording`, даже если
фактически содержат одинаковую аудиозапись. Один `media_variant` можно
подтверждённо назначить нескольким таким recordings через независимые
`track_source` разных позиций:

```text
media_variant
  ├─ track_source → collection_track A → collection_recording A → provider recording A
  └─ track_source → collection_track B → collection_recording B → provider recording B
```

Результат поиска из конкретного издания используется как provenance/evidence
для выбора recording. `ALBUM`, `ALBUMARTIST`, локальные номера и дата сборника не
заменяются полями найденного чужого релиза. Один общий source не заставляет
объединять разные provider Recording ID и при публикации получает metadata
конкретной позиции.

В fixtures макета `providerTrackId` хранит **контекст найденного кандидата для сравнения**, а не команду вставить `collection_track_provider_link` в БД. Для provider-релиза связь позиции допустима; для локального сборника при реализации сохраняется recording-link с учётом ограничения выше.

## 6. Local provider

Утверждённый контракт ручных provider-записей описан в
[`../design/local-provider.md`](../design/local-provider.md). Отдельная вкладка
«Собственный каталог» управляет `provider_artist`, `provider_release` и `provider_recording`;
она не является локальной provider-колонкой или расширением формы создания
collection-релиза. Обязательны только not-null бизнес-поля соответствующей
таблицы DBML. Существующую сущность любого provider можно выбрать как ссылку,
сохраняя её ownership и native key, без копирования в Local. Поиск не создаёт
записи, а одинаковые имена не означают идентичность. Макет не задаёт удаления
provider-записей или распространения metadata при правке. Provider и library
независимы: удаление provider-записей никогда не удаляет local entities или
managed publications; удаление library entities сохраняет provider records, но
удаляет подтверждённые зависимые publications безопасной асинхронной операцией.

Удаление library entities — отдельный подтверждаемый async service operation:
publication удаляет только принадлежащий приложению managed file и publication
row; release — его positions/publications, но не standalone recordings; artist —
его связанные releases и напрямую связанные recordings, positions и publications.
Позиции удаляемых recordings в сохраняемых releases также удаляются. Точное
подтверждение перечисляет зависимости и output paths. Макет показывает очередь
запроса, но не выполняет filesystem/DB mutations. См. `../design/decisions.md`.

Для Local-релиза UI-модель содержит один носитель и упорядоченный массив позиций;
каждая позиция ссылается на существующий `provider_recording`. Номер вычисляется
из текущего порядка (`1..n`), не вводится и не сохраняется как независимое
переопределение. Название/длительность записи — defaults; только отличия хранятся
в `title_override` и `duration_override_ms`. Duration control принимает целые
секунды или `М:СС`, отображает `М:СС` и переводит значение в миллисекунды при
сохранении. Пустой массив допустим. Поля релиза включают основной/дополнительные
типы, язык и необязательный script. Жанры выбираются из общей библиотеки MusicBrainz по
MBID и каноническому имени; публикационный MusicBrainz genre не зависит от
наличия локальной библиотеки. Generic `tags` MusicBrainz и произвольные source
tags не являются fallback жанрами. Существующие scopes artist/recording/release
сохраняются без наследования release → recording/позиция. При отсутствии
локального каталога Local genres могут оставаться пустыми; см. `../design/genres.md`.

## 7. Состояния, которые должны быть в production

- Провайдер недоступен: показать кэш и дату, оставить ручное назначение/локальную публикацию.
- Опубликованный файл недоступен: в колонке тегов ошибка чтения, а не пустые теги или локальные значения.
- Кандидат исчез после нового поиска: ручной черновик не считать автоматически подтверждённым по устаревшему evidence.
- Файл несовместим: запрещённое назначение с причиной, не красный confidence без объяснения.
- Конфликт версии preview: остановить подтверждение, предложить пересчитать, сохранить операторский ввод.
- Пользователь отменил drag/диалог: ни локальное состояние, ни публикация не изменились.

## 8. Открытые вопросы реализации

До реализации UI предстоит определить schema/read-model входных групп и drafts,
а также точный механизм чтения публикаций. Изменение утверждённой matching policy
требует отдельного согласования; этот макет её не меняет. Модель provider
recording-связей и возможность одного variant обслуживать разные recordings уже
утверждены.
