# Данные для интерфейса: evidence и опубликованные теги

Этот документ описывает необходимые будущие UI-контракты, а не существующие API.
Утверждённые инварианты находятся в `docs/design`; физическая SQL-схема появится
только в плане соответствующего этапа.

## 1. Объяснение confidence без выдуманной математики

Технический дизайн содержит `match_candidate.confidence` в диапазоне `[0,1]` и
`evidence jsonb`, но пока не определяет формулу. UI не может честно объяснить
«как получено 94%», пока backend не предоставляет расчёт. В v2 удалены
иллюстративные проценты v1.

### Что оператор должен получить от matching

| Данные | Назначение в UI |
|---|---|
| Итог confidence `[0,1]` и версия алгоритма | Показать нормализованное значение, не объявляя его калиброванной вероятностью |
| Решение и порог | Почему можно автоматически привязать или нужна ручная проверка |
| Raw source и provider value | Конкретные сопоставленные значения |
| Нормализованные значения и правила | Например, совпало после нормализации регистра, а не буквально |
| Признак и его применимость | TITLE/ARTIST/duration/fingerprint/MBID/позиция/релиз; missing и not-applicable различаются |
| Weight, contribution, penalty | Откуда взялся итог. Значения предоставляет алгоритм, не frontend |
| Причина veto/конфликта | Live vs studio, разные recordings, несовместимое аудио, неоднозначное издание |
| Время и scope расчёта | Позиция, recording либо издание; track confidence не выдавать за release confidence |

Frontend должен проверять непротиворечивость объяснения: если итог взвешенный,
показывать формулу агрегации и полный набор вкладов/штрафов; если иной,
показывать соответствующий путь решения. Не суммировать произвольные признаки
до 100%. Отсутствие fingerprint — «не использован», не «совпал». Fingerprint,
tags и duration являются evidence формулы, а не отдельными decision methods.

**Что реально делает макет:** сравнивает исходные строки, нормализованные
NFKC/lowercase/пробелами строки, длительности с Δ секунд и номера. Высокий/низкий
verdict берётся из fixtures для проверки двух веток flow. Формула confidence,
веса и вклады показаны как не заданные. Это не реализация matching и не
предложение числового порога.

Подтверждённая связь хранит только `decision_method=automatic|manual`, а не
confidence. Automatic link может быть пересчитан новой policy; manual link
защищён от автоматического перевыбора. Ручной выбор не меняет confidence
кандидата и может не совпадать с текущей автоматической рекомендацией.

## 2. Частичность — несколько независимых чисел

Для группы нужны: количество уникальных файлов, доступных путей/вариантов, целевых позиций, назначенных позиций, выбранных для публикации, уже опубликованных и оставшихся свободных файлов.

Один файл в двух позициях: две назначенные позиции, один использованный файл. Снятая галочка исключает действие публикации, но не удаляет назначение. Пустая позиция не удаляет её старую managed-копию. Повторное подтверждение неизменённого плана не создаёт новые артефакты.

Preview должен передавать текущие/ожидаемые версии метаданных, источника и публикации. Backend перепроверяет версии, доступность файлов, права, совместимость и коллизии непосредственно перед применением; client-side preview не гарантирует безопасность.

## 3. Теги в публикации — не metadata_version

В DBML `track_publication` хранит путь, формат, snapshot качества/аудио и версию, **но не полный набор реально записанных тегов**. `published_version` подтверждает предполагаемую актуальность, а не буквальное содержимое файла, который мог измениться извне.

Для запрошенного UI потребуется операция чтения managed artifact:

- идентификатор публикации и путь;
- наблюдаемые теги в нормализованной форме с массивами значений;
- время чтения и наблюдаемый digest/состояние совпадения с ожидаемым;
- статус: прочитан / отсутствует / недоступен / ошибка разбора / изменён извне;
- отображение container-specific tags в общие поля, при необходимости raw namespace отдельно.

Это **предложение контракта**, не выбранная стратегия хранения. Можно возвращать наблюдаемое актуальное состояние без истории; кэш/инвалидацию нужно определить при реализации. Нельзя записывать ожидаемые локальные теги в колонку «сейчас в файле» до чтения и проверки реального результата.

В макете `track.published.tags` — независимый fixture-snapshot. Локальная правка не меняет его. Демонстрационная публикация создаёт новый snapshot в памяти. Реальное чтение контейнеров здесь отсутствует и не заявляется.

## 4. Артисты и альбомы

У локального артиста/релиза есть свои значения и связи с провайдером. Входные и опубликованные значения ARTIST, ALBUMARTIST, DATE и других полей живут **в файлах**, могут различаться по трекам и не агрегируются произвольно.

Для overview нужен read-model множества значений: значение → количество файлов → раскрыть конкретные файлы. Для точного сравнения всегда можно выбрать один файл и увидеть все четыре источника значений. Множественные артисты сохраняются упорядоченными; массивы не сворачиваются в потерянное первое значение.

## 5. Сборник, recordings и provider links

`collection_track_provider_link.provider_release_track_id` уникален. Позиция 01 локального сборника не обязана быть эквивалентом позиции 01 исходного альбома провайдера.

Разные provider Recording ID остаются разными `collection_recording`, даже если
фактически содержат одинаковую аудиозапись. Один `media_variant` можно
подтверждённо назначить нескольким таким recordings через независимые
`track_source` разных позиций:

```text
media_variant
  ├─ track_source → collection_track A → collection_recording A → provider recording A
  └─ track_source → collection_track B → collection_recording B → provider recording B
```

Результат поиска из конкретного издания используется как provenance/evidence
для выбора recording. `ALBUM`, `ALBUMARTIST`, локальные номера и дата сборника не
заменяются полями найденного чужого релиза. Один общий source не заставляет
объединять разные provider Recording ID и при публикации получает metadata
конкретной позиции.

В fixtures макета `providerTrackId` хранит **контекст найденного кандидата для сравнения**, а не команду вставить `collection_track_provider_link` в БД. Для provider-релиза связь позиции допустима; для локального сборника при реализации сохраняется recording-link с учётом ограничения выше.

## 6. Состояния, которые должны быть в production

- Провайдер недоступен: показать кэш и дату, оставить ручное назначение/локальную публикацию.
- Опубликованный файл недоступен: в колонке тегов ошибка чтения, а не пустые теги или локальные значения.
- Кандидат исчез после нового поиска: ручной черновик не считать автоматически подтверждённым по устаревшему evidence.
- Файл несовместим: запрещённое назначение с причиной, не красный confidence без объяснения.
- Конфликт версии preview: остановить подтверждение, предложить пересчитать, сохранить операторский ввод.
- Пользователь отменил drag/диалог: ни локальное состояние, ни публикация не изменились.

## 7. Отдельное согласование перед backend

Необходимо отдельно согласовать формулу confidence, порог automatic decision,
правила неоднозначности, schema/read-model входных групп и drafts и точный
механизм чтения публикаций. Модель provider recording-связей и возможность
одного variant обслуживать разные recordings уже утверждены.
