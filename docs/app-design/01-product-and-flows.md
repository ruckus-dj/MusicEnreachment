# Продукт и сценарии · v2

## 1. Основание и статус

Основание: шесть файлов [`../design/`](../design/), замечания пользователя к v1 и три его изображения. v2 заменяет flow первой версии. Исходный технический дизайн не изменяется этим предложением.

**Подтверждено пользователем:** можно публиковать часть релиза; неразмеченные файлы остаются во входящих. Полный уверенный релиз автоматически сопоставляется и публикуется. Неполный/неоднозначный попадает в ручной разбор. Сборник может не иметь provider-релиза, а отдельные recordings могут находиться в разных альбомах.

Также подтверждены: две темы с системным default; плотный интерфейс; текстовый поиск releases; drag-and-drop; объяснение совпадений; сравнение тегов трёх источников истины; три вида каталога.

## 2. Что означает каждая сущность

| Сущность | Что видит оператор |
|---|---|
| Входная группа | Файлы, предварительно сгруппированные по исходным тегам/папке. Это ещё не подтверждённое издание |
| Релиз провайдера | Конкретное издание: страна, год, каталог, носители и позиции |
| Локальный релиз | Собственная запись медиатеки, в том числе личный сборник без внешнего аналога |
| Recording | Композиция, которую можно использовать в нескольких локальных позициях |
| Позиция трека | Место в конкретном релизе; может иметь несколько связанных вариантов и один явно выбранный аудиоисточник для публикации |
| Вариант аудио | Технический файл с codec/качеством/тегами; может использоваться несколькими позициями |
| Публикация | Управляемый файл на диске. Его текущие теги могут отличаться от локально отредактированных |

Группы, draft-назначения, их сохранение и результаты matching ещё требуют API/read-model проработки. Макет не объявляет новые DBML-таблицы утверждёнными.

## 3. Общая цепочка

```text
Сканирование источников
  → теги + технический анализ + fingerprint
  → предварительные группы альбомов
  → поиск релизов + кандидаты по позициям
       ├─ полный, однозначный, все позиции уверенные
       │    → применить связи → опубликовать автоматически
       └─ неполный / неоднозначный / нет издания
            → входящие: ручной разбор
                 ├─ выбрать издание → назначить файлы его позициям
                 └─ сохранить локальный релиз → сопоставить recordings отдельно
            → выбрать позиции → preview → подтвердить
            → опубликована только выбранная часть
            → неразмеченные файлы остаются во входящих
```

Автоматический путь сохраняет ранее утверждённый инвариант: не повторяет и не понижает качество существующей публикации. Уверенность matching и качество аудио — разные величины. Отсутствие подходящего файла для одной позиции не блокирует ручную публикацию других.

Утверждённая matching policy, включая текстовую метрику RapidFuzz `token_set_ratio`, текущую версию `matching-rapidfuzz-v1`, порог применимости по совокупному confidence **≥0.70**, retrieval ranking, top-1 artist-fit и неизменные итоговые assignment profiles, описана в [`docs/design/decisions.md`](../design/decisions.md). Прототип показывает fixture-verdict и демонстрационные сравнения, но не рассчитывает confidence, его вклады или числовой результат и не выдаёт их за работу policy.

## 4. Экран входящих

Одна компактная таблица групп: название/папка, файлы, назначенные позиции, свободные файлы, режим, опубликованная часть, причина ручного разбора. Отсюда открывается понятное рабочее место, а не абстрактное «решение проблемы».

Примеры в макете:

- **Northern Lines:** 10 позиций у провайдера, 9 входных файлов. Семь уверенных назначений, один спорный трек, один неопознанный фрагмент, две позиции без файлов.
- **Small Hours:** 8 из 8, все fixture-verdict высокие. Команда демонстрации обработки показывает автоматическую публикацию без ручного drag-and-drop.
- **Road Notes:** личный сборник из 5 позиций. Provider-релиза нет. Recordings могут быть из Northern Lines, Signals, Small Hours и Collected Rooms.

## 5. Ручное сопоставление с изданием

1. Открыть входную группу. Слева явный текстовый поиск releases и кандидаты; в центре трек-лист выбранного издания; справа отдельный список неназначенных файлов.
2. Уверенные назначения предварительно заполнены. Неуверенные **не превращаются в подтверждённые молча**.
3. Выбрать строку → увидеть её теги. Нажать «Высокий / Низкий / Вручную» → увидеть признаки и отличия.
4. Перетащить файл на позицию или выбрать файл Enter/Space и нажать «Добавить вариант». Добавление создаёт связь и не снимает существующие связи, включая связи того же файла с другими позициями; повторное добавление той же связи ничего не меняет.
5. Среди связанных вариантов явно выбрать радиокнопкой один аудиоисточник для публикации. Добавление связи не меняет уже выбранный источник; если выбора ещё нет, добавленная связь не выбирается автоматически.
6. Снять галочки с позиций, которые не нужно публиковать. Публикация использует только выбранный источник; связанные альтернативы остаются связанными, а назначенный, но исключённый файл не получает нового действия публикации.
7. Preview показывает create/replace/unchanged/skip. Подтверждение меняет только выбранные bundles.

Drop меняет **черновик**, не исходный файл и не действующую публикацию. Переход между кандидатами хранит независимые черновики в макете; соответствующие правила persistence в продукте требуют проработки. Возврат к предыдущему изданию восстанавливает его назначения. Поиск нового кандидата не должен терять текущую раскладку.

Не представляем confidence как калиброванную вероятность. При ручном назначении показываем «Решение оператора» и сохраняем рассчитанный confidence кандидата без повышения до 100%.

## 6. Сборник без provider-релиза

1. Открыть локальный режим. Центральный список теперь состоит из **локальных позиций**, сформированных из группы, а не из треков чужого альбома.
2. Сохранить название, альбомного артиста, год и порядок сборника. Назначить его файлы позициям.
3. У позиции нажать «Найти recording», ввести название композиции/артиста.
4. Результат показывает composition, artist, duration и релиз, в котором найден recording. Релиз здесь **контекст доказательства**, а не целевой альбом.
5. Связать recording с локальной позицией. Название альбома провайдера не копируется в ALBUM сборника; TRACKNUMBER провайдера не заменяет локальный номер.
6. Публиковать выбранную часть. Recording-связь тоже необязательна: неизвестную композицию можно опубликовать с ручными/исходными данными.

Нельзя связывать один provider_release_track с несколькими локальными позициями
вопреки unique-ограничению DBML. Позиции могут разделять общий local recording,
когда provider Recording ID действительно один. Разные MBID остаются разными
local recordings, но один `media_variant` может быть подтверждённым source для
обоих. Подробности в `03-data-and-evidence.md`.

## 7. Медиатека и публикации

В глобальной медиатеке доступны **Артисты / Все альбомы / Все треки** и фильтр
**«В наличии / Не хватает / Все»**. «В наличии» у позиции означает доступный
исходник или существующий published audio; «Не хватает» — нет ни того, ни другого.
На артистах и альбомах частичный объект попадает в обе выборки: достаточно одной
позиции с аудио для «В наличии» и одной без аудио для «Не хватает». «Все» включает
весь отображаемый каталог, включая provider-only записи. Неизвестный total или
незагруженный provider cache не показывается как ноль, отсутствие или полная
дискография; default фильтра не задан. Наличие аудио, наличие исходников и
опубликованность имеют отдельные подписи/счётчики: «Есть аудио», «Есть исходники»,
«Опубликовано».

Карточка артиста → компактная шапка → раскрываемые альбомы → таблица треков.
Можно раскрыть несколько альбомов одновременно. Альбом также имеет
самостоятельный адрес. При открытии альбома виден полный трек-лист; строки
несовпадающих позиций остаются читаемыми и доступными, а match-state независимо
от published/metadata state. В режимах «В наличии» и «Не хватает» совпавшие
позиции могут быть акцентированы, остальные приглушены, но не отключены. В
«Все» соответствие фильтру не разделяет строки. Match-state не сообщается только
цветом. Трек открывает подробности выбранного источника, публикации и сравнение
тегов.

Выбор одного/нескольких артистов, альбомов или позиций открывает контекстный
preview; выбор артиста раскрывает его существующие альбомы и позиции. Один
агрегированный preview показывает `create/update/unchanged/unprocessable/skipped`
с причинами и деталями до позиции. Он использует только имеющиеся источники или
существующие публикации. Отсутствующий файл — пропуск с причиной, не создание
collection entities и не автоматический fallback. Provider-каталог можно
просматривать, но это не массовое создание медиатеки и не новая схема получения
полноты каталога.

Контроль текущих публикаций остаётся в контексте объектов медиатеки, не отдельной
вкладкой: там видны output path, snapshot, актуальность и attention. Операции —
только текущие running/retry/error; завершённая история не добавляется. План
публикации — preview перед применением, не пункт sidebar. Отдельная вкладка
«Собственный каталог» предназначена для ручного управления записями provider
Local и не является частью формы создания collection-релиза.

Для артиста допустима компактная сводка раздельных показателей, например
`Есть аудио:5альбомов—2полностью3частично·48треков` и
`Опубликовано:4альбома—1полностью3частично·39треков`, с переходом к подробностям.
Это UX-направление, а не требование добавить все метрики в каждое представление.
Для каждого показателя альбом учитывается при наличии хотя бы одной отвечающей
позиции; полный требует известного полного track-list издания и соответствия всех
позиций, частичный — как минимум одной отвечающей и одной не отвечающей позиции.
Если track-list неизвестен и наблюдаемые позиции не доказывают частичность,
полнота остаётся явной `unknown`; отсутствие каталога само по себе не определяет
полноту или частичность. Пустой `0/0` не полный. Число треков — число позиций
релизов, а не файловых вариантов или уникальных recordings между релизами.
«Есть аудио», «Есть исходники» и «Опубликовано» независимы; действующее правило
наличия аудио source ИЛИ существующий published audio остаётся неизменным. Если
счётчик исходников присутствует, он аналогичен, но не обязателен. Provider total
показывается только для известного scope partial cache, не как полная дискография;
выбор считать release-group или конкретные издания не определён. Для provider-linked
альбома знаменатель — число позиций известного издания; без provider total он не
выдумывается. Полнота публикации none/partial/full имеет текст и N/M; неизвестный
или пустой total не считается full. Подробности — в [решении владельца](../design/decisions.md#уточнение-владельца-от-2026-11-01-сводные-показатели-артиста).

Metadata difference от публикации — отдельный индикатор, независимый от полноты;
full-published объект может иметь metadata differences. «Метаданные изменились»
сравнивает эффективные metadata для явного обновления (с действующими merge,
защитой ручных полей и `absent`) с фактическими тегами, встроенной обложкой и
lyrics последней успешной CURRENT-публикации. Provider cache/технические версии
сами по себе не создают difference; изменения audio source/quality/path и
filesystem drift/missing отдельны. Успешная новая CURRENT-публикация, включая
успешную recovery-регистрацию, заменяет baseline; произвольное внешнее изменение
файла его не переписывает. Альбом может показывать число изменившихся треков с
раскрытием конкретных полей. Алгоритм/hash, периодичность и цвет пока не
определены. Получение provider данных само по себе не меняет опубликованные файлы;
правила распространения provider-данных в локальные metadata этим решением не
меняются.
Для обновления metadata уже опубликованных файлов пользователь выбирает объекты,
просматривает preview и подтверждает действие; новые provider данные и cache сами
по себе его не запускают. Это не меняет automatic quality improvement только для
AUDIO с сохранением CURRENT tags/cover/lyrics и не отменяет автоматическую первую
публикацию eligible matched complete releases. Подробности — в [решении владельца
от 2026-11-01](../design/decisions.md#уточнение-владельца-от-2026-11-01-подтверждённое-обновление-metadata-публикаций).
Отдельная возможная подсветка новых provider-значений защищённых полей остаётся
открытым вопросом; она не снимает защиту и не применяет значение автоматически.
Подробный критерий — в [уточнении владельца](../design/decisions.md#уточнение-владельца-от-2026-11-01-критерий-отличий-metadata-публикации).

Сохраняются no automatic downgrade, no fallback при удалении source и ручное
downgrade с предупреждением и подтверждением. Массовое подтверждение не обходит
matching ambiguity, protected manual tags или identity/authority guards. Новая
политика atomicity/cancellation для bulk не задаётся.

В текущих fixtures прототипа 4 артиста, 5 релизов, 37 позиций. Это не полная
дискография и не продуктовые counts; значения вычисляются из демонстрационных
сущностей.

**Издания MusicBrainz (уточнение владельца 2026-11-01):** конкретные издания со
связанными источниками или текущими публикациями показываются отдельными
плоскими строками, даже если относятся к одной release group; каждая строка
открывает свой track-list без дополнительной групповой ступени. Назначения,
track-lists, публикации и metadata не объединяются. Если у группы нет ни одного
такого издания, показывается одна запись отсутствующего альбома для release group;
отсутствующие альтернативные издания той же группы не добавляются, когда
фактическое издание уже есть. Группировка — по identity MusicBrainz release group,
не по названию; cross-provider grouping и canonical/recommended edition не
вводятся.

В детали отсутствующей группы оператор явно выбирает конкретное издание по
доступным характеристикам (например, год, страна, формат, число позиций,
disambiguation). До выбора track-list отсутствует, точное число недостающих
позиций показывается как `—`, не `0` и не полное число edition. После выбора
виден только его track-list; смена выбора заменяет список, не объединяет его с
другими. Нет автоматического first/standard/recommended/canonical выбора. Это
только просмотр: выбор не создаёт collection entities или публикацию, не
скачивает аудиофайлы и не подразумевает их наличие. Существующее издание открывается напрямую
со своим полным track-list.

Частичные объекты остаются в обеих выборках issue 6, а отсутствующие позиции
внутри конкретного издания не скрываются. Подсчёт issue 9 остаётся по позициям
каждого фактического издания; группировка отсутствующих групп его не меняет.
Provider/tracks denominator и сводка артиста для смешанных единиц release group и
конкретного издания остаются открытыми: нельзя приравнять одну группу к одному
изданию, суммировать несопоставимые единицы или переименовывать total в число
позиций. «Есть источник/публикация» означает связанный source или identity текущей
публикации; влияние runtime-доступности файла/output на regrouping не определено.
Удаление source не удаляет текущую публикацию. Издание сохраняет отдельную строку,
пока остаётся другой связанный источник или текущая публикация; без обоих
применяется правило отсутствующей группы.

## 8. Сравнение тегов

Пять колонок: **поле / исходник / провайдер / локальная медиатека / текущая публикация**. Последняя не подменяется текущими локальными данными. Есть области «Артист / Альбом / Трек», выбор конкретной позиции/файла и «Только отличия».

У артиста и альбома нет самостоятельного опубликованного аудиофайла. Поэтому их значения показываются **в контексте выбранного опубликованного трека**. Если у разных треков ARTIST/ALBUM/DATE отличаются, не выводить произвольное одно значение как «теги артиста». Для полного продукта нужен список конфликтующих значений и их файлов; макет демонстрирует переключение конкретного файла.

«Провайдер» — нормализованные metadata provider-cache, а не обязательно буквальный контейнерный тег. «Исходник» — массивы observed_tags. «Публикация» — результат чтения актуального managed artifact с путём и временем наблюдения. Отсутствие publication, отсутствие поля и ошибка чтения — разные состояния.

Управление пользовательскими музыкальными metadata не ограничивается read-only
сравнением: все используемые Navidrome поля доступны для редактирования на
подходящем уровне объекта, переноса из выбранного источника, публикации в
соответствующие теги и проверки результата. Полный перечень задаёт
[`документация Navidrome metadata`](../design/navidrome-metadata.md); поля не
исключаются из-за отсутствия в текущем backend. Собственное необязательное
`sort_name` артиста отделено от display name; sort-правила для нескольких
артистов не подразумеваются. Жанры — multiselect из общей библиотеки MusicBrainz,
не свободный текст и не generic tags; жанры не наследуются между scopes.

Сведения об артисте и конкретном издании постоянно видны в компактном read-mode.
«Редактировать» переключает те же поля на ввод и становится «Сохранить» без
изменения размеров/расположения формы и действия; место для «Отменить» зарезервировано.
Отмена и Escape отбрасывают несохранённый ввод, а ошибка сохранения его сохраняет.
После сохранения поля остаются видимыми readonly. Колонки исходника и текущей
публикации относятся только к конкретному треку, не к артисту или альбому.
Изменение metadata объекта само по себе не меняет источник и не запускает
публикацию. См. [решение владельца от 2026-11-03](../design/decisions.md#решение-владельца-от-2026-11-03-полнота-редактируемых-метаданных-и-имя-сортировки).

## 9. Остальные процессы

- **Setup:** серверный persistent tools-directory → автоматическая подготовка инструментов → output-каталог/формат → метаданные/итог. Общая рабочая папка staged source analysis настраивается позже в Settings и не является требованием Setup. Нет регистрации, DB credentials не редактируются в UI.
- **Инструменты:** автоматическая проверка не чаще раза в 24 часа и ручной refresh только сообщают; установка, проверка опубликованной upstream SHA-256 при наличии, обязательная `-version` каждого executable, активация и откат остаются отдельными явными действиями. Не принимать произвольный download URL и не сохранять upstream catalog в БД.
- **Пропал диск:** недоступный источник не удаляет публикацию; ручная публикация возможна для остальных доступных источников.
- **Удаление root:** удаление последней location variant снимает его `track_source`-связи и возможный selected-source выбор, но не выбирает альтернативу и не меняет текущую публикацию. Детали и правила качества: [решение владельца](../design/decisions.md#уточнение-владельца-от-2026-11-01-track_source-при-удалении-source-root).
- **Источники:** при добавлении оператор явно выбирает «На месте» (`in_place`) или «Через рабочую копию» (`staged`), без default; read-only политика показывается отдельно. Все staged-копии используют общую runtime-настройку серверной рабочей папки, отдельную от output. Её отсутствие не блокирует Setup/добавление, но блокирует staged processing. Изменение пути запрещено при использующих его операциях или сохранённых копиях; автоматического переноса нет.
- **Сбой части публикации:** показываем конкретную незавершённую операцию и текущую зарегистрированную копию; соседние успешные позиции не объявляем неуспешными. После обычного исключения файл может быть установлен без записи результата в БД. При recovery совпадения тегов и технических параметров frozen target с frozen inputs и текущей authority достаточно для регистрации без полной подготовки; байтовая идентичность и происхождение аудио из выбранного source не доказываются. Иначе выполняется полный retry. Время файла не доказывает успех. Для позиции доступна отдельная явная повторная публикация с полной подготовкой из выбранного source; preview `unchanged` остаётся без записи. Подробнее: [уточнение владельца](../design/decisions.md#уточнение-владельца-от-2026-11-01-критерий-recovery-публикации-и-явный-повтор).
- **Переименование/перенос:** сохранить правило и применить план — разные операции. Коллизии блокируют затронутую часть до явного решения.
- **Удаление:** библиотечные сущности и provider catalog — независимы. Единое
  действие «Удалить» в медиатеке удаляет только publication, release с его
  позициями/publications либо artist с его зависимыми releases и напрямую
  связанными recordings/positions/publications. Release deletion не удаляет
  standalone recordings. Provider records всегда сохраняются; удаление provider
  records — отдельный процесс, не UI «Собственного каталога». Все library deletion
  flows подтверждают точный scope и выполняются асинхронно через service operation;
  сначала удаляются только принадлежащие приложению managed output files,
  затем строки. Source read-only по умолчанию; очистка после успеха не включается
  автоматически.
- **Проверка текущих публикаций:** для уже зарегистрированных аудиофайлов позиций периодическая проверка сравнивает сохранённые size и `mtime`, отмечает missing/drift и не переписывает baseline по произвольному файлу. Artwork и lyrics встроены в аудиофайл; отдельные файлы публикации для них не проверяются. Недоступность output root не означает missing. Интервал не определён; неизвестные файлы не сопоставляются автоматически.
- **Смена output:** в Settings текущий `/srv/music` read-only; серверный picker задаёт только кандидата, а отдельное подтверждение предупреждает о сбросе всех queues/jobs и удалении всех DB-ссылок на прежний output, включая строки публикаций и ссылки на размещённые в нём служебные файлы. Старые физические файлы сохраняются, автоматической перепубликации нет; source inventory, library entities/source links и analyses сохраняются. Независимая общая рабочая папка staged source analysis не сбрасывается: сохраняются её настройка, AUDIO-копии, DB-отслеживание (ownership, соответствие источнику и пригодность) и незавершённые запрошенные analysis steps. Сброшенная обработка не возобновляется автоматически ни вследствие reset, ни после последующего перезапуска; явный запуск может переиспользовать пригодную копию. Queued jobs не блокируют, running/claimed блокируют, включая повторную проверку непосредственно при подтверждении. Состояние в прототипе выбирается демонстрационным селектором и не является настройкой продукта. Статический макет показывает подтверждение, но не выполняет reset и оставляет все данные/fixtures прежними.
- **Конфликт версии:** пересчитать план, не перезаписывать чужие изменения молча. Нет выдуманной истории/undo.

## 10. Открытые решения, не блокирующие макет

1. Изменения утверждённой matching policy требуют отдельного согласования; макет таких изменений не предлагает.
2. Контракт групп входящих, сохранение drafts и повторное matching.
3. Чтение актуальных тегов публикации и определение расхождений digest; история не нужна.
4. Минимум Setup, проверка пересечения каталогов и перенос tools/output.
5. Именование, коллизии и удаление managed bundles.
6. Политика перезаписи ручных метаданных автоматикой; копирование полей остаётся явным.
7. Необязательные assets, ручная загрузка artwork/lyrics и права на контент.
8. Безопасные River retry/cancel, без глобального kill.

Частичная публикация, работа без provider-релиза, плотная компоновка и темы **уже не открытые вопросы**. Spotify/Discogs, плеер, плейлисты, видео, роли пользователей и история из референсов не импортируются в область продукта.

## 11. Local provider

На отдельной вкладке **«Собственный каталог»** оператор просматривает и ищет provider artists, releases и recordings, открывает запись и явно создаёт или редактирует её. Результаты поиска только показывают существующие записи: имя или название не создаёт новую сущность автоматически и не выполняет merge. Перед созданием оператор ищет подходящий объект у существующих providers. UI удаления provider-записей нет; их отдельный процесс не удаляет library entities или publications, а удаление library entities не удаляет provider records.

Форма требует только бизнес-поля `[not null]` DBML: artist `name`, release `release_group_title` и `title`, recording `title`. Nullable поля показываются как необязательные. Любая существующая запись любого provider может быть выбрана как ссылка с сохранением её provider ownership и native key; выбор не копирует её в Local. Для Local-записи показывается собственный Local key. Изменение metadata не запускает публикацию. Нет drafts, статусов пригодности, удаления provider-записей, удаления исходников или автоматической публикации. Межпровайдерные последствия изменения/удаления provider-записей и распространение metadata остаются открытыми и UI не обещает их.

У Local-релиза один носитель. Его трек-лист содержит позиции, выбирающие существующие самостоятельные композиции из каталога; новая композиция из формы релиза не создаётся. Название и длительность выбранной композиции видны как defaults, а поля переопределения необязательны. Позиции добавляются, удаляются и переставляются; их номера автоматически пересчитываются с 1. Пустой список разрешён. Длительность override вводится целыми секундами или `М:СС`, отображается как `М:СС` и сохраняется как `duration_ms`. Релиз также содержит primary/secondary release type и language, без script. Жанры выбираются только из общей библиотеки жанров текущей конфигурации MusicBrainz (public/self-hosted) — поиск, multiselect и autocomplete без свободного ввода; отсутствие или ошибка каталога отключают только picker и не блокируют создание, редактирование или публикацию Local с пустыми genres. Контракт: [`genres.md`](../design/genres.md).

В статическом прототипе каталог, формы, поиск, ссылки и подтверждение сохранения работают на in-memory fixtures; это не API и не production CRUD.
