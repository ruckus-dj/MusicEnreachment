# Продукт и сценарии · v2

## 1. Основание и статус

Основание: шесть файлов [`../design/`](../design/), замечания пользователя к v1 и три его изображения. v2 заменяет flow первой версии. Исходный технический дизайн не изменяется этим предложением.

**Подтверждено пользователем:** можно публиковать часть релиза; неразмеченные файлы остаются во входящих. Полный уверенный релиз автоматически сопоставляется и публикуется. Неполный/неоднозначный попадает в ручной разбор. Сборник может не иметь provider-релиза, а отдельные recordings могут находиться в разных альбомах.

Также подтверждены: две темы с системным default; плотный интерфейс; текстовый поиск releases; drag-and-drop; объяснение совпадений; сравнение тегов трёх источников истины; три вида каталога.

## 2. Что означает каждая сущность

| Сущность | Что видит оператор |
|---|---|
| Входная группа | Файлы, предварительно сгруппированные по исходным тегам/папке. Это ещё не подтверждённое издание |
| Релиз провайдера | Конкретное издание: страна, год, каталог, носители и позиции |
| Локальный релиз | Собственная запись медиатеки, в том числе личный сборник без внешнего аналога |
| Recording | Композиция, которую можно использовать в нескольких локальных позициях |
| Позиция трека | Место в конкретном релизе; имеет один выбранный аудиоисточник |
| Вариант аудио | Технический файл с codec/качеством/тегами; может использоваться несколькими позициями |
| Публикация | Управляемый файл на диске. Его текущие теги могут отличаться от локально отредактированных |

Группы, draft-назначения, их сохранение и результаты matching ещё требуют API/read-model проработки. Макет не объявляет новые DBML-таблицы утверждёнными.

## 3. Общая цепочка

```text
Сканирование источников
  → теги + технический анализ + fingerprint
  → предварительные группы альбомов
  → поиск релизов + кандидаты по позициям
       ├─ полный, однозначный, все позиции уверенные
       │    → применить связи → опубликовать автоматически
       └─ неполный / неоднозначный / нет издания
            → входящие: ручной разбор
                 ├─ выбрать издание → назначить файлы его позициям
                 └─ сохранить локальный релиз → сопоставить recordings отдельно
            → выбрать позиции → preview → подтвердить
            → опубликована только выбранная часть
            → неразмеченные файлы остаются во входящих
```

Автоматический путь сохраняет ранее утверждённый инвариант: не повторяет и не понижает качество существующей публикации. Уверенность matching и качество аудио — разные величины. Отсутствие подходящего файла для одной позиции не блокирует ручную публикацию других.

Числовой automatic threshold для confidence, веса, обработка равных кандидатов и конкретные признаки **не придуманы**. В прототипе используются явные fixture-verdict и воспроизводимые raw-сравнения; алгоритм должен быть отдельно согласован.

## 4. Экран входящих

Одна компактная таблица групп: название/папка, файлы, назначенные позиции, свободные файлы, режим, опубликованная часть, причина ручного разбора. Отсюда открывается понятное рабочее место, а не абстрактное «решение проблемы».

Примеры в макете:

- **Northern Lines:** 10 позиций у провайдера, 9 входных файлов. Семь уверенных назначений, один спорный трек, один неопознанный фрагмент, две позиции без файлов.
- **Small Hours:** 8 из 8, все fixture-verdict высокие. Команда демонстрации обработки показывает автоматическую публикацию без ручного drag-and-drop.
- **Road Notes:** личный сборник из 5 позиций. Provider-релиза нет. Recordings могут быть из Northern Lines, Signals, Small Hours и Collected Rooms.

## 5. Ручное сопоставление с изданием

1. Открыть входную группу. Слева явный текстовый поиск releases и кандидаты; в центре трек-лист выбранного издания; справа отдельный список неназначенных файлов.
2. Уверенные назначения предварительно заполнены. Неуверенные **не превращаются в подтверждённые молча**.
3. Выбрать строку → увидеть её теги. Нажать «Высокий / Низкий / Вручную» → увидеть признаки и отличия.
4. Перетащить свободный файл на позицию. Альтернатива без мыши: выбрать файл Enter/Space и нажать «Назначить выбранный» в строке.
5. Если строка занята, подтвердить замену. Вытесненный файл снова свободен, если не назначен другой позиции.
6. Если файл уже назначен, предложить перенос или явное повторное использование. Не нарушать M:N модели.
7. Снять галочки с позиций, которые не нужно публиковать. Назначенный, но исключённый файл тоже останется без нового действия публикации.
8. Preview показывает create/replace/unchanged/skip. Подтверждение меняет только выбранные bundles.

Drop меняет **черновик**, не исходный файл и не действующую публикацию. Переход между кандидатами хранит независимые черновики в макете; соответствующие правила persistence в продукте требуют проработки. Возврат к предыдущему изданию восстанавливает его назначения. Поиск нового кандидата не должен терять текущую раскладку.

Не представляем confidence как калиброванную вероятность. При ручном назначении показываем «Решение оператора» и сохраняем рассчитанный confidence кандидата без повышения до 100%.

## 6. Сборник без provider-релиза

1. Открыть локальный режим. Центральный список теперь состоит из **локальных позиций**, сформированных из группы, а не из треков чужого альбома.
2. Сохранить название, альбомного артиста, год и порядок сборника. Назначить его файлы позициям.
3. У позиции нажать «Найти recording», ввести название композиции/артиста.
4. Результат показывает composition, artist, duration и релиз, в котором найден recording. Релиз здесь **контекст доказательства**, а не целевой альбом.
5. Связать recording с локальной позицией. Название альбома провайдера не копируется в ALBUM сборника; TRACKNUMBER провайдера не заменяет локальный номер.
6. Публиковать выбранную часть. Recording-связь тоже необязательна: неизвестную композицию можно опубликовать с ручными/исходными данными.

Нельзя связывать один provider_release_track с несколькими локальными позициями
вопреки unique-ограничению DBML. Позиции могут разделять общий local recording,
когда provider Recording ID действительно один. Разные MBID остаются разными
local recordings, но один `media_variant` может быть подтверждённым source для
обоих. Подробности в `03-data-and-evidence.md`.

## 7. Каталог

Глобальная медиатека: **Артисты / Все альбомы / Все треки**. Поиск и фильтр «все / опубликованные / неопубликованные» работают внутри выбранного вида. В списке треков единица строки — позиция в релизе: одна композиция может встречаться несколько раз, но это не дубликаты одной публикации.

Карточка артиста → компактная шапка → раскрываемые альбомы → таблица треков. Можно раскрыть несколько альбомов одновременно. Альбом также имеет самостоятельный адрес. Трек открывает подробности выбранного источника и сравнение тегов.

В прототипе 4 артиста, 5 релизов, 37 позиций. Счётчики вычисляются из демонстрационных сущностей, а не из статических чисел «24 релиза» первой версии.

## 8. Сравнение тегов

Пять колонок: **поле / исходник / провайдер / локальная медиатека / текущая публикация**. Последняя не подменяется текущими локальными данными. Есть области «Артист / Альбом / Трек», выбор конкретной позиции/файла и «Только отличия».

У артиста и альбома нет самостоятельного опубликованного аудиофайла. Поэтому их значения показываются **в контексте выбранного опубликованного трека**. Если у разных треков ARTIST/ALBUM/DATE отличаются, не выводить произвольное одно значение как «теги артиста». Для полного продукта нужен список конфликтующих значений и их файлов; макет демонстрирует переключение конкретного файла.

«Провайдер» — нормализованные metadata provider-cache, а не обязательно буквальный контейнерный тег. «Исходник» — массивы observed_tags. «Публикация» — результат чтения актуального managed artifact с путём и временем наблюдения. Отсутствие publication, отсутствие поля и ошибка чтения — разные состояния.

## 9. Остальные процессы

- **Setup:** серверный persistent tools-directory → автоматическая подготовка инструментов → output-каталог/формат → метаданные/итог. Нет регистрации, DB credentials не редактируются в UI.
- **Инструменты:** периодическая проверка только сообщает; установка, upstream checksum/signature при наличии, `--version`, активация и откат остаются явными. Не принимать произвольный download URL и не сохранять upstream catalog в БД.
- **Пропал диск:** недоступный источник не удаляет публикацию; ручная публикация возможна для остальных доступных источников.
- **Сбой части публикации:** показываем конкретный bundle, текущую копию и фазу; соседние успешные позиции не объявляем неуспешными.
- **Переименование/перенос:** сохранить правило и применить план — разные операции. Коллизии блокируют затронутую часть до явного решения.
- **Удаление:** публикации и исходники — разные действия. Source read-only по умолчанию; очистка после успеха не включается автоматически.
- **Конфликт версии:** пересчитать план, не перезаписывать чужие изменения молча. Нет выдуманной истории/undo.

## 10. Открытые решения, не блокирующие макет

1. Формула confidence, признаки, веса, missing-data policy, automatic threshold/ambiguity policy и версия алгоритма.
2. Контракт групп входящих, сохранение drafts и повторное matching.
3. Чтение актуальных тегов публикации и определение расхождений digest; история не нужна.
4. Минимум Setup, проверка пересечения каталогов и перенос tools/output.
5. Именование, коллизии и удаление managed bundles.
6. Политика перезаписи ручных метаданных автоматикой; копирование полей остаётся явным.
7. Необязательные assets, ручная загрузка artwork/lyrics и права на контент.
8. Безопасные River retry/cancel, без глобального kill.

Частичная публикация, работа без provider-релиза, плотная компоновка и темы **уже не открытые вопросы**. Spotify/Discogs, плеер, плейлисты, видео, роли пользователей и история из референсов не импортируются в область продукта.
