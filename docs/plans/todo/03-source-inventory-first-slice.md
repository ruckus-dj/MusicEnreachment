# План: первый срез инвентаря источников

## Статус

Согласованный исполнимый план из 10 этапов. Общий черновик области
`docs/plans/to-decompose/source-inventory-and-analysis.md` сохраняет
решения для следующего этапа анализа.

**Подтверждено владельцем:** следующий план заканчивается работающим
инвентарём папок и проверкой их аудиопотока через уже доступный после Setup
`ffprobe`; fingerprint (`fpcalc`), SHA-256 и остальной технический анализ —
отдельный план. Scan запускается только кнопкой, добавление root его не запускает;
инвентарь ограничен расширениями `.flac`, `.wav`, `.aif`, `.aiff`, `.ape`,
`.wv`, `.mp3`, `.m4a`, `.aac`, `.ogg`, `.opus`, `.wma`, `.mka` без учёта
регистра. Расширение служит первым фильтром; `ffprobe` подтверждает аудио.
Файлы без аудиодорожки остаются в инвентаре с отдельным статусом; если
файл не изменился, повторный scan не запускает для него `ffprobe` и дальнейшую
обработку. Ошибка `ffprobe` сохраняется как проблема данного файла, scan
остальных файлов продолжается; при следующем scan проблемный файл проверяется
снова, даже если он не изменился. Удаление root удаляет все его
source locations из БД, но не трогает входные файлы на диске или уже
существующую медиатеку в output. Режим `staged` и work-directory
отложены до следующего плана; этот срез читает source напрямую.
Следующие пункты не нужно переоткрывать: source по умолчанию read-only;
`source_root` и `source_location` отличаются от managed publication; scan
generation фиксируется лишь после полностью успешного обхода; недоступный
root не удаляет прежний inventory; пути сохраняются без case folding;
directory symlinks не обходятся, выход за root запрещён; `device`/`inode`
не определяют идентичность. Основание:
`docs/design/decisions.md`, `docs/design/data-model.md`,
`docs/plans/to-decompose/source-inventory-and-analysis.md`.

## Цель, сценарий и ограничения

Оператор после Setup добавляет серверный каталог, видит его путь, доступность
и состояние последнего успешного сканирования, вручную запускает scan и
просматривает постраничный список обнаруженных файлов. Повторный scan
обновляет новые/изменённые пути и удаляет отсутствующие только при полностью
успешном обходе. Отключение root останавливает новые scans и оставляет
последний инвентарь видимым. Удаление root с явным подтверждением удаляет
его инвентарь из БД, но не удаляет файлы источника и managed output.
Для недоступного root видны прежние записи и ошибка, а не фиктивный пустой
результат.

В этом плане нет полного технического анализа, fingerprint, дедупликации,
source deletion, импортирования уже опубликованной библиотеки, автоматического
расписания, выбора `in_place`/`staged`, настройки work-directory,
сканирования по перетаскиванию файлов из браузера, `media_variant`,
MusicBrainz или нового env-параметра. Обход читает metadata исходного
дерева и запускает `ffprobe` на подходящих по расширению файлах напрямую
из source. В следующем плане выбор staged будет возможен только вместе
с временной копией. Проверка аудиопотока не является полным анализом.

## Общие правила исполнения

- Этапы 1–10 выполнять по порядку, один этап — один небольшой проверяемый
  change set. Перед ним читать соседние реализации и тесты. Не переписывать
  уже применявшиеся SQL-миграции: добавлять новую пару `.tx.up.sql` /
  `.tx.down.sql` с версией позже последней существующей.
- В каждом этапе обновить относящиеся к изменению тесты. **Единственный
  локальный тест/build gate — `task verify`**; не запускать дополнительные
  локальные suites или платформенные сборки. После изменения API pipeline
  генерации выполняется внутри `task verify`; generated-клиент вручную не
  править. При неудаче `task verify` разрешена узкая диагностика причины.
- Для интеграции с PostgreSQL использовать существующий
  `backend/internal/testpostgres` и `*_integration_test.go`; для файловой
  системы — управляемые тестовые каталоги и события/барьеры вместо sleeps.
  Проверять реальные rollback/commit и доставку River, а не только mocks.
- После завершения независимый проверяющий агент сопоставляет каждый пункт
  плана с кодом и повторно запускает `task verify`; автор изменений не
  объявляет выполнение полным самостоятельно. Ручная проверка реального
  браузерного сценария дополняет, а не заменяет тесты.

### 4. Обход файловой системы без преждевременного изменения inventory

**Зависимости:** 2–3. **Изменить:** новый компонент обхода в
`backend/internal/service/source_scan.go`; не помещать файловый обход в
API или persistence.

Идти от зарегистрированного root, не следовать directory symlinks и не
выходить за root через file symlink; symlink entries пропускать целиком.
Включать только обычные файлы с одним из 13 утверждённых расширений
(сравнение без учёта регистра) и с точным relative path, size и mtime
из stat. Файлы без расширения и с иным расширением не записывать.
Для новых/изменённых файлов запускать активный managed `ffprobe` по
абсолютному server path с timeout 120 секунд и лимитом JSON-ответа 1 MiB;
разбирать структуру
streams: есть хотя бы один audio stream — `audio`, успешный ответ без него —
`no_audio`. Неизменённые `audio` и `no_audio` не проверять повторно;
`probe_error` проверять на каждом scan. Ошибку запуска/чтения хранить как
`probe_error` с безопасным текстом и продолжать scan, не приравнивать её к
`no_audio`. Никаких fingerprint, tags, codec, duration здесь не сохранять.
Игнорировать каталоги как locations; ошибки чтения любого поддерева и
cancellation делают
обход неуспешным целиком. Пакетно сохранять кандидатов только для текущего
operation ID. Progress показывает `queued`/`traversing`/`applying`, без
придуманного процента или использования `bytes_completed` как счётчика
файлов. Для изменяющегося файла сверять metadata до и после probe, а перед
применением кандидатов повторно проверять их актуальность; при
расхождении завершать scan неуспехом, а не фиксировать ложный snapshot.

**Проверить:** временные деревья с каждым из 13 расширений, вариантами их
регистра, неаудио расширениями, файлом без расширения, nested paths,
именами с разным регистром, symlink cycle/escape, permission/cancellation
и изменением файла через детерминированный барьер. Fake command runner
возвращает JSON с audio/video-only/без streams/ошибкой/чрезмерным выводом;
повторный scan не вызывает probe для неизменённых `audio` и `no_audio`,
но вызывает для `probe_error` и изменённых файлов. До успешного применения
все старые locations неизменны.

### 5. River scan operation и выполнение worker

**Зависимости:** 2–4. **Изменить:**
`backend/internal/service/operations.go`, `backend/internal/jobs/`,
`backend/internal/app/app.go`, repository enqueue.

Запускать operation с snapshot только root ID, ожидаемого configured path
и версии snapshot; River args несут только operation ID. Operation и River
job создавать атомарно по существующему `InsertTx` boundary. Создание
operation и удаление root сериализовать блокировкой root в БД: нельзя
поставить scan на удаляемый root или удалить root после проверки,
но до записи active scan. Worker перечитывает root, проверяет завершённый
Setup, платформу, enabled state и наличие active verified `ffprobe` до
обхода; отсутствие рабочего инструмента проваливает весь scan, не превращая
каждый файл в `probe_error`. Затем worker
запускает обход, применяет результаты одной транзакцией и только после
успешного применения помечает operation succeeded. Ошибка сохраняет
безопасную причину и старый inventory. Один root не сканируется параллельно
дважды. Не менять dispatch существующих install/move.

**Проверить:** PostgreSQL/River dispatcher tests с настоящими транзакциями:
enqueue rollback, duplicate scans, successful delivery, traversal failure.
Без sleep; блокировать worker тестовым event/barrier.

### 6. Retry и startup recovery сканирования

**Зависимости:** 5. **Изменить:** `backend/internal/jobs/`,
`backend/internal/service/operations.go`, repository методы очистки кандидатов.

Failed scan допускает явный retry той же operation с **новым** обходом;
старые кандидаты удаляются до retry. На startup осиротевший queued/running
scan без живого River job переводится в failed с возможностью retry; его
кандидаты очищаются, успешный inventory не трогается. Для окна «DB commit
уже прошёл, operation ещё не succeeded» восстановление сравнивает
сохранённый operation ID последнего применённого поколения и доводит
operation до succeeded без повторного удаления locations. Если DB commit
не произошёл, старый inventory остаётся видимым. Не менять политику
восстановления install/move.

**Проверить:** PostgreSQL/River dispatcher tests повторного обхода,
прерывания до/после apply, startup recovery, preservation при ошибке
и отсутствия побочных изменений install/move. Управлять порядком событий
тестовыми барьерами, без ожиданий по времени.

## Критерии готовности

1. Оператор может зарегистрировать read-only root и просмотреть inventory
   без доступа браузера к файловой системе сервера.
2. Новый, изменённый и удалённый путь корректно отражаются после успешного
   повторного scan; неизменённый location сохраняет identity.
3. Недоступный root, частичный обход, изменение файла во время обхода,
   отмена, падение worker и rollback БД не стирают прошлый inventory.
4. Повторный scan root не начинается параллельно; retry после failure
   выполняет новый полный обход, не применяя старые кандидаты.
5. Path change не выдаёт старые locations за инвентарь нового пути;
   отключённый root сохраняет записи и не запускает scans; удалённый root
   теряет только свои locations в БД, не исходники и не output.
6. Case-sensitive имена не сливаются; symlink не даёт выйти за root;
   source bytes не изменяются; ровно 13 утверждённых аудиорасширений
   попадают в inventory без регистрации остальных файлов.
7. REST/OpenAPI/client согласованы, операции наблюдаемы через REST/SSE,
   а реальный экран различает пустоту, сбой и устаревшие данные.
8. `audio` подтверждается ffprobe; `no_audio` не проверяется повторно до
   изменения файла, а `probe_error` остаётся видимой проблемой и
   перепроверяется при следующем scan без остановки остальных файлов.
9. `task verify` и независимая проверка плана проходят; в этом срезе
   нельзя выбрать `staged` без отдельного следующего плана.
