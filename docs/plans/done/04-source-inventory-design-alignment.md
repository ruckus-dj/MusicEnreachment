# План: привести инвентарь источников к утверждённому дизайну

## Статус и выбор следующего шага

Следующий этап после `done/03-source-inventory-first-slice.md` — исправить
расхождения уже поставленного инвентаря, зафиксированные в
`docs/audit/design-implementation-2026-10-01.md`. Доступность корня и Windows
amd64 обещаны в завершённом плане и техническом дизайне, поэтому сначала
восстанавливаем их, а уже потом отдельно прорабатываем полный анализ. Этот
этап не вводит `media_variant`, staged mode, work-directory, SHA-256, fingerprint,
matching и публикацию. Их границы и ещё не принятые продуктовые решения
остаются в `docs/plans/to-decompose/source-inventory-and-analysis.md`.

**Цель оператора:** при потере доступа к каталогу видеть сохранённый инвентарь
и достоверную ошибку, на Windows amd64 регистрировать абсолютный серверный
путь, а в диагностическом режиме не изменять корни.

**Утверждённые основания:** `docs/design/decisions.md` (поддержка Windows
amd64, диагностический режим и source reconciliation),
`docs/design/deployment.md` (недоступный root оставляет прошлый inventory),
`docs/design/external-tools.md` (проверка работоспособности managed tools),
`docs/plans/done/03-source-inventory-first-slice.md` (доступность, статусы и
границы проверки аудиопотока). Новых продуктовых решений план не принимает.
**Продуктовых вопросов для этого корректирующего этапа нет:** требуемые
платформы, поведение при недоступности и запрет мутаций в диагностике уже
зафиксированы. Для последующего полного анализа отдельно понадобятся решения
о составе технических данных, политике повторного анализа и границах
staged-обработки; этот план их не подменяет.
При обнаружении неоднозначности, не разрешимой этими документами, остановить
только зависимый пункт и явно спросить владельца, не вводя молчаливый default.

## Порядок исполнения

Каждый пункт — отдельный небольшой change set с тестами именно его поведения.
Перед правкой прочитать существующие tests. Единственный локальный test/build
gate — `task verify`; узкий запуск допустим только для диагностики его
неудачи. Не править старые SQL-миграции и generated-клиент вручную. После
каждого проверенного инкремента — отдельный commit в стиле истории проекта
только если сессия исполнения получила явное разрешение на commits.

### 1. Ослабить платформенно неверное ограничение пути в БД

**Зависимости:** нет.

Добавить **новую** `.tx.up.sql`/`.tx.down.sql` пару в
`backend/internal/migrations/` после существующих версий: убрать `LIKE '/%'`
для `source_root.configured_path`; оставить проверку абсолютности в
`settings.NormalizePath` и service-валидации. Не принимать через HTTP
произвольный относительный путь и не переписывать применённую миграцию.
В `backend/internal/persistence/*integration_test.go` проверить, что после
миграции БД принимает строку `C:\Music` и `/srv/music`, а service отвергает
относительный путь. В существующей Windows CI matrix отдельный unit test
проверяет `settings.NormalizePath` на реальном Windows `C:\Music`;
PostgreSQL-проверка строки на Unix и Windows-проверка нормализации вместе
доказывают две границы, но не заменяют Windows end-to-end с PostgreSQL.
Проверить rollback новой пары на чистой тестовой БД и `task verify`;
платформенные сборки оставить CI. Основание:
`docs/audit/design-implementation-2026-10-01.md`, пункт 2.

### 2. Сохранять недоступность root, не меняя его inventory

**Зависимости:** нет.

В `backend/internal/persistence/source_repository.go` добавить адресное
обновление `status='unavailable'` и непустой безопасной причины для текущего
root (SQL CHECK запрещает `NULL`, а непустота нужна для понятной ошибки);
не изменять `scan_generation`, `inventory_path`, locations или
`last_successful_scan_at`. Проверить конкуренцию с новым успешным scan:
устаревшая ошибка старой operation не должна перезаписать его `available`.
Сохранить существующую транзакцию успешного apply, очищающую ошибку. В
PostgreSQL integration tests проверить последовательность «успех →
недоступность → успешный повтор» и сохранность идентичности/содержимого
locations; затем `task verify`. Основание: пункт 1 аудита.

### 3. Отмечать только доказанную недоступность при сканировании

**Зависимости:** 2.

В `backend/internal/service/source_scan.go`,
`backend/internal/service/source_scan_start.go` и
`backend/internal/jobs/scan_worker.go` провести сообщение о недоступности
зарегистрированного каталога к методу пункта 2, включая отказ проверки пути
перед запуском и ошибку обхода корня. Отдельная `probe_error` одного файла,
отмена, конфликт/ошибка БД или недоступный инструмент не означают, что root
недоступен. Причина в root — безопасный для UI текст без сырого traceback;
ошибка operation остаётся отдельно. Детерминированными service/worker и
PostgreSQL tests проверить эти случаи и повторный успех без потери прошлого
inventory; затем `task verify`.

### 4. Обновлять статус на открытом экране после failure

**Зависимости:** 2–3.

`frontend/src/features/sources/SourceScanControl.tsx` вызывает обновление
root не только после success, но и после перехода операции в failed;
`SourceDetailScreen.tsx`, `SourcesScreen.tsx` и `sourcesApi.ts` уже умеют
показывать `unavailable`, безопасную причину и последний inventory:
сохранить это поведение, не выдавая ошибку отдельного файла за
недоступность каталога. Не вводить
таймеры или фиктивные проценты: SSE остаётся сигналом для повторного REST-read.
Дополнить соседние RTL-тесты перехода, повторного открытия и восстановления
после успешного scan; `task verify`, затем вручную проверить экран desktop и
узкий viewport на реальном API. Основание: пункт 1 аудита и S09/S10 в
`docs/app-design/02-screens.md`.

### 5. Закрыть мутации root в диагностическом режиме

**Зависимости:** нет.

`backend/internal/api/sources.go`: добавить существующий
`requireSupportedPlatform` к POST/PATCH/DELETE корня, сохранив GET для
чтения диагностики и уже действующий запрет POST scan. В
`backend/internal/api/sources_test.go` и интеграционном тесте проверить
несовпадение платформ после завершённого Setup: GET разрешён, POST/PATCH/DELETE
и scan дают существующий ответ `503`, данные БД не изменились; нормальная платформа сохраняет
возможность всех команд. `task verify`. Основание: пункт 3 аудита и
`docs/design/decisions.md` о diagnostic mode.

### 6. Исправить противоречие в документации проверки версии

**Зависимости:** нет.

В `docs/design/decisions.md` и `docs/design/external-tools.md` заменить
неверное обещание `--version` точным описанием существующего `-version` для
`ffmpeg`, `ffprobe` и `fpcalc` и объяснить совместимость с утверждёнными
готовыми бинарниками. Производственный `versionArgument` не менять:
комментарий `backend/internal/integrations/tools/tools.go:78-80` объясняет
отказ `fpcalc` от двойного дефиса, константа определена на строке 82.
Вручную сверить все утверждения в этих двух документах с call sites
`backend/internal/integrations/tools/lifecycle.go:438,545`; `task verify`.
Завершённые планы не переписывать задним числом.
Основание: раздел «Расхождение документа» аудита.

### 7. Проверить пользовательский путь и завершить независимую приёмку

**Зависимости:** 1–6.

На доступном PostgreSQL и подготовленном Setup вручную создать source,
просканировать каталог, сделать его недоступным, повторить scan и убедиться:
`GET /sources/{id}` показывает `unavailable` с безопасной причиной,
`GET /sources/{id}/locations` сохраняет прежние пути; после восстановления
доступа следующий успешный scan возвращает `available`. На диагностической
платформе HTTP-проверка POST/PATCH/DELETE должна давать отказ без изменений.
Для Windows-пути отдельно принять PostgreSQL integration test со строкой
`C:\Music` и Windows amd64 CI unit test на `NormalizePath`; эти два теста
не объявлять полноценной end-to-end проверкой регистрации на Windows.
Запустить **ровно** `task verify` и передать
независимому проверяющему этот план, diff, результат gate и ручной сценарий:
он сопоставляет каждый пункт с кодом и тестами и повторяет `task verify`.
Только после его вердикта COMPLETE переносить план в `done/`.

## Критерии готовности

1. Неизменный inventory сохраняется при потере доступа; root и UI сообщают
   недоступность, а затем восстанавливаются после успешного scan.
2. Обычная ошибка одного файла или отмена не меняет доступность root; старая
   операция не перезаписывает состояние более нового успешного scan.
3. БД принимает абсолютные Windows и Unix строки, относительные пути
   отклоняются на границе; Windows CI отдельно подтверждает нормализацию
   drive path. Полный Windows+PostgreSQL сценарий остаётся deploy-smoke.
4. Диагностическая платформа оставляет чтение, но запрещает изменения roots.
5. Документы описывают реальный аргумент версии; `task verify` и независимая
   приёмка проходят без ослабления существующих проверок.
