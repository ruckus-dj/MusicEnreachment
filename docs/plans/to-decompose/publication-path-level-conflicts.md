# Конфликты уровней пути публикации

Статус: **to-decompose**. Вынесено владельцем из плана 12 2026-10-26.
Это описание проблематики для отдельной проработки, не готовый implementation
plan и не разрешение вводить новые правила группировки или UI.

## Действующее решение

До реализации отдельного согласованного плана разные артисты и разные релизы
могут без ограничений принадлежности сущностям попадать в один каталог.
Это относится и к default, и к пользовательским шаблонам. Вложенные custom
templates не должны отклоняться только из-за отсутствия entity-owned layout.
Каталоги сопоставляются по native filesystem semantics, не по Unicode folding
или идентичности артиста/релиза.

Конфликт полного пути файла разрешается существующим publication flow:
стабильный position suffix, закрепление выбранного имени и удлинение suffix
при новом конфликте. Публикация другой позиции не перезаписывается. Это не
разрешает заменять файл каталогом, каталог файлом или обходить существующие
проверки чужих файлов, внешних изменений и безопасности относительного пути.
Специального per-level conflict UI пока нет.

## Проблематика

Шаблон задаёт структуру пути, но сам по себе не объясняет, является ли
совпадение каталогов намеренным объединением или столкновением сущностей.

- `{ALBUM_NAME}/{TRACK_NAME}.{EXT}` смешивает пространство имён альбомов всех
  артистов. Два разных релиза `Greatest Hits` могут получить один каталог,
  хотя оператор ожидал отдельный каталог каждого релиза.
- Добавление артиста снижает число пересечений, но не исключает одноимённых
  артистов и разных одноимённых релизов одного артиста.
- `{TRACK_NAME}.{EXT}` намеренно не содержит каталога артиста или релиза:
  общая папка здесь ожидаема, а конфликт возникает на уровне полного имени файла.
- Один recording может встречаться в нескольких релизах и позициях. Его ID
  недостаточно для определения владельца публикуемого файла: нужно учитывать
  идентичность позиции релиза.
- Литералы, год, тип альбома и номер диска могут задавать структурные уровни,
  которые не являются самостоятельными artist/release/track entities.
- В одном компоненте могут смешиваться tokens разных уровней; fallback может
  менять фактически использованную ветвь. Подстроки шаблона и совпадение MBID
  или имён не заменяют локальную идентичность сущности.

## Предложенное направление, ещё не утверждённые правила

Рассмотреть конфликты отдельно на уровне артиста, релиза и файла/позиции.
Показывать конфликтующих владельцев в UI и позволять явно задавать
неконфликтное имя для filesystem, **не меняя музыкальные теги**.

При декомпозиции требуется отдельно согласовать:

1. Как определяется смысл компонента, включая mixed tokens, literals и fallback.
2. Как отличить намеренно общий каталог от ошибочного смешивания сущностей.
3. Где хранятся FS-only names, каков их scope и как они закрепляются при retry,
   metadata/template changes и явной реорганизации.
4. Как показываются конфликты, выбор имени и результаты preview/confirmation.
5. Как новый flow сочетается с действующим автоматическим position suffix,
   shared directories и уже опубликованными путями без скрытого перемещения.
6. Как учитывать native case/Unicode equivalence, file/directory collisions
   и конкурентные admissions, не перезаписывая другого владельца.

Временное разрешение общих каталогов не считается ошибкой или незавершённостью
плана 12. Будущий план не должен ретроактивно переименовывать существующие
публикации без отдельного согласованного действия.
