# Аудит соответствия кода техническому и графическому дизайну — 2026-10-07

## Статус и область

Аудит размещён здесь по запросу владельца как материал для декомпозиции
корректирующего этапа. Это не согласованный план реализации, не приёмка и не
источник новых продуктовых решений. Предлагаемые исправления требуют отдельного
плана; документ сам по себе не разрешает их реализацию.

Проверенная ревизия: `f5f1a92b4d13a43c761d676d958731273c59bd03`.
На момент проверки tracked-изменений не было; `test_stand/` был untracked.
Исходный код в ходе аудита не изменялся.

Сопоставлены актуальные требования `docs/design/`, графический прототип
`docs/app-design/` и поставленный scope завершённых этапов 01–07. Приоритет
имеют последние решения владельца в `docs/design/decisions.md`, а не старые
формулировки планов, скриншоты или более строгие технические предположения.

## Вердикт

Продолжать декомпозицию следующих этапов можно, но утверждение «всё в порядке»
не подтверждается. Перепроектирование не требуется; перед расширением
реализации рекомендуется короткий корректирующий этап, прежде всего устранение
P1 в подтверждении переноса инструментов. UX-приёмка текущих Settings этим
аудитом не выдана.

## Найденные проблемы

### 1. P1 — подтверждение переноса использует прежние параметры

**Код:** `frontend/src/features/settings/SettingsScreen.tsx:427,439–442,925–947`.

После preflight путь и флажок удаления прежних управляемых файлов остаются
редактируемыми, но их изменение не сбрасывает `movePlan`. Подтверждение отправляет
token прежнего плана, а не текущие значения формы.

Сценарий: проверить перенос с удалением старых файлов, снять флажок и подтвердить.
Backend всё равно получает план с удалением. Аналогично можно подтвердить перенос
в каталог, отличный от показанного в input. Сервер повторно проверяет прежний
snapshot (`backend/internal/service/move_tools.go:154–167`), поэтому изменение
только UI-полей не обнаруживает.

**Основание:** `docs/design/external-tools.md:22–25` — preflight и scoped
confirmation; `docs/app-design/DESIGN.md:72` — подтверждение количества и путей.

**Предложение:** инвалидировать план при изменении входов, включая изменения во
время запроса; показывать immutable summary проверенного пути и политики удаления.
Добавить RTL-сценарии изменения пути и checkbox после preflight.

### 2. P2 — ошибки модальных операций показываются вне диалога

**Код:** `frontend/src/features/settings/SettingsScreen.tsx:365–366,428–429,452–453,869–872,880–961`.

Ошибки проверки/подтверждения переноса и подтверждения загрузки инструментов
попадают в общий alert вне открытого native modal dialog. При `showModal()`
остальная страница inert: сообщение недоступно обычной клавиатурной навигацией,
а попытка фокусировать внешний alert не восстанавливает работу внутри диалога.

**Основание:** `docs/plans/done/02-setup-manager-and-managed-tools.md:777–790`;
`docs/app-design/DESIGN.md:90` — доступные текстовые ошибки.

**Предложение:** отдельные ошибки, alert и фокус внутри соответствующего диалога;
покрыть отказ preflight, истёкший token и ошибку запуска операции.

### 3. P2 — обновление Settings стирает несохранённые изменения

**Код:** `frontend/src/features/settings/SettingsScreen.tsx:125–143,248,463–466`.

Каждый `refreshState()` безусловно переписывает все редактируемые значения.
Например, изменение output теряется при сохранении LRCLIB или завершении фоновой
операции с инструментами. Поля доступны во время запросов, поэтому могут теряться
и изменения, внесённые после начала сохранения.

**Основание:** `docs/app-design/02-screens.md:169` — заметность несохранённых
изменений; план 02, строки 771–785 — редактирование настроек и server re-read,
который не требует отмены черновиков других секций.

**Предложение:** разделить серверный snapshot и drafts, синхронизировать только
сохранённую секцию либо pristine-поля; добавить dirty-индикацию и тесты сохранности
другой секции при mutation/operation completion.

### 4. P2 — тёмная тема Settings сохраняет светлый фон оболочки

**Код:** `frontend/src/routes/AppShell.tsx:88–90`;
`frontend/src/features/settings/settings.css:15–27`.

Settings переключает основной текст на `#e3eae3`, но окружающий main остаётся
`bg-stone-100`; собственного фона у `.settings-screen` нет. Текст вне панелей
становится светлым на светлом фоне. Вывод основан на CSS, не на браузерном снимке.

**Основание:** `docs/app-design/DESIGN.md:19–24,86–90` — согласованные canvas/ink
tokens и доступность обеих тем.

**Предложение:** применить согласованные tokens к Settings shell, включая
header/navigation; проверить текущий интерфейс в браузере с тёмной темой.

### 5. P2 — нет повторной загрузки после первоначальной ошибки Settings

**Код:** `frontend/src/features/settings/SettingsScreen.tsx:175–179,869–878`.

При ошибке первого `GET /settings` state остаётся undefined. Alert виден, но
кнопка обновления условна по наличию state. Для восстановления требуется reload
страницы или повторный вход на маршрут.

**Основание:** `docs/app-design/02-screens.md:202`; план 02, строки 787–790 —
initial load и accessibility states.

**Предложение:** показывать retry независимо от наличия snapshot; покрыть
последовательность error → retry → successful load.

### 6. P2 — конкурентное изменение output допускает пересечение с tools

**Код:** `backend/internal/service/setup.go:218–238`;
`backend/internal/settings/settings.go:334–344`;
`backend/internal/persistence/settings.go:81–91`;
`backend/internal/persistence/setup_manager.go:490–511`.

Move уже проверил output, но ещё копирует файлы. Settings в это время сохраняет
пустой output, равный новому tools root либо его родителю: проверка учитывает
только старый tools root, а запись output не берёт move lock. Move переключает
root без повторной проверки output. Обе операции могут завершиться успешно,
нарушив инвариант непересечения.

**Основание:** план 02, строки 133–135,215–223 — tools/output не пересекаются,
сервер повторяет проверки перед изменением.

**Предложение:** сериализовать изменение output с move и транзакционно проверять
пересечение относительно текущего/целевого tools root; добавить concurrency
integration test. Сценарий выявлен статически, отдельно не воспроизводился.

### 7. P2 — backend допускает несколько версий и переключение до Complete Setup

**Код:** `backend/internal/api/tools.go:178–194,229–240`;
`backend/internal/persistence/setup_manager.go:222–259,395–398`.

До завершения Setup можно последовательно загрузить две версии одного package.
Start проверяет платформу, но enqueue не ограничивает число версий; успешный
worker заменяет active ID через `ActivateInstallationDuringSetup`. Отдельный
activation route также доступен до Complete.

**Основание:** `docs/design/decisions.md:172–176`; план 02, строки 173–176 —
Setup выбирает ровно одну версию каждого package, переключение нескольких
installations доступно только после Setup.

**Предложение:** под соответствующими locks ограничить вторую выбранную версию
после успешной первой, сохранив retry неуспешной загрузки; explicit activation
ограничить завершённым Setup. Добавить API/integration tests на отказы.

### 8. P3 — README неверно описывает остановку локального запуска

**Код/документация:** `README.md:86–89`, `Taskfile.yml:49–57`.

README предлагает остановку через Ctrl+C, хотя `task run` уже запускает Compose
с `--detach`. Для остановки нужен `task stop`.

**Предложение:** согласовать инструкцию с действующей командой.

## Что не является дефектом текущего среза

- Matching, AcoustID, медиатека, публикация, artwork/lyrics, staged-режим,
  scheduled scan и автоматический retry failed steps относятся к будущему scope.
- Совпадение наблюдаемых size/mtime — утверждённый критерий текущести. Обнаружение
  подмены bytes при неизменных size/mtime не вводится как требование или блокер.
- Старый screenshot Settings не требуется копировать буквально: актуальная
  дизайн-система v2 заменяет прежнюю просторную композицию.
- Глобальный system/light/dark selector остаётся незакрытым дизайн-gap.
  Место хранения персональной UI-настройки отдельно не определено; аудит не
  выбирает его и не превращает gap в новое требование завершённого этапа.

## Проверки и ограничения

`task verify` выполнен на проверенной ревизии и завершился успешно:

- генерация OpenAPI/Orval и проверка generated-кода;
- Go lint и Biome;
- интеграционные Go-тесты;
- Vitest: 15 файлов, 168 тестов;
- Node: 2 теста;
- production build frontend и backend.

Были предупреждения Node о недоступном localStorage и Vite о чанке более
500 kB; gate прошёл. После проверки tracked-изменений не было.

В просмотренных путях scan, автоматического анализа, persistence и recovery
подтверждённых actionable-блокеров не найдено. Основные архитектурные решения
технического фундамента соответствуют дизайну. Это не доказательство отсутствия
дефектов во всём репозитории.

Графическое сравнение выполнено по исходникам, CSS и материалам прототипа.
Браузерного прогона текущего приложения не было, полное визуальное совпадение
и WCAG-соответствие не подтверждены. Реальные managed-tool/crash-сценарии отдельно
не повторялись. Платформенная CI-матрица не запускалась; локальный gate проверен
только на текущей macOS-среде. Успешные существующие тесты не опровергают найденные
статическим ревью сценарии.
