# Локальный провайдер

**Статус: утверждённый дизайн; реализация приложения требует отдельного
поручения.** Дизайн разрешает использовать Local как обычного provider в
существующей модели, без новых таблиц и зеркал.

## Цель и границы

Добавить `Local` как обычного провайдера метаданных: его записи создаёт и
изменяет оператор, а не provider sync. Использовать существующие таблицы
`provider`, `provider_artist`, `provider_release`, `provider_recording`,
`provider_release_track` и provider links. Новых таблиц для локального провайдера
этот черновик не предлагает.

Ручное создание и редактирование provider-записей артистов, релизов и recordings
выполняется на отдельном экране «Собственный каталог». Это CRUD provider-записей, а не замена и не
расширение формы создания collection-релиза. Создание возможно только явным
действием оператора, когда подходящей сущности нет во внешнем каталоге; поиск по
имени не создаёт запись автоматически и не объединяет сущности. Никаких drafts,
непригодных статусов, публикации или удаления исходников этот дизайн не вводит.

## Модель данных и связи

- В `provider` существует обычная строка с кодом `local`; UI показывает
  отдельную вкладку «Собственный каталог».
- Ручные записи Local используют те же поля и граф сущностей, что и другие
  провайдеры. Связи provider-графа могут вести к записям других providers, в том
  числе артист релиза Local — к provider-artist другого provider, а позиция Local
  — к provider-release или provider-recording другого provider. `provider_id`
  каждой записи остаётся её собственной принадлежностью и namespace native key;
  она не наследуется от связанных записей. Поведение обновления/удаления записей
  с межпровайдерными зависимостями остаётся открытым вопросом и этим черновиком
  не определяется.
- Обычные provider links связывают Local-записи с сущностями медиатеки. Для
  одной локальной сущности допускается не более одной связи на provider согласно
  существующей модели; связи с разными providers независимы. Копировать импортную
  сущность в Local только ради такой связи не требуется.
- Существующие сущности любого provider доступны для выбора как ссылки; выбор
  сохраняет provider ownership и native key каждой записи. Возможны артист с
  MusicBrainz, Spotify и Deezer links одновременно; релиз
  может иметь только Local link; разные записи могут быть связаны с разными
  провайдерами независимо. Provider track lists не обязаны совпадать.
- Local-native key не является MBID. Уникальность MBID относится только к
  MusicBrainz; для Local и других providers используются их собственные keys.
  Стабильный `provider_key` сохраняется при переименовании и изменении metadata:
  правка полей не создаёт другую идентичность. Техническое предложение для
  реализации — генерировать UUID-ключ при создании, не вычислять его из имени
  или названия. Это native key Local, а не MusicBrainz MBID.
- Уникальность имени артиста без MBID отложена уточнением владельца от
  2026-10-29: её обеспечивает оператор вручную. Применительно к Local-записям и
  кросс-provider links сейчас не требуются DB-ограничения, автоматическое
  слияние/дедупликация по имени и normalization/resolver. Сравнение без учёта
  регистра и пробелов по краям остаётся будущим ожиданием, а не текущим
  ограничением. Уникальность MBID/provider key и правило не более одной связи на
  provider сохраняются.
- Роли вроде composer/lyricist/vocalist/guitarist остаются метаданными и не
  образуют artist entity или artist links. `ALBUMARTIST` задаёт artist links
  релиза, `ARTIST` — исполнителей recording/позиции.

## Ручное управление и lifecycle

- Оператор вручную создаёт и редактирует записи Local на отдельном экране «Собственный каталог»,
  используя поля соответствующих `provider_*` сущностей. Удаление не входит в
  утверждённые UI-flow. Ручная правка
  сохраняет существующее поведение приоритета ручных изменений и последующих
  provider updates; сама по себе не вводит новую override-модель.
- MusicBrainz sync продолжает обновлять MusicBrainz-записи. Он не создаёт,
  редактирует и не удаляет записи Local.
- Существующие критерии изменения matching для сущностей с Local links такие же,
  как для links с другими providers; отдельный алгоритм или порог для Local не
  предлагается.
- Существующая сущность из любого provider выбирается как ссылка на уже
  существующую сущность медиатеки, а не копируется в Local ради ссылки. Создание
  Local-записи доступно только как явное действие после поиска, если внешнего
  кандидата нет. Одинаковые имена сами по себе не означают идентичность.
- В Local-формах обязательны только бизнес-поля, помеченные `[not null]` в
  соответствующей таблице DBML; nullable поля остаются необязательными. Для
  артиста это `name`, для release — `release_group_title` и `title`, для
  recording — `title`. Неполные данные не получают drafts или unusable statuses.
  Это правило не меняет согласованную форму создания collection-релиза: она
  остаётся отдельным workflow, без публикации при создании.
- Local-релиз поддерживает один носитель. Его упорядоченный трек-лист ссылается
  только на уже существующие самостоятельные композиции (`provider_recording`);
  форма позиции не создаёт recording. Название и длительность берутся из
  композиции, а необязательные `title_override` и `duration_override_ms` задают
  отличия только для данного Local-релиза. Позиции автоматически нумеруются
  последовательно `1..n` после добавления, удаления и перестановки; ручного ввода
  номеров нет. Нулевое число позиций не запрещено этим дизайном.
- В Local-форме релиза присутствуют основной и дополнительные типы релиза и язык;
  поля script нет. Длительность вводится целыми секундами или `М:СС`, отображается
  как `М:СС`, хранится в `duration_ms`.
- Жанры остаются открытым вопросом: утверждённого источника/словаря нет. До
  отдельного решения не добавлять ни picker, ни свободный ввод жанров.
- Эта проработка не разрешает удалять исходные аудиофайлы, автоматически
  перепубликовывать изменённые записи или выбирать новое поведение cleanup для
  опубликованных artifacts.
- Local metadata edits сохраняют действующее поведение изменения metadata; сами
  по себе они не запускают публикацию. Последствия редактирования Local-записи
  для зависимых записей и распространение/версионирование metadata отдельно не
  определены.
- Последствия удаления Local/provider-записи при наличии ссылок из записей
  другого provider не определены и требуют отдельного решения. В частности,
  существующие FK delete policies сами по себе не утверждают продуктовый контракт
  владения или синхронизации чужих записей. Для случаев без таких зависимостей
  поведение остаётся предметом существующих FK DBML; это черновик не меняет их
  delete policies и не задаёт нового поведения удаления.

## Сценарии проверки

1. Создать Local-only альбом с артистом и позициями, не создавая копий
   соответствующих MusicBrainz-записей и не публикуя аудио.
2. Импортировать артиста из MusicBrainz, затем связать его с независимыми
   Spotify/Deezer entities и Local-записью, сохранив отдельные provider keys.
3. Связать Local-релиз с коллекцией, имеющей другие provider links, не сводя
   несовпадающие трек-листы к одному списку.
4. Изменить Local-метаданные, затем обновить MusicBrainz cache: запись Local и
   текущие ручные overrides не должны быть заменены MusicBrainz sync.
5. Отдельно проработать удаление provider-записи, на которую ссылаются записи
   другого provider; проверить существующие FK delete policies, не выводя из них
   неутверждённое поведение ownership/sync.

## Критерии дизайна

- Local использует существующую provider-модель и не требует новых таблиц.
- Импортированные сущности можно связывать с Local и другими provider entities
  независимо, без обязательного дублирования.
- Записи provider-графа могут ссылаться на записи других providers, сохраняя
  собственные provider ownership и native keys; Local и внешние provider keys
  не смешиваются с MusicBrainz MBID.
- Ручные изменения Local, правила matching и текущие ручные overrides сохраняют
  поведение, уже определённое для provider records.
- Нет неутверждённых обязательных полей, удаления source-файлов,
  автоматической публикации или каскадного удаления managed artifacts.

## Открытые вопросы

- Удаление Local-записи с межпровайдерными зависимостями и обновление/удаление
  связанной внешней записи: не определены. Не выводить ownership, синхронизацию
  или каскадное поведение из текущих FK.
- Распространение изменений metadata, latest-only/version propagation: открытое
  предложение, не утверждённое поведение.
- Уникальность имени артиста без MBID отложена отдельным решением: оператор
  обеспечивает её вручную; нормализация, автоматическое объединение и DB
  uniqueness не требуются.
- Источник/словарь жанров для выбора жанра не утверждён; не выбирать его и не
  вводить свободный ввод до решения владельца.
