# Развёртывание и первая настройка

## Source analysis и output

Контракт source inventory, режимов обработки, per-file analysis, retained staged
copies, fingerprint cache и output описан в
[решениях](./decisions.md#текущий-контракт-инвентаря-анализа-и-output).

## PostgreSQL

Развёртывание и integration-тесты используют PostgreSQL 18. Compose использует
официальный образ `postgres:18`: при загрузке образа этот тег выбирает актуальный
minor-релиз ветки 18. Версия бинарников embedded PostgreSQL в тестах фиксируется
зависимостью в `backend/go.mod` и обновляется вместе с ней; она не обновляется
автоматически вслед за плавающим Docker-тегом.

В официальном образе 18 том `postgres-data` монтируется в `/var/lib/postgresql`,
а `PGDATA` по умолчанию находится в `/var/lib/postgresql/18/docker`. Прежний mount
`/var/lib/postgresql/data` относился к образам 17 и ниже.

Смена образа и mount не мигрирует существующий кластер 17. Перед запуском с 18
остановите старое развёртывание, сохраните резервную копию и выполните явный
dump/restore в отдельный кластер 18 либо подготовленный `pg_upgrade`.
Старый том сохраняется до проверки перенесённых данных. Не удаляйте его и не
принимайте новую пустую БД за результат миграции: старые файлы в корне тома не
становятся кластером 18 в новой раскладке автоматически. Само приложение и
его SQL-миграции не выполняют major upgrade PostgreSQL.

## Серверные пути

Значения, выбранные в браузере, всегда относятся к машине, на которой работает
MeloTrove, а не к рабочей станции с браузером. В базовом Compose-развёртывании
хостовый путь вывода `${MELOTROVE_OUTPUT_DIR:-./music}` смонтирован в
`/var/lib/melotrove/output`; в Setup указывается именно этот путь контейнера.

При Initial Setup output должен быть пустым: существующая библиотека публикаций не
импортируется. Это не ограничивает последующие сохранения того же, уже
настроенного и заполненного output root. Настроенные корни tools и output должны
быть абсолютными, доступными для записи и непересекающимися.

## Каталог управляемых инструментов

Постоянный Compose-том `/var/lib/melotrove/tools` намеренно не входит в образ.
Это может быть смешанный каталог с файлами администратора. MeloTrove записывает
в PostgreSQL скачанные и проверенные версии управляемых инструментов, а их файлы
хранит в версионированной раскладке `ffmpeg/<version>/` и `fpcalc/<version>/`.
Неизвестные файлы никогда не обнаруживаются сканированием корня tools и не
удаляются; неизвестный файл в точном пути управляемого исполняемого файла
требует явного подтверждения перезаписи. Записываются и удаляются только точные
пути, записанные в БД для управляемых инструментов.

## Инвентарь источников и analysis

Source roots — серверные каталоги, из которых MeloTrove читает файлы. Их пути
задаются в UI и не передаются через environment. Внутри roots приложение ничего
не создаёт и не изменяет; источники read-only. Для контейнерного deployment
оператор самостоятельно добавляет source mounts в Compose, предпочтительно
read-only (пример ниже). Политика read-only независима от режима обработки:
`in_place` («На месте») или `staged` («Через рабочую копию») явно выбирается для
каждого root без default. Все staged source-analysis AUDIO-копии используют один
общий серверный каталог из runtime-настройки UI/БД, отдельный от output и не
передаваемый через environment. Он не задан по умолчанию и не требуется при Setup
или регистрации root, но должен быть настроен перед staged processing. Настройку
нельзя менять, пока каталог используется операциями или в нём остаются сохранённые
рабочие копии; автоматического переноса нет. Дополнительные правила проверки пути
сверх общего контракта серверных путей пока не определены. Это отдельный рабочий
каталог, не publication staging, scratch/output или staging инструментов.

```yaml
    volumes:
      - tools-data:/var/lib/melotrove/tools
      - ${MELOTROVE_OUTPUT_DIR:-./music}:/var/lib/melotrove/output
      - /srv/music/sources:/srv/music/sources:ro
```

Добавление root инициирует ручной scan. Scan перечисляет/stat-ит файлы и ставит
per-file jobs, но не выполняет copy/probe/hash. Новые и изменённые файлы
обрабатываются этими jobs; неизменённые по наблюдаемым size/mtime не ставятся
повторно автоматически. Ошибочную работу можно повторить вручную. Size и `mtime`
совпадают — достаточный product freshness criterion; побайтовая идентичность и
строгие guarantees против конкурентной подмены не являются продуктовыми
требованиями.

Staged processing создаёт отслеживаемую AUDIO-копию в общей рабочей папке и
сохраняет пригодную копию для retry/restart до завершения всех запрошенных
analysis steps. Удаление таких копий — отдельное явное действие; cleanup error не
отменяет успешный анализ. Fingerprint cache сохраняет один последний успех на
SHA-256; версия `fpcalc` является provenance, не частью cache key. При rerun
прежний успех сохраняется до успешной замены. Analysis не публикует файлы.
Смена output не затрагивает эту независимую рабочую папку: её настройка,
принадлежащие обработке AUDIO-копии, их DB-отслеживание (ownership, соответствие
источнику и пригодность) и незавершённые запрошенные analysis steps сохраняются.
Это не сохраняет jobs: сброшенная обработка не возобновляется автоматически ни
вследствие reset, ни после последующего перезапуска; явный запуск может
переиспользовать пригодную копию.

Успешный scan удаляет locations путей, которые больше не обнаружены; недоступный
root или незавершённый scan не удаляет существующий inventory. Root нельзя
отключить; его можно удалить при отсутствии активной работы после подтверждения
точного текущего server path и количества inventory locations. Удаление root
удаляет его locations; `track_source`-связи остаются, пока variant имеет хотя бы
одну location, и все удаляются при удалении последней location — даже если
SHA-256 analysis сохраняется как reusable cache. Variant без SHA-256 удаляется
после последней location. Удаление выбранной связи очищает выбор, не выбирая
автоматически другой вариант. Удаление root не запускает fallback или
перепубликацию; локальная медиатека, строки текущих публикаций и опубликованные
файлы сохраняются. Существующая automatic policy улучшения качества остаётся,
но равное/худшее качество автоматически не подставляется; ручное понижение
требует предупреждения и подтверждения. Принадлежащие приложению staged-копии,
относящиеся к удаляемым источникам, удаляются. Исходные файлы на хосте никогда не
удаляются и не изменяются. Интерфейс показывает состояние фоновых операций;
детали очереди/ретраев не меняют указанные продуктовые правила.

Контракт matching описан в решениях и плане 11. Output setting и staged
source-analysis artifacts сами по себе не определяют publication
extraction/remux/tagging или atomic replacement.

## Восстановление платформы

При первом запуске с БД фиксируются `GOOS` и `GOARCH` экземпляра. Не переносите
его БД между платформами в расчёте на автоматическую миграцию инструментов.
Несовпадение оставляет доступными диагностику и UI, но readiness сообщает об
ошибке, а Setup и продуктовые операции блокируются. Автоматической миграции
платформы или инструментов нет. Восстановите записанную платформу или
используйте отдельно инициализированную БД.
