# Требования

## Источники, analysis и output

Актуальные решения и датированные свидетельства сохранены в
[`плане 10`](../plans/done/10-staged-source-analysis.md#appendix-a-owner-decisions).
Source inventory, in-place/staged processing, retained staged copies, fingerprint
cache и управление output поставлены в завершённом плане 10; ниже — действующий
контракт, а не список ожидающего refactor.

- Режим `in_place`/`staged` явно выбирается при добавлении каждого root; default
  и отдельного общего work-directory/container overlay нет. Изменение режима
  влияет на будущую обработку. Root нельзя отключить; его можно добавить или
  удалить. Scan запускается вручную; периодическое сканирование и автоматический
  retry не вводятся.
- Scan перечисляет и stat-ит кандидатов, затем ставит per-file processing jobs;
  копирование, probe и hashing выполняются при обработке, не при scan. Неизменённые
  по size/mtime файлы не ставятся повторно автоматически; ошибку можно повторить
  вручную. Product freshness определяется совпадением наблюдаемых size и `mtime`;
  более строгие filesystem/race guards не становятся новыми требованиями.
- Staged mode использует принадлежащую работе AUDIO-копию, отслеживаемую в БД и
  сохраняемую для retry/restart до успеха всех запрошенных шагов. Cleanup failure
  отделён от результата анализа; eligible copies удаляются явным действием.
  Копии, используемые live processing или принадлежащие незавершённой запрошенной
  работе, удалять нельзя. Отсутствующая ссылка очищается, копия при необходимости
  создаётся заново. Квот,
  произвольного лимита размера и in-place fallback нет; ENOSPC требует ручного
  retry после устранения причины.
- На SHA-256 хранится один последний успешный fingerprint. Версия `fpcalc` —
  provenance, не ключ истории; старый успех сохраняется при running/failed rerun
  и заменяется только после нового успеха. Fingerprint не является media identity.
- File-processing concurrency имеет утверждённый default 4 и независима от
  provider RPS; AcoustID RPS=3 не утверждён.
- Output path обязателен и не очищается. Initial Setup требует пустой output;
  последующее сохранение уже выбранного, в том числе заполненного, того же root
  является отдельным сценарием и не меняет правило Initial Setup. Смена output
  сначала валидирует путь и запрещается при running/claimed execution. Queued work
  не блокирует смену: транзакционно сбрасываются все очереди/задачи и все
  DB references на прежний output, но не удаляются старые физические
  файлы. Локальные сущности, source links, inventory и analyses сохраняются;
  автоматической повторной публикации нет. `analysis`, `publication`, `checks`,
  `media` — предложенные логические области, не закреплённые физические имена.
- Реализация файловой публикации остаётся отдельным следующим этапом. Не считать
  publication staging, extraction, remux/tagging или atomic replacement уже
  поставленными.

### Уточнение целевого контракта публикации · 2026-10-31

Решение владельца от 2026-10-31 в `decisions.md` уточняет прежнюю формулировку
от 2026-10-23: текущий результат не сопровождается step journal, backup,
prepared-result record или durable receipt. После обычного исключения файл может
оказаться установленным без записи результата в БД; обычный retry полностью
повторяет подготовку и замену. При восстановлении незавершённой операции сначала
проверяется её известный frozen target: его теги и технические параметры можно
прочитать без транскодирования и полной подготовки, чтобы зарегистрировать только
результат, соответствующий operation inputs и текущей authority. Иначе выполняется
полный retry. Дата файла не доказывает успех.

Периодическая проверка касается только зарегистрированных аудиофайлов позиций:
сравнивает сохранённые при регистрации size и `mtime`, отмечает drift/missing и не
меняет базовую пару по произвольному файлу. Artwork и lyrics встроены в этот файл,
отдельные файлы публикации для них не проверяются. Недоступный output root не
означает missing.
Период проверки, его default, новые UI controls/statuses, power-cut guarantees и
поиск/сопоставление неизвестных файлов не определяются этим контрактом.

Совместимость старых данных не нужна: проект — unpublished prototype. Squash
migrations допустим, но не обязателен.

## Local provider

- Local является обычным provider в существующих `provider_*` таблицах и
  использует существующие provider links; новые таблицы и зеркала не добавляются.
- На отдельном экране «Собственный каталог» для записей provider Local оператор ищет и явно создаёт/редактирует artists,
  releases и recordings. Создание не происходит автоматически по поиску или
  имени; сначала оператор ищет подходящую внешнюю сущность.
- Обязательны только not-null бизнес-поля DBML: artist `name`, release
  `release_group_title` и `title`, recording `title`. Nullable поля необязательны.
- Существующая сущность любого provider может быть выбрана как reference без
  копирования в Local; ссылки сохраняют ownership и native key каждой записи.
- Не вводятся drafts/unusable statuses, удаление в UI, автоматическая публикация
  или удаление исходных файлов. Изменение metadata сохраняет текущее поведение и
  само по себе не запускает публикацию.
- Последствия удаления записей с межпровайдерными зависимостями и распространение
  или versioning metadata не определены. Latest-only/version propagation остаётся
  неутверждённым предложением.
- Local-релиз имеет один носитель и упорядоченный список позиций, каждая из которых
  выбирает существующий provider recording. Название/длительность композиции —
  значения по умолчанию; title/duration overrides необязательны. Порядковый номер
  не вводится вручную и автоматически пересчитывается как `1..n` после изменения
  списка. Пустой список позиций не запрещён.
- Для Local-релиза доступны primary/secondary release type и language, но не
  script. Duration UI принимает целые секунды или `М:СС`, отображает `М:СС` и
  хранит `duration_ms`.
- Жанры: источник/словарь выбора не утверждён; не реализовывать picker или свободный
  ввод, пока владелец не выберет источник.

Детали: [`local-provider.md`](./local-provider.md). Дизайн утверждён; production
реализация требует отдельного поручения.

## Контекст продукта

MeloTrove — серверное web-приложение для персональной или небольшой общей
медиатеки. Основное место развёртывания — NAS или другой постоянно работающий
локальный сервер; приложение работает с доступной серверу файловой системой, а
оператор управляет им через браузер. Web-интерфейс проектируется desktop-first и
не обязан быть mobile-first. По идее продукт близок к SoulSync, но использует
контролируемую организацию и явные ручные действия оператора.

Сервис получает файлы из локальных директорий и подключаемых дисков. Источники
по умолчанию read-only; по отдельной настройке исходный файл можно удалить
после успешной публикации.

Для каждого входящего каталога оператор явно выбирает обработку на месте или
через принадлежащую file-processing работу staged AUDIO-копию в managed output.
Отдельного общего work-directory setting/container overlay нет.

SHA-256 опционален и управляется глобальной настройкой. Переключение не удаляет
сохранённые digest и не пересчитывает неизменённые источники. SHA-256 — критерий
идентичности media: совпадающий digest связывает locations с одним variant, а
при отсутствии digest (`NULL`) locations независимы. Fingerprint переиспользуется
по SHA-256; фактическая версия `fpcalc` хранится как provenance, не как cache key.

После scan новые и изменённые источники автоматически обрабатываются отдельными
per-file jobs с независимыми analysis steps; ошибка одного шага не отменяет
успешные результаты остальных. Наблюдаемое совпадение size/mtime — продуктовый
критерий freshness; не добавляется требование побайтовой идентичности или
доказательства идентичности файлового объекта.

Первичный провайдер метаданных — MusicBrainz, включая self-hosted
развёртывание. Тексты запрашиваются из LRCLIB. Spotify, Apple Music, Discogs,
Deezer и другие провайдеры относятся к будущим отдельным продуктовым задачам.

Целевой продукт предусматривает управляемые публикации с выбранными
аудиоисточниками, метаданными, обложками и текстами. Файловая публикация ещё не
поставлена и остаётся отдельным следующим этапом. Входные источники read-only;
удаление после успешной публикации — отдельная настройка будущей реализации.

Многочасовые и крупные audio sources не исключаются из scan. CUE или ручные
границы могут назначить сегменты одного source нескольким tracks; без явной
разметки приложение не делит большой файл автоматически.

Встроенной аутентификации и авторизации нет: приложение не управляет
пользователями, сессиями, токенами, ролями или разрешениями и считает полностью
доверенным любой клиент, достигший backend. TLS, authentication и ограничение
сетевого доступа обеспечивает deployment — например, reverse proxy с
forward-auth. Bundled UI и API работают с одного origin; CORS не требуется.

Environment ограничен bootstrap-конфигурацией: PostgreSQL connection и
необязательные HTTP bind address/port. Все рабочие настройки, включая log level
и любые credentials внешних API, изменяются через UI и хранятся в PostgreSQL.
Сохранённые secrets не возвращаются через API и не попадают в логи или URL.

Каждая новая продуктовая задача должна пройти отдельную полноценную
проработку до начала реализации.
