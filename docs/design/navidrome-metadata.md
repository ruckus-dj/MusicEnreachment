# Метаданные для Navidrome

## Назначение и статус требований

Решение владельца от 2026-11-03: оператор управляет всеми пользовательскими
музыкальными метаданными, которые использует Navidrome. Этот документ задаёт
целевой контракт, а не описание готовности API/backend. Реализация следует
документации; набор полей существующих endpoint и демонстрационных fixtures не
ограничивает требования.

Покрытие поля означает всю цепочку: хранение в соответствующей сущности,
просмотр и редактирование, явное сохранение/очистка, получение значения из
согласованного источника, отображение будущего результата в preview, запись
публикации и проверка прочитанного результата. Сохранение в произвольный JSON
или read-only вывод тега сами по себе не являются покрытием.

**Последующее уточнение владельца от 2026-11-03:** шесть значений ReplayGain
gain/peak трека и альбома и R128 gain трека и альбома являются измерениями
конкретного аудио, не ручными музыкальными тегами. В макете они объединены в
readonly-блок с существующими значениями или «Не рассчитано»; прежнее требование
ручного редактирования этих шести полей отменено. Отсутствие/ошибка расчёта не
блокирует публикацию и не разрешает перенос значений другого аудио.
`encodedby`/`encodersettings` этим исключением не затрагиваются. Автоматический
расчёт, его стандарт/алгоритм, состав альбомного аудиоконтекста и lifecycle —
отдельная ещё не спроектированная задача; макет не генерирует результаты.

## Проверенная внешняя база

Сверка выполнена 2026-11-03 с Navidrome **v0.64.2**, commit
`101145742f4762164202cb4858c9126258bdc463`. Это воспроизводимая база перечня,
а не решение навсегда ограничить совместимость этой версией.
При сверке с другой версией перечень и интерпретация проверяются заново;
надпись «все поля» без указания upstream-версии и настроенных mappings не
считается доказательством полноты.

  считаются отдельными бизнес-полями; закомментированный `writer` не входит в
  default mapping (его aliases входят в `composer`).
- [Чтение, нормализация и разбиение значений](https://github.com/navidrome/navidrome/blob/101145742f4762164202cb4858c9126258bdc463/model/metadata/metadata.go),

  [модель артиста](https://github.com/navidrome/navidrome/blob/101145742f4762164202cb4858c9126258bdc463/model/artist.go),

- Официальные пояснения:
  [tagging](https://www.navidrome.org/docs/usage/library/tagging/),
  [custom tags](https://www.navidrome.org/docs/usage/configuration/custom-tags/),
  [artwork](https://www.navidrome.org/docs/usage/library/artwork/),
  [persistent IDs](https://www.navidrome.org/docs/usage/configuration/persistent-ids/).
  Страницы сайта могут меняться; для конкретного поведения выше закреплён commit.

Navidrome читает теги из файлов, а собственные artist/album объекты строит по
ним. MeloTrove имеет самостоятельные artist/release/recording сущности, поэтому
место редактирования поля не обязано совпадать с таблицей Navidrome. Значения
при публикации материализуются в каждом соответствующем файле. Метка
`album: true` в upstream mapping означает использование в альбомных Tags
Navidrome, а не правило наследования в MeloTrove.

Перечень ниже покрывает **все 89 default-полей**, включая additional:
использование в smart playlists тоже считается использованием, отсутствие
отдельной колонки в Navidrome не исключает поле. Пользовательские `Tags.*`
Navidrome могут добавлять имена сверх default mapping; их нельзя объявлять
поддержанными одной этой конечной таблицей. Для дополнительного настроенного
поля также нужны известные имя, aliases, тип, множественность и проверенный
output mapping. Какие custom mappings использует целевая установка, должно
быть явно установлено при проверке совместимости, без новых env-переменных.

## Реестр default-полей Navidrome

Имена в первом столбце — ключи upstream mapping, **не обязательно имя тега для
записи**. Например, `recordlabel` читает `LABEL`/`PUBLISHER`,
`musicbrainz_recordingid` читает `MUSICBRAINZ_TRACKID`, а
`musicbrainz_trackid` — `MUSICBRAINZ_RELEASETRACKID`. Конкретное файловое
представление выбирается из aliases upstream и проверяется чтением; запись
всех ключей просто в upper case не является корректным универсальным mapping.

«Контекст» ниже задаёт место осмысленного управления данными, а не новую
цепочку приоритетов. Трек/позиция — одна существующая сущность; отдельный
уровень `position` не создаётся. Sort name редактируется только в карточке
артиста; сортировочные значения упорядоченных credits производны от `sort_name`
связанных артистов. При формировании тегов отсутствующее значение заменяется
`name` того же артиста, не заполняя сохранённое поле. Совпавшие итоговые sort-name
разных артистов приводят к пропуску обоих sort-тегов затронутой группы с
неблокирующим сообщением в preview. Отдельных исключений для альбома или трека
нет. Для спорного распределения остальных значений между
recording и конкретной позицией сохраняются границы решений в `decisions.md`.
Все перечисленные описательные значения должны быть управляемы оператором;
идентичности управляются выбором/сопоставлением, а не произвольным изменением
native key.

## Множественность, aliases и проверка результата

- Upstream читает aliases в указанном порядке и собирает значения из всех
  совпавших aliases. Для scalar-поля берётся первое значение; для списков
  сохраняются значения с удалением пустых и точных дубликатов. Поэтому нельзя
  одновременно публиковать противоречащие значения в разных aliases.
- `ARTISTS` / `ALBUMARTISTS` представляют отдельные значения и не разбиваются
  строковыми разделителями. При их отсутствии одиночные `ARTIST` /
  `ALBUMARTIST` могут разбиваться настроенными разделителями. UI должен
  сохранять список и порядок, а не заставлять оператора вручную угадывать
  разделитель или портить имя вроде `AC/DC`.
- `ARTISTSSORT` / `ALBUMARTISTSSORT` и списки artist MBID позиционно
  сопоставляются с отдельными именами. Sort-значения ordered credits производны
  от `sort_name` связанных артистов с подстановкой их `name` только для тегов
  при отсутствующем значении. Если итоговые sort-name разных артистов группы
  совпадают, оба её sort-тега опускаются с сообщением в preview, без блокировки
  публикации и изменения сохранённых данных (решение от 2026-11-05). Display
  credit, отдельные имена, sort-значения и IDs нельзя независимо сортировать
  или схлопывать.
- Genre/mood splitting (`;`, `/`, `,`) и role splitting (`/`, `;`) — поведение
  Navidrome, не разрешение свободного создания жанров в MeloTrove.
- `DATE`, `RELEASEDATE`, `ORIGINALDATE` имеют разную семантику. Navidrome также
  содержит legacy date corrections; проверка включает частичные даты `YYYY`,
  `YYYY-MM`, `YYYY-MM-DD`, не только один условный год.
- R128 и ReplayGain различны: upstream может преобразовывать R128 Q7.8 gain в
  ReplayGain (+5 dB после деления на 256), если ReplayGain отсутствует. Это факт
  чтения upstream, не выбранный default обработки MeloTrove.
- Lyrics имеют языковую/структурированную форму; artwork — бинарное вложение
  или внешний файл, не текстовый тег. Существующие правила artwork/lyrics
  сохраняются; наличие в Navidrome не разрешает менять утверждённые размеры
  обложек, источники или подтверждение обновления.
- Проверка публикации включает чтение выбранным reader и ожидаемую
  интерпретацию Navidrome, включая additional tags. Если формат/reader не
  представляет поле, это явное ограничение, а не молчаливая потеря значения.
- У закреплённого Navidrome есть собственная нормализация типов и ограничения
  чтения: default string length 1024, comment 4096, lyrics 1048576; некорректные
  числовые/UUID/date значения могут отбрасываться. Это ограничения совместимости
  upstream, не автоматически выбранные ограничения ввода MeloTrove и не
  разрешение молча обрезать сохранённое значение.

## Что нельзя выдавать за редактируемые файловые теги

Полнота музыкальных метаданных не означает подделку свойств файла или
пользовательского состояния другого сервера:

| Класс | Что это означает |
| --- | --- |
| Codec, bitrate, sample rate, bit depth, channels, duration, size | Факты конкретного аудио; показываются, а не изменяются текстовым metadata-полем. Запрошенное преобразование аудио — отдельное действие. |
| Path, mtime, filesystem timestamps | Факты файла и правила размещения, не музыкальные теги. |
| `Order*`, Navidrome PID/ID, counts, sums | Вычисляемые ключи сортировки/идентичности и агрегаты; не то же самое, что явные `Sort*` значения. |
| Rating, starred, play count/date | Персональные annotations Navidrome; default mapping не импортирует их как музыкальные file tags. Их синхронизация — отдельная интеграция, не часть редактора тегов. |
| Biography, внешние artist images, загруженное в Navidrome изображение артиста | Не музыкальные file tags default mapping; их наличие у Navidrome не означает существования такого поля в аудиофайле. |

Embedded artwork и lyrics при этом не исключаются из управляемого музыкального
содержимого: они уже имеют отдельные согласованные workflows. Navidrome сам
не записывает теги в наши файлы; ответственность за требуемую публикацию несёт
MeloTrove.

## Артист как самостоятельный объект

| Поле | Представление и управление |
| --- | --- |
| `name` | Отображаемое имя; существующее обязательное поле. |
| `sort_name` | Необязательное «Имя для сортировки», редактируется отдельно от `name`. |
| `disambiguation` | Необязательное уточнение одноимённых артистов. |
| `genres` | Множественный выбор из общей библиотеки MusicBrainz с поиском; идентичность по MBID, показ канонического имени. |
| `tags` | Отдельные описательные tags; не замена genres и не автоматический источник жанров. |
| Provider links | Собственные идентичности/связи: provider, native key, способ сопоставления; не редактируются как текст имени или сортировки. |

Набор применяется к сведениям артиста медиатеки и соответствующим редактируемым
описательным полям записи провайдера Local; это независимые сущности. Редактирование
одной не является разрешением автоматически переписывать другую.

Свойство `sort_name` принадлежит артисту и редактируется только в карточке
артиста. Сортировочные значения ordered credits выводятся из `sort_name`
связанных артистов с подстановкой их `name` только в тегах при отсутствии
sort-name; сохранённое поле не заполняется. Совпавшие итоговые sort-name разных
артистов группы означают пропуск обоих её sort-тегов с сообщением в preview.
Отдельные контекстные поля сортировки не вводятся. Идентичность артиста и provider links не меняются при
изменении любого имени.

Основные сведения постоянно видимы и выглядят как текст в режиме чтения.
По замечанию владельца о перегруженной компоновке от 2026-11-03 полный реестр
не выводится одной простынёй: дополнительные поля доступны в тематических
группах с раскрытием и в readonly-режиме, без удаления полей или изменения
их смысла. Пустые роли не занимают отдельные строки до явного добавления;
текущие значения и число заполненных сведений отражаются в сводках групп.
«Редактировать» включает ввод в тех же элементах, «Сохранить» возвращает readonly
после успешного сохранения. В открытых группах геометрия полей, формы и основной кнопки не меняется;
место «Отменить» зарезервировано. Отмена/Escape восстанавливают сохранённые
значения; ошибка сохраняет введённый draft. Для genres используется picker, а
не свободная строка. Пустое необязательное поле не блокирует сохранение или
публикацию; отсутствие библиотеки отключает только выбор жанров согласно
[`genres.md`](./genres.md).

## Границы объектов и публикации

- Поля артиста, издания, recording и позиции не сводятся к одной форме артиста.
  `ALBUMARTIST` относится к исполнителям издания, `ARTIST` — к исполнителям
  recording/позиции. Упорядоченность credits и несколько исполнителей сохраняются.
- Composer, lyricist, conductor и другие роли остаются описательными metadata;
  полнота поддержки Navidrome не разрешает создавать из них artist entities или
  новые artist links вопреки [`decisions.md`](./decisions.md).
- Исходный файл и текущая публикация — evidence конкретного трека. У артиста или
  альбома нет единого исходного файла или общего снимка тегов всех его треков.
- Редактирование metadata не переписывает входные источники и само не запускает
  публикацию. Существующие правила preview, подтверждения обновления metadata и
  сохранения metadata при quality upgrade остаются действующими.
- Отображаемые и сортировочные имена — разные сохранённые данные. Решением
  владельца от 2026-11-05 подстановка `name` вместо незаполненного `sort_name`
  разрешена только при формировании тегов. Нельзя терять поля из-за ограничений
  формы, текущего API либо ошибочно считать контекстный список свойством артиста.

## Критерии полноты дизайна и последующей реализации

1. Сверка с закреплённым mapping даёт все **89** default-ключей без пропусков
   additional, ролевых IDs, множественных sort-имён, R128 и технически
   описательных `encodedby`/`encodersettings`. Aliases не раздваивают поля формы.
2. Для каждого пользовательского поля определены область объекта, форма
   редактирования/выбора, сохраняемое значение и файловое представление.
   Нерешённая область/политика помечается как пробел, а не объявляется готовой
   на основании generic JSON. Ограничения конкретного writer/reader показываются
   явно и не отменяют требования.
3. Имя артиста и имя сортировки сохраняются независимо; изменение одного не
   подменяет второе. Сортировочные значения ordered credits производны от
   `sort_name` связанных артистов с подстановкой их `name` только для тегов
   при отсутствующем значении; сохранённый `sort_name` не заполняется.
   При совпадении итоговых sort-name разных артистов группы оба её sort-тега
   опускаются с явным сообщением в preview, а имеющиеся в CURRENT значения
   показываются как подлежащие очистке. Несколько credits, имён, sort-значений и
   MBID сохраняют позиционное соответствие; ограничения reader проверяются явно.
4. Сведения артиста содержат уточнение, настоящий множественный genre-picker
   и отдельные tags. Отсутствие каталога жанров не блокирует сохранение пустых
   genres или публикацию; произвольный genre-текст не предлагается как обход.
5. Проверены read/edit/save/cancel/Escape, сохранение введённых значений при
   ошибке и отсутствие изменения геометрии формы/действий в обоих режимах,
   в светлой/тёмной теме и узком окне. Провайдерные native keys не становятся
   обычными редактируемыми текстовыми полями.
6. Проверены точность дат, ordered multi-values, work/movement, роли с
   инструментами, различие generic tags/genres, названий и номеров, музыкальной
   тональности/темпа и свойств аудио. Формы не теряют менее заметные поля.
7. Preview и readback различают текущие сохранённые сведения объекта и текущую
   публикацию конкретного трека. Сохранение формы не меняет sources,
   provider ownership или уже опубликованные файлы и не запускает публикацию.
8. Для согласованных форматов публикации проверены реальные aliases, значения
   и множественность при чтении Navidrome; additional-поля проверены также как
   доступные metadata для smart playlists, не только как колонки его объектов.

Полный контракт не считается реализованным, пока остаются неопределённые
правила, влияющие на результат. Статус реализации и доказательства проверок
фиксируются отдельно от этого целевого документа.

## Отдельные решения, ещё требующие владельца

Обязательная поддержка полей не разрешает молча выбрать новые значения или
политики разрешения:

1. Точное расположение дополнительных контекстных полей и разрешение их
   значений между recording, изданием и позицией, если оно не задано ранее.
   Для genres/tags/explicit/ISRC сохраняются существующие открытые вопросы;
   реестр совместимости не утверждает универсального наследования.
2. Custom `Tags.*` конкретной установки Navidrome: какие дополнительные поля
   включены, их типы/aliases и проверяемое представление. Default-реестр
   конечен, произвольные расширения требуют отдельной явной сверки.

Эти вопросы не отменяют уже утверждённые наличие и редактирование поля. До
согласования нельзя выдавать конкретную цепочку наследования genres/tags/explicit/ISRC
за решение владельца.
