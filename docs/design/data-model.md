# Целевая модель данных

## Source analysis и output

Актуальный продуктовый и runtime-контракт source analysis, staged-copy retention,
fingerprint cache и output реализован в завершённом плане 10; см.
[`решения`](./decisions.md#текущий-контракт-инвентаря-анализа-и-output) и
датированные [решения владельца плана 10](../plans/done/10-staged-source-analysis.md#appendix-a-owner-decisions).
В частности, явный per-root mode, per-file processing, retained staged AUDIO
copies и один последний fingerprint success на SHA уже поставлены. Source
freshness на уровне продукта означает совпадение наблюдаемых size и `mtime`;
более строгие implementation guards не добавляют требований.

Этот документ и DBML описывают логические сущности/связи, а не являются
побайтовым зеркалом runtime-схемы. Не выводить из концептуального DBML наличие
runtime-таблицы/worker или статус реализации соответствующего процесса. Файловая
публикация остаётся отдельным следующим этапом и не считается поставленной.

## Логические области

| Область | Назначение |
| --- | --- |
| Кэш провайдеров | Долговременные данные внешних источников: артисты, релизы, recordings, позиции треков и обложки. |
| Инвентарь источников | Корни сканирования, пути файлов и технические варианты аудио. |
| Локальная медиатека | Актуальные артист, релиз, recording и трек с независимой от провайдера жизнью. |
| Сопоставление | Кандидаты и подтверждённые связи между локальными и provider-сущностями. |
| Публикации | Текущий каталог релиза и единственный зарегистрированный аудиофайл каждой опубликованной позиции; незавершённая работа отражается общей operation/retry-моделью. |

## Основные сущности и связи

### Локальная медиатека

- `collection_artist` представляет артиста.
- `collection_release` представляет альбом/релиз и имеет упорядоченный набор
  артистов через `collection_release_artist`.
- `collection_recording` представляет композицию (recording) и имеет
  упорядоченный набор артистов через `collection_recording_artist`.
- `collection_track` связывает конкретную позицию трека в релизе с recording;
  хранит номер носителя, позицию, отображаемый номер, возможные overrides и
  текущее состояние публикации.
- Локальные сущности существуют и без provider-связей, поэтому поддерживают
  полностью ручную публикацию.

Идентичность артиста уточнена владельцем 2026-10-29: MusicBrainz MBID
однозначно связан с локальным артистом через provider key и provider link.
Позднейшим уточнением того же дня уникальность имени отложена: сейчас её
обеспечивает оператор вручную; автоматическое объединение по имени и новые
ограничения схемы для имени не требуются. Отдельные credits ссылаются
на переиспользуемого артиста и сохраняют собственные порядок и отображаемое имя.
Уточнение владельца от 2026-10-29: `ALBUMARTIST` определяет артистов релиза,
а `ARTIST` — исполнителей recording/позиции. Иные роли (например, композитор,
автор текста, вокалист или гитарист) остаются значениями метаданных; они не
создают артистов или дополнительные связи с релизом/recording. Ролевой текст и
credit не являются ключами идентичности. Разные MBID не объединяются из-за
одинакового имени. Уникальность provider identity и ограничение одной связи
с каждым provider сохраняются при конкурентных транзакциях и прямом SQL-доступе;
это не требование уникальности имени.

## Локальный провайдер

Утверждённый дизайн [`локального провайдера`](./local-provider.md) использует
существующие `provider_*` сущности и provider links для записей, создаваемых и
изменяемых вручную. Он не вводит проекционные или иные новые таблицы и не меняет
физическую схему. Provider-граф может содержать межпровайдерные ссылки, при этом
каждая запись сохраняет собственные provider ownership и namespace native key.
Удаление записей с зависимостями и распространение/versioning metadata остаются
открытыми вопросами.

### Источники аудио

- `source_root` описывает логически настроенный входящий каталог, его server
  path, режим обработки (`in_place` или `staged`), поколение последнего успешного
  scan и текущую доступность. Он не представляет managed-медиатеку в output.
  Удаление root удаляет его locations и связанные source variants в инвентаре,
  но никогда не удаляет физические файлы хоста. При этом media analysis с
  SHA-256 сохраняется как общий reusable cache; variant без SHA-256 удаляется,
  когда на него больше не остаётся ссылок и удерживающих операций. Принадлежащие
  приложению staged-копии, относящиеся к удаляемым источникам, удаляются, но
  локальная медиатека, строки публикаций и текущие опубликованные файлы
  сохраняются.
- `source_location` существует только для фактически найденного пути внутри
  root и хранит точный relative path, size, mtime и поколение наблюдения. После
  полностью успешного scan не найденные повторно locations удаляются; ошибка
  или недоступность root не изменяет существующий inventory. Удаление root
  удаляет все его locations.
- `media_variant` содержит технические и извлечённые данные файла: параметры
  контейнера и аудио, нормализованные теги, данные `ffprobe`, fingerprint
  Chromaprint, качество, версии анализа, актуальные технические проблемы и
  опциональный SHA-256 точных source bytes.
- Одинаковый SHA-256 означает одну идентичность media: locations из разных roots
  с одинаковым digest ссылаются на один `media_variant`. Идентичность определяется
  только SHA-256; fingerprint не является идентификатором. Если digest отсутствует
  (`NULL`), locations независимы. Variant с digest сохраняется как кэш анализа и
  matching даже без locations; orphan variant без digest удаляется после
  завершения удерживающих его операций. Переключение настройки не изменяет уже
  существующие variants.
- `track_source` связывает вариант с треком медиатеки, фиксируя метод и
  способ принятия решения, совместимость, выбранный источник и необязательные
  границы CUE/manual-сегмента. Связь
  `media_variant` ↔ `collection_track` является M:N: один файл может быть
  источником нескольких позиций треков в разных или одном релизе. Для каждой
  позиции трека предполагается один выбранный источник.

### Провайдеры и сопоставление

- `provider` описывает источник метаданных и его доступность.
- `provider_artist`, `provider_release`, `provider_recording` и
  `provider_release_track` образуют независимый кэш данных конкретного
  провайдера, включая артистов и позиции треков.
- У Local-релиза один носитель. Его позиции упорядочены, каждая ссылается на уже
  существующий `provider_recording`; `track_position` и отображаемый номер
  автоматически равны порядку позиции 1..n. `title_override` и
  `duration_override_ms` необязательны и переопределяют одноимённые значения
  композиции только для этого релиза. Local UI вводит длительность секундами или
  `М:СС`, показывает `М:СС`, а хранит миллисекунды. Это ограничение Local
  workflow, не общего provider-графа.
- Форма Local-релиза включает `release_group_primary_type`,
  `release_group_secondary_types` и `language`; поля `script` в ней нет.
  Источник/словарь жанров не утверждён, поэтому UI-пикер и свободный ввод жанров
  не определены.
- Связи `collection_*_provider_link` сохраняют сопоставление локальной сущности
  с эквивалентом провайдера и способ решения (`automatic`/`manual`). Manual link
  защищён от автоматического перевыбора; automatic может быть пересчитан новой
  matching policy.
- `match_candidate` хранит текущие кандидаты сопоставления audio-варианта с
  provider-позицией, нормализованный confidence `[0,1]`, evidence и версию
  matching policy. При повторном matching набор кандидатов заменяется;
  подтверждённые links не дублируют confidence.
- Связи внутри provider-графа могут соединять записи разных providers; например,
  provider-позиция может ссылаться на release одного provider и recording другого,
  а artist credits могут ссылаться на artist другого provider. `provider_id`
  каждой записи сохраняет её собственную принадлежность и namespace native key;
  связь не меняет и не наследует эти значения. Обновление/удаление записей с
  межпровайдерными зависимостями отдельно не определено (см. уточнение в
  `decisions.md`). Локальные сущности по-прежнему могут иметь неполные связи с
  несколькими providers. Различающийся состав provider track lists не изменяет
  local track list.

Обычный provider `Local` и ручное управление его кэш-записями описаны в
[`local-provider.md`](./local-provider.md) как утверждённый дизайн. Это не
добавляет новой таблицы или схемного инварианта; реализация приложения требует
отдельного поручения.

### Обложки и тексты

- `artwork_asset` кэширует бинарные изображения и их происхождение.
- `release_artwork_candidate` делает изображения кандидатами для локального
  релиза; `collection_release` выбирает один из них.
- `lyrics_document` хранит plain или синхронизированный текст от провайдера.
- `recording_lyrics` допускает несколько текстов и языков на один recording;
  `collection_track` выбирает текст для публикации.

### Управляемая публикация

- `release_publication` хранит единственную опубликованную директорию релиза,
  её обложку и версию. Эта директория не является исключительной: разные релизы
  могут использовать одну папку, если полные пути их файлов не конфликтуют.
  Уникальность текущей публикации задаётся ID релиза, а не путём папки;
  существующие правила разрешения конфликтов имён файлов сохраняются.
- `track_publication` хранит единственный опубликованный трек, путь, формат,
  codec, снимок качества выбранного источника и версию публикации.
- Зарегистрированный аудиофайл позиции (`track_publication`) хранит size и
  `mtime` как исходную пару для проверки внешнего изменения. Периодическая
  проверка сравнивает именно эту пару: несовпадение отмечает drift, отсутствие —
  missing; недоступность output root не считается missing. Artwork и lyrics
  встроены в аудиофайл; отдельные файлы публикации для них не проверяются.
  Совпадение size и `mtime` достаточно, hash для этой проверки не обязателен.
  Базовая пара не переписывается по произвольному содержимому.
- `release_publication` и `track_publication` представляют только текущие
  зарегистрированные результаты. Step journals, резервные копии, prepared-result
  records, durable receipts и отдельные publication-attempt сущности в текущую
  модель не входят. Незавершённая работа остаётся в существующей operation/retry
  модели; детали восстановления описаны в датированном уточнении 2026-10-31 в
  `decisions.md`.

## Зафиксированные инварианты модели

1. Медиатека хранит актуальное состояние, а не журнал изменений.
2. Локальные артист, релиз, recording и трек самостоятельны и могут не иметь
   связей с провайдерами.
3. Технический вариант файла отличается от позиции трека. Один `media_variant`
   может использоваться несколькими позициями треков, например для одного
   recording в разных релизах или повторной позиции внутри релиза.
4. У позиции трека только один активный выбранный источник и одна активная
   управляемая публикация.
5. Автоматическая публикация не понижает и не повторяет качество уже
   опубликованного трека.
6. Провайдерные ответы являются долговременным кэшем; кандидаты matching и
   незавершённые operations принадлежат текущему состоянию, но отдельная история
   или publication-attempt сущность не хранится.
7. Source inventory не хранит отсутствующие пути: location удаляется только по
   результату полностью успешного scan доступного root.
8. Идентичность source не зависит от `device`/`inode`. SHA-256 определяет media
   identity; без digest locations остаются независимыми.
9. Один variant может быть выбран для tracks, относящихся к нескольким локальным
   recordings и provider Recording ID; metadata публикации остаются свойством
   конкретного release track.
10. Большой source может представлять несколько CUE/manual-сегментов и не
    исключается по длительности или размеру. Sample rate хранится в Hz без enum.
11. Confidence принадлежит кандидату, а `automatic`/`manual` — подтверждённому
    решению. Ручное решение не изменяет confidence и блокирует автоматический
    перевыбор.
12. Quality scores разных policy versions напрямую не сравниваются.
13. Выбранная artwork candidate принадлежит своему release; удаление выбранного
    candidate требует сначала снять выбор.
14. Изменение publication state координируется с файловой операцией; каскад БД
    сам по себе не считается удалением managed artifact. Зарегистрированная
    publication row описывает только текущий результат, а не шаги или историю
    его файловой операции.
15. Удаление source root удаляет только root и его inventory/source associations,
    включая связи `track_source`; оно не удаляет исходные файлы хоста, локальные
    entities, publication rows или текущие опубликованные файлы. SHA-256 analysis
    остаётся кэшем без locations; variant без digest удаляется после освобождения
    последней ссылки и удерживающих операций. Staged-копии, принадлежащие
    приложению и связанные с удалёнными источниками, удаляются.

Для deferred scan tool holds `tools_read_required` является изменяемым отражением
наличия `operation_tool_read_hold`: admission scan может иметь `false` при tools,
записанных в snapshot; захват/освобождение hold и изменение флага завершаются в
одной транзакции. Guard проверяет их итоговое совпадение и отсутствие hold у
terminal operation, но не требует создавать scan hold для каждого snapshot tool и
не приравнивает snapshot-флаг к изменяемому полю операции.
