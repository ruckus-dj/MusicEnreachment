# Продуктовый контракт

Этот документ — единый актуальный контракт продукта и утверждённых технических
ограничений. Он описывает текущее целевое поведение, а не историю согласований,
план работ или состояние реализации. Исторические отчёты и планы остаются
свидетельствами своего времени и не переопределяют этот контракт. Детальные
контракты предметных областей указаны ссылками ниже.

## Продукт и границы доверия

- MeloTrove — серверное web-приложение для персональной или небольшой общей
  медиатеки. Оно работает с файловой системой сервера (в том числе NAS и
  подключаемыми дисками), управляется через браузер и ориентировано на desktop.
- Удаление исходного файла после успешной публикации — отдельная runtime-настройка,
  по умолчанию выключенная. Доступ к источникам и mount mode остаются вне
  service contract; обязательные read-only mounts не требуются.
- Встроенной аутентификации и авторизации нет. Любой клиент, достигший backend,
  имеет полный доступ; TLS, аутентификация и сетевые ограничения относятся к
  deployment boundary. Backend не доверяет identity headers. UI и API используют
  один origin; CORS не добавляется.
- Управляемые публикации — отдельные от исходников копии. Для позиции конкретного
  издания существует не более одной текущей публикации; несколько источников не
  создают дубликаты.
- Приложение хранит только актуальное состояние, не историю действий и результатов.
  Устаревшие попытки/результаты обновляются или удаляются; после успешного recovery
  не сохраняется неуспешный оригинал ради аудита. Evidence незавершённого исполнения
  удерживается лишь пока необходимо для текущего действия или безопасного recovery.

## Настройка, среда и инструменты

- Единственная конфигурация до доступа к БД — обязательный `DATABASE_URL` и
  необязательные `HTTP_BIND_ADDRESS` (по умолчанию `0.0.0.0`) и `HTTP_PORT`
  (по умолчанию `8080`). Остальные рабочие настройки задаются в UI и хранятся в
  PostgreSQL; конфигурационные файлы и дополнительные environment overrides не
  вводятся.
- Уровень логирования — `debug/info/warn/error`, default `info`, применяется без
  перезапуска. До загрузки настроек из БД startup использует `info`; startup
  errors выводятся независимо от сохранённого уровня.
- Bootstrap выполняется через Setup, после успешного завершения которого Setup
  не является обычным экраном. Его завершённость отделена от последующего
  состояния здоровья настроек. Настройки Setup далее редактируются в Settings.
- Output обязателен; начальная настройка требует пустой каталог. Позднее можно
  сохранить уже выбранный, в том числе заполненный, тот же root. Технические и
  медиафайлы используют общий физический output root.
- Общая рабочая папка staged AUDIO-копий — независимая runtime-настройка UI/БД,
  без default и без env. Она не требуется для Setup или регистрации root, но
  обязательна до staged processing. Папка не пересекается с source roots,
  tools или output: запрещено совпадение и вложенность в обе стороны. Проверка
  выполняется при изменении любой из этих сторон и при добавлении/изменении root.
  Требований пустоты или размещения на одном volume нет. Папку нельзя менять,
  пока существуют использующие её операции или сохранённые копии; автоматического
  переноса нет.
- `ffmpeg`, `ffprobe` и `fpcalc` управляются как загружаемые и проверяемые
  executable-файлы из утверждённых источников, а не как системные установки.
  Версия проверяется аргументом `-version`; checksum сверяется, если источник её
  публикует. В Setup успешная установка активирует выбранную версию; позднее
  добавление версии и её активация — отдельные явные действия. Подробности:
  [`external-tools.md`](./external-tools.md).
- Настройки секретов доступны через типизированный UI. Сохранённое значение не
  возвращается API и не попадает в URL, логи или копируемую диагностику. Доступ к
  БД и её backups относится к deployment security boundary.
- Настройка использования LRCLIB — переключатель, включённый по умолчанию.
  Выключение запрещает новые запросы, не удаляя сохранённые lyrics и не меняя
  CURRENT-публикации. Base URL, credentials, таймауты и RPS в UI не добавляются.

## Источники, инвентарь и анализ

- Для каждого source root оператор явно выбирает `in_place` или `staged`; default
  нет. Root нельзя отключить, можно добавить или удалить. Scan запускается
  вручную; расписание и
  автоматический retry не вводятся. Scan обнаруживает файлы и планирует per-file
  processing; copy, probe и hashing выполняются обработкой, не обходом каталога.
- Изменения inventory фиксируются только после успешного полного обхода root.
  Успешный scan доступного root удаляет location, которая больше не найдена;
  недоступность root или незавершённый scan не удаляют inventory. Удаление root
  удаляет его locations, но не файлы хоста, медиатеку или текущие публикации.
- Свежесть источника определяется совпадением наблюдаемых размера и `mtime`.
  `device`/`inode` не являются идентичностью. Неизменённые по этим значениям
  источники повторно автоматически не обрабатываются; ошибку можно повторить
  вручную. Более строгие filesystem/race guarantees не являются продуктовыми
  условиями.
- При обнаруженном изменении размера или `mtime` location сразу теряет связь
  с прежним variant — как с SHA-256, так и без него. До нового анализа это новый
  непроверенный файл: он не наследует прежние связи и результаты и не допускается
  к публикации как прежний источник. Совпадение пути не сохраняет идентичность.
  Повторная связь с SHA-256 возможна только по вновь вычисленному digest.
- SHA-256 — единственный критерий идентичности media, если глобальная настройка
  включена. Переключение не запускает backfill/rehash/merge/split. Hash считается
  для новых и изменённых источников; staged-режим использует подготовленную
  копию. Одинаковый digest объединяет locations в variant; без digest locations
  независимы. Fingerprint не является identity.
- На SHA-256 хранится один последний успешный fingerprint. Версия fpcalc —
  provenance, не cache key; успешное значение сохраняется при running/failed
  повторном расчёте и заменяется только новым успехом. Fingerprint пригоден для
  matching только после подтверждения ровно одного audio stream. Нет массового
  backfill или таймерных retries. Variant с SHA-256 сохраняется как переиспользуемый
  cache даже без locations; variant без SHA-256 удаляется после последней
  location.
- Если успешный полный scan удалил последнюю location variant для действительно
  исчезнувшего файла, все его `track_source`-связи удаляются, выбор очищается
  без fallback и republish; CURRENT сохраняется.
- SHA-256 включён по умолчанию и при включённой настройке считается для всех новых
  и изменённых файлов, включая `no_audio`. Переключение настройки не запускает
  backfill неизменённых файлов и не удаляет сохранённые hashes/results. Полный
  `ffprobe` за один запуск получает наличие audio и все доступные технические
  данные; повторный probe для технических данных того же файла не требуется.
  Успешный актуальный результат переиспользуется. `probe_error` перепроверяется
  при scan; переход `probe_error → audio` запускает первую автоматическую
  поэтапную обработку, даже если size/mtime прежние. `fpcalc` запускается без
  duration-аргумента и использует стандартные первые 120 секунд.
- Обработка файла состоит из независимых шагов `ffprobe`, SHA-256 (если включён)
  и Chromaprint. Успехи шагов сохраняются независимо. File-processing concurrency
  имеет default 4 и независима от provider RPS; AcoustID RPS=3 не устанавливается.
- Размеры и длительности не имеют произвольных верхних продуктовых лимитов;
  запрещаются отрицательные или структурно бессмысленные значения. Большие и
  многочасовые sources сканируются. CUE или явные ручные границы могут назначить
  сегменты одного source нескольким позициям; автоматического деления без такой
  разметки нет. Sample rate хранится как целые Hz, без enum-ограничения.
- Staged AUDIO-копия принадлежит работе, отслеживается в БД и сохраняется до
  успеха всех запрошенных шагов; пригодная копия используется при явном retry.
  Отсутствующая ссылка очищается, копия при необходимости создаётся заново.
  Ошибка cleanup не меняет результат анализа. Используемые и удерживаемые
  незавершённой работой копии защищены от очистки; eligible-копии удаляются только
  явным действием. Нет квот, произвольного лимита размера или in-place fallback.
- Смена output запрещена при running/claimed execution. Queued work не блокирует
  её: очереди и ссылки БД на прежний output сбрасываются транзакционно, физические
  файлы не удаляются, автоматической перепубликации нет. Локальная медиатека,
  source links, inventory и analyses сохраняются. Staged-копии и их учёт
  независимы от output reset; reset не сохраняет jobs и не возобновляет обработку
  автоматически. Явный новый запуск может переиспользовать подходящую копию.
- Подробная модель источников и данных — [`data-model.md`](./data-model.md) и
  [`music_ingest_redesign.dbml`](./music_ingest_redesign.dbml).

## Провайдеры, сопоставление и медиатека

- Основной metadata provider — MusicBrainz (public или self-hosted); lyrics —
  LRCLIB. Другие провайдеры требуют отдельной проработки. MusicBrainz identity
  определяется MBID, не именем. Разные MBID остаются разными артистами; без MBID
  совпадение имени само по себе не является командой объединить записи.
- Provider graph допускает связи между разными providers. `provider_id` задаёт
  принадлежность самой записи и пространство её native key. У локальной сущности
  может быть не более одной ссылки на каждый provider; связи могут быть
  независимыми и неполными. Provider records и library entities — независимы.
- В медиатеке записи появляются только через provider-mediated workflow:
  provider record (включая Local) связывается с локальной сущностью через incoming
  matching. CRUD каталога Local сам по себе не создаёт library entities.
  Самостоятельное прямое создание collection entities из UI/API не является
  workflow медиатеки. Каждая сущность медиатеки связана хотя бы с одним
  провайдером. Для данных, которых нет у сторонних провайдеров, используется Local;
  отсутствие внешнего MBID не означает отсутствие provider-связи.
- Local — обычный provider в существующей модели. Оператор явно создаёт и
  редактирует его artists/releases/recordings; сначала выполняет поиск.
  Обязательны только бизнес-поля, обязательные в provider-модели. Удаление
  provider-записей не входит в этот UI. Существующие записи любого provider можно
  связывать без копирования в Local.
- Local-релиз содержит один носитель и упорядоченные позиции, каждая ссылается на
  существующий provider recording. Отдельной сущности `position` нет. Позиция
  может переопределить title и duration; иначе используются значения recording.
  Номер позиции вычисляется из порядка. Duration в интерфейсе вводится целыми
  секундами или `М:СС`, отображается `М:СС` и хранится в миллисекундах (`int64`);
  произвольный двухчасовой предел не вводится. Поля script и жанров доступны по
  соответствующим контрактам; пустой список позиций допустим.
- Artist credits и связи исполнителей сохраняют порядок, отображаемые имена,
  join phrases и роли. `ALBUMARTIST` относится к релизу, `ARTIST` — к recording/
  позиции; значения ролей сами по себе не создают дополнительных artist links.
- MusicBrainz release groups группируются по identity, не по совпадению названия.
  Конкретные издания с записью в медиатеке отображаются раздельно, каждое со своим
  track-list и metadata, в том числе при недоступном аудио. Если в release group
  нет ни одного релиза в медиатеке, показывается одна отсутствующая запись группы.
  Для неё оператор явно выбирает edition; до выбора нет track-list и число
  отсутствующих позиций неизвестно (`—`). Автоматического canonical/default
  выбора, объединения editions или копирования metadata нет.
- Incoming matching использует утверждённую policy и сохраняет ручные решения.
  Полностью пригодное решение может применяться автоматически; неполное требует
  review всей раскладки, совпавшая часть отдельно не применяется. Manual link
  защищён от автоматического перевыбора до явного изменения/возврата в automatic.
   Ручное назначение источника добавляет связь и не снимает существующие; выбор
   аудио для публикации отдельный.
- Matching confidence — одно нормализованное значение `[0,1]`; accepted link
  хранит метод решения (`automatic`/`manual`), а не confidence. Текущая текстовая
  policy — `matching-rapidfuzz-v1`, официальный RapidFuzz C++ `token_set_ratio`
  через C ABI/cgo с Unicode code-point input; нормализация, транслитерация,
  coverage penalty и остальные factors/weights сохраняются. Score не является
  самостоятельным persisted полем. Решение
  использует утверждённую совокупную границу 0.70 и ручной review при её
  недостижении, без обязательного порога для каждого отдельного поля. Automatic
  link хранит версию policy принятия решения. Неподдерживаемые старые plans и
  decisions не применяются под новой policy; retrieval ranking не заменяет
  итоговые release selection и assignment profiles.
- Evaluation хранит только актуальное состояние, не историю. Сохранение последней
  evaluation до замены допускается, но необязательно. Invalidated parked automatic
  wait после смены source configuration, captures или manual authority не
  публикует устаревший review и не применяет links. Automatic mode планирует
  переоценку на свежих данных; manual mode требует явного возврата в automatic,
  без постановки старой apply/restore задачи. Внутреннее evidence транзакции не
  является пользовательской историей и не определяет отдельной ledger policy.
- Ручной provider picker позволяет менять query, вводить MBID/URL и выбирать
  artist/release. Размер страницы по умолчанию 10, пользователь может его менять;
  это не меняет automatic shortlist. Явное снятие сохранённой ручной связи не
  удаляет файлы или provider metadata и не запускает rematching: группа остаётся
  manual до явного возврата в automatic. Queued automatic apply не восстанавливает
  снятую связь.
- Для входящей группы с artist evidence поиск использует полные `ALBUMARTIST`
  values, при их отсутствии — полные `ARTIST` values. Рассматривается только
  top-1 найденный artist; его fit к полным значениям должен быть не ниже 0.70,
  файлы без artist evidence исключаются, отсутствие сравнимого evidence ведёт к
  ручному review. Для подходящего artist загружается полный постраничный каталог
  releases, затем локально выбираются top-10 releases на группу файлов, не на
  каждый файл. Если top-1 artist не подходит, требуется ручной поиск/проверка.
- Без artist evidence retrieval выполняется последовательно: `album + track →
  album → track`; следующий этап запускается, если предыдущий не дал применимых
  candidates. Серверный поиск ограничен top-10 результатами на логический запрос;
  локальное ранжирование использует только полученные данные. OR-запрос может
  содержать сохранённые значения и их нормализованные/транслитерированные формы;
  `/` и `;` разделителями не являются.
- Release shortlist ранжируется средним доступных текстовых сходств полного album
  artist с полными release artist credits и album с лучшим из release title либо
  title + disambiguation; отсутствующий фактор исключается. Ранг суммируется по
  файлам группы. Tie-breaker — число точных полных строк DATE/CATALOGNUMBER; любое
  отсутствующее поле не является mismatch, DATE не сокращается до года. Последняя
  ничья разрешается MBID только для воспроизводимого shortlist, не для выбора
  automatic winner. Если после всех artistless этапов ни один candidate не
  достигает совокупного confidence 0.70, review показывает полный release и track
  inventory только последнего исполненного этапа; если этап пуст — исходную
  captured file group без provider layout. Ниже порога ничего автоматически не
  назначается и частичное применение запрещено.
- Фильтр медиатеки «В наличии / Не хватает / Все» различает audio presence и
  publication. Для позиции наличие аудио — доступный source ИЛИ существующий
  published audio; для артиста/альбома частичный объект присутствует в обеих
  выборках. «Все» включает отображаемые provider-only записи и выбрано изначально.
  Availability, source count и publication state имеют отдельные
  подписи. Полнота publication показывается текстом и N/M, независимо от
  availability; неизвестный total не означает ноль или полноту.
- Общий список артистов медиатеки включает только артистов релизов. Участие только
  в credits отдельных песен не добавляет артиста в этот список; сами credits
  сохраняются. Это правило не определяет отдельную карточку или удаление гостевого
  артиста.
- Сводки артиста считают альбомы и позиции раздельно для аудио, исходников и
  публикаций. Для каждого показателя альбом учитывается при хотя бы одной
  отвечающей позиции; полный — только при известном полном track-list и
  соответствии всех позиций, частичный — при наличии отвечающих и не отвечающих
  позиций. Если полнота track-list неизвестна и позиции не доказывают частичность,
  состояние `unknown`; пустой `0/0` не full. Число треков означает позиции релизов,
  не файловые варианты и не уникальные recordings между релизами. Счётчик
  исходников необязателен; не требуется выводить каждую метрику на каждом экране.
  Provider-числа обозначают только известный partial cache scope, не полную
  дискографию. Итоговое число альбомов артиста складывается из конкретных записей
  релизов в медиатеке и известных MusicBrainz release groups, для которых в
  медиатеке нет ни одного релиза. Каждая запись релиза учитывается отдельно,
  в том числе несколько из одной release group и записи без доступного аудио;
  отсутствующая в медиатеке release group учитывается один раз. Runtime-доступность
  аудио не меняет эту группировку и единицы подсчёта.
- Публикация управляется в контексте артиста, альбома и track position, а не на
  отдельном экране. Выбор одного или нескольких объектов раскрывает имеющиеся
  позиции и формирует один точный агрегированный preview. Отсутствующие файлы
  пропускаются с причиной; отсутствующие library entities не создаются.
  Provider cache не означает полную дискографию.
- Подробности Local и жанров: [`local-provider.md`](./local-provider.md),
  [`genres.md`](./genres.md). Полный реестр редактируемых музыкальных полей:
  [`navidrome-metadata.md`](./navidrome-metadata.md).

## Метаданные и управление

- Локальная медиатека сохраняет достижимость по цепочке artist → release →
  track/позиция → recording: каждый release связан хотя бы с одним artist,
  каждый recording — хотя бы с одним release через его позицию. Недостижимые
  recordings и релизы без артистов в медиатеке недопустимы. Это инвариант
  библиотечного графа, а не ограничение независимого provider-каталога.
- Требования к полям определяются продуктовым контрактом, а не полнотой текущей
  реализации или fixtures. Все поддерживаемые пользовательские музыкальные поля
  Navidrome представлены в подходящей области модели, редактируемы и сохраняемы,
  а при публикации записываются и проверяются в соответствующих тегах. Read-only
  сравнение не заменяет редактирование.
- Отображаемое имя и необязательное уточнение `disambiguation` локального артиста
  редактируются в его карточке независимо от значений провайдера. Identity и
  provider links не меняются; сохранение само по себе ничего не перепубликует.
- У артиста есть отдельное необязательное `sort_name`, редактируемое только в
  карточке артиста. При публикации отсутствующее значение заменяется отображаемым
  именем только в проекции итоговых sort-тегов; сохранённые данные не меняются.
  Порядок значений соответствует artist credits. Если одинаковые итоговые sort
  значения разных артистов приводят к удалению элементов в целевом приложении,
  затронутая sort-tag группа целиком опускается, preview объясняет причину, а
  существующие соответствующие теги очищаются. Другие группы не затрагиваются.
   Имена разных артистов в projected file tag names при коллизии уточняются как
  `Name (disambiguation)` без изменения сохранённого имени; если коллизия остаётся,
  затронутая artist MBID group опускается с предупреждением. При неполном списке
  artist MBID вся затронутая группа опускается с preview notice, сохраняя release
  и recording MBID.
- Карточки артиста и издания показывают сведения постоянно. Редактирование
  включает поля на месте, не меняя геометрию; отмена/Escape восстанавливают
  сохранённые значения, ошибка не уничтожает draft. Source и publication сведения
  относятся к конкретной позиции, а не агрегированному объекту. Редактирование
  само по себе не меняет источники или CURRENT publication.
- Для названия и длительности позиции применяется только `track override →
  recording`; release в этом приоритете не участвует. Это не универсальное
  наследование прочих metadata. Наследование tags/explicit/ISRC и смысл пустых
  значений для них не расширяются этим правилом.
- Для файловых credits исполнителей применяется явный override позиции → credits
  recording. При отсутствии override используются credits recording; явный пустой
  override очищает credits и останавливает fallback. Override позиции включает
  ручное значение и явно заданные провайдером credits release-track, в том числе
  пустой список. Ручное значение имеет приоритет над provider credit позиции;
  скопированный из recording fallback отдельным override не становится.
  Это правило не изменяет release credits или source/provider links и не задаёт
  наследование прочих полей.
- Файловый `GENRE` выбирается от частного к общему: genres recording, при их
  отсутствии — genres release, затем — объединение genres артистов recording.
  Жанры разных scopes не складываются; сохранённые genres сущностей не меняются.
  Явный пустой genre override очищает `GENRE` и останавливает fallback.
  При нескольких артистах recording жанры объединяются без повторов по MBID;
  сохраняется порядок первого появления по порядку credits и жанров артиста.
- Явное ручное назначение пустой строки допустимо для любого тега, включая
  названия и имена артистов; допустим и пустой список артистов. Это сохранённый
  tag override, не отсутствие переопределения и не удаление source/provider links.
  Отсутствие override сохраняет текущее/исходное provider value. Разрешение пустого
  тега не отменяет обязательные бизнес-поля при создании provider-сущности.
- Эффективные metadata сравниваются с baseline CURRENT точно: регистр, пробелы,
  Unicode-представление и порядок списков значимы; нормализация поиска не
  применяется. Карточки, индикатор и preview используют один критерий. Сравнение
  охватывает фактические теги, встроенную обложку и lyrics, учитывая merge,
  protected fields и `absent`, но не provider cache или технические версии.
  Baseline меняется только после успешной новой CURRENT publication, включая
  допустимую recovery-регистрацию; история baseline не хранится.
- Невалидные metadata в preview — `unprocessable` с причиной; отсутствующий файл
  или явно исключённая позиция — `skipped` с причиной. Preview сообщает точные
  отличия и предупреждения до подтверждения. Эти правила не определяют атомарность
  всего пакетного запроса или политику повторов.
- Автоматический расчёт параметров громкости не является обязательной частью
  публикации. Шесть измерений ReplayGain/R128 — readonly-поля конкретного аудио;
  отсутствие показывается как «Не рассчитано», не как ноль. `encodedby` и
  `encodersettings` этим исключением не затронуты.
- В MP3 и M4A не записываются инструментальные `performer` credits: текущий
  TagLib writer не сохраняет их имена и структуру исполнителя/инструмента без
  потерь. Полные структурированные значения остаются в медиатеке; preview явно
  сообщает о пропуске, который сам по себе не блокирует публикацию. Основные
  `ARTIST`/`ALBUMARTIST` и остальные поддерживаемые contributor roles этим
  исключением не затрагиваются. Запятые в именах не запрещаются; это исключение
  не распространяется на другие форматы.
- Provider updates и изменения локальных metadata сами не переписывают файлы.
  Обновление уже опубликованных metadata требует явного выбора, preview и
  подтверждения. Ручные overrides и `absent` защищены; явные workflows обложек и
  lyrics остаются. Политика не ослабляет matching ambiguity, identity/authority
  guards или запрет автоматического downgrade.
- Для связанного MusicBrainz release доступна явная команда получить свежие
  upstream-данные, а не только перечитать сохранённый cache. Ручные значения,
  включая явное удаление значения (`absent`), сохраняют приоритет; свежие
  provider-данные сами не изменяют publication.

## Публикация и восстановление

- Начальная публикация, повторная и принудительная публикация проходят одним
  workflow и одной точной UI preview до подтверждения. Preview учитывает текущие
  настройки формата и path template, эффективные metadata, cover и lyrics,
  действующие защиты и точные отличия от CURRENT. Обычный preview `unchanged` не
  пишет результат. Принудительное повторное намерение всегда выполняет полную
  подготовку из выбранного source, даже если target уже подходит; оно не становится
  `unchanged`. Измерения другого аудио не переносятся. Retry ошибки и явное
  принудительное повторное намерение различаются.
- Для сравнения аудио смена исходного расположения внутри того же variant не
  является заменой аудио. Совпадающий SHA-256 исходных файлов означает одно и то
  же аудио. Другой variant с отличающимся SHA-256 считается заменой аудио: совпадение
  формата, технических параметров, тегов, cover, lyrics и пути не доказывает
  равенство аудио.
- Автоматическое улучшение качества допускается только для AUDIO и сохраняет
  CURRENT tags, artwork и lyrics. Автоматическая замена равного или худшего
  качества запрещена. Ручное понижение требует предупреждения и подтверждения.
  Ручная публикация использует выбранный source любого качества: низкое качество
  или неизвестный/несравнимый ранг сами по себе её не блокируют. Порогов качества
  и нижней границы измеренного среднего битрейта относительно настройки кодировщика
  нет; проверки технической совместимости формата и потока сохраняются.
  Удаление source не выбирает альтернативу и не запускает fallback/republish.
- Publication operation использует актуальное зарегистрированное состояние, без
  истории попыток, step journal, backup/rollback copies, prepared-result records
  или durable receipts. Durable River args содержат только operation ID; worker
  перечитывает входы из snapshot. Целый временный результат готовится приватно
  рядом с destination на той же файловой системе, проверяется и атомарно
  заменяется native operation. Delete-then-copy fallback запрещён. SQL transaction
  не удерживается вокруг ffmpeg. Полная гарантия сохранности при потере питания
  не обещается.
- Изменения одной позиции/target сериализуются; stale manual selection и текущая
  authority проверяются до записи. Publication result и current/reset/delete
  используют общий coordinator; проигравшая работа не перезаписывает target
  другого владельца. Redelivery завершённой операции не выполняет filesystem
  callbacks. Cancel и исчерпание retries дают видимую ошибку и ручной retry; cleanup
  не начинается до подтверждённого результата. Для процессов достаточно дождаться
  основного процесса и собственных callbacks, без требования доказать остановку
  всего дерева потомков.
- Если filesystem replacement произошёл, а DB commit результата не завершился,
  обычный retry полностью повторяет подготовку и замену. Для незавершённой
  операции сначала проверяется известный frozen target: соответствие фактических
  тегов и технических параметров frozen inputs при актуальной authority достаточно
  для recovery. Дата файла, побайтовая идентичность и доказательство source
  provenance не требуются. Неподходящий/отсутствующий target приводит к полному
  retry, в том числе с заменой изменённого извне неподходящего файла по тому же
  пути при актуальной authority; нельзя выдумывать недоступный provenance lyrics.
- Изменение пути внутри output регистрирует новый результат в БД и ставит cleanup
  прежнего принадлежащего приложению файла атомарно с результатом; фактическое
  удаление выполняется после commit и может завершиться предупреждением. Сброс
  или смена output root не удаляет старые файлы.
- Проверка зарегистрированных publications сравнивает сохранённые size и `mtime`;
  отличие — drift, отсутствие файла — missing. Недоступность output root не
  считается missing и не меняет baseline. Проверяются зарегистрированные
  аудиофайлы; artwork и lyrics встроены в них. Неизвестные файлы автоматически не
  ищутся и не сопоставляются.
- Несколько релизов могут занимать один каталог при отсутствии конфликта полного
  пути. Конфликт имени разрешается стабильным position suffix с закреплением
  имени и удлинением при повторном конфликте; перезапись файла другой позиции
  запрещена. Короткие MBID tokens — первые восемь hex-символов UUID; полные MBID
  остаются в тегах. Путь действующей публикации автоматически не переименовывается.
- Проверка writable output эмпирически определяет эквивалентность имён временными
  probe-файлами в технической области общего физического root. Planner использует
  результат при проверке коллизий; platform-specific scope checks не являются
  prerequisite для probe.

## Обложки и тексты

- Source tags, lyrics, technical metadata и оригинальные artwork bytes извлекаются
  при analysis и сохраняются в БД; publication читает их из БД. Из выбранного
  source берётся только audio stream. Не выполняется поздний поиск source tags,
  artwork, lyrics или длительности.
- Cover precedence: provider artwork, затем сохранённая source artwork. Среди
  source-кандидатов выбирается наибольшее разрешение фактически сохранённого
  изображения; равенство разрешается минимальным ID. Manual authority сохраняется.
- Новая входная artwork принимается, если каждая сторона не больше 10000 px;
  превышение — необязательная ошибка и не должно молча менять выбранную обложку
  или блокировать audio publication. Generic CURRENT inspection и сохранение
  legacy artwork не ограничиваются новым input limit. Оригинальные bytes в БД не
  перекодируются; publication получает derivative, вписанный в 2048×2048 без
  увеличения и без обязательного lossy encoding. Жёсткий предел RSS не обещается.
- Изменение pending cover применяется ко всем уже опубликованным позициям релиза;
  простое сохранение pending не применяет её. Работа с artwork не выполняет
  позднего поиска в исходниках.
- Повторный поиск lyrics не требует исходника: используются metadata и длительность
  текущей публикации. Применение текста работает с CURRENT audio; ручной текст и
  явное отсутствие защищены. При recovery сохраняется фактический прочитанный
  текст, но недоступная история его получения остаётся неизвестной.
- Подробный реестр тегов и upstream-покрытия —
  [`navidrome-metadata.md`](./navidrome-metadata.md).

## Удаление и очистка

- Source-root deletion — операция над inventory MeloTrove, не над файловой
  системой. Хостовые источники никогда не удаляются и не меняются; удаляются root,
  его locations и принадлежащие приложению staged-копии. Текущие публикации,
  library entities и файлы публикаций сохраняются. SHA-256 variants остаются
  cache; variants без digest удаляются после последней location. `track_source`
  остаётся, пока у variant есть location; при удалении последней location все
  такие связи удаляются, а выбранная связь очищается без автоматической замены.
  Удаление root требует подтверждения точного текущего server path и количества
  inventory entries, отклоняется при queued/running задачах root, включая claimed
  execution, и не запускает fallback/republish. Неуспешная задача сама по себе не
  блокирует удаление: вместе с root удаляются зависимые от него failed-задачи и
  все их временные файлы, включая удерживаемые staged-копии. Возможность retry
  таких задач убирается; удержание копии для повтора не переживает удаление root.
  Для зависимой failed publication удаление root само выполняет безопасный отказ
  от восстановления и убирает retry, а не требует отдельного предварительного
  разрешения recovery. Этот отказ не удаляет CURRENT, library или файлы публикаций;
  recovery authority нельзя просто отбросить по признаку `failed` вне этого
  явного workflow удаления root.
- Source cleanup после успешной publication — opt-in и по умолчанию выключен.
  Перед началом читается актуальная настройка; queued/running consumers и retained
  holds защищены. Если одному исходному файлу назначено несколько сегментов,
  удаление разрешено только после успешной публикации всех назначенных сегментов,
  включая ещё не поставленные в очередь; публикации одного сегмента недостаточно.
  Непосредственно перед удалением сверяются size и `mtime`; при
  несовпадении файл не удаляется. Принимается остаточная гонка внешнего изменения
  между проверкой и удалением; hash, quarantine и атомарный compare-and-unlink не
  требуются. Повтор после неопределённого результата — только явное действие
  оператора после полной сверки; само отсутствие файла при автоматическом retry
  не доказывает успешную очистку.
- Публикация и managed output удаляются только через service operation: безопасное
  удаление принадлежащего приложению файла предшествует транзакционному удалению
  строк. Чужие/общие файлы не удаляются; FK cascade не используется как файловый
  механизм. Удаление library object не удаляет provider records, а provider
  deletion не удаляет library или publication. Если файл уже удалён, а удаление
  строк БД не завершилось, явный retry при свободном пути завершает удаление строк.
  Если по прежнему пути появился другой файл, retry не удаляет его, не завершает
  удаление соответствующей записи и показывает конфликт. Это правило managed
  deletion не заменяет отдельные ограничения retry очистки исходников.
  Root/parent, обычный файл, identity и hash проверяются непосредственно перед
  удалением. Принимается остаточное окно внешней подмены между проверкой и unlink;
  атомарный compare-and-unlink не обещается.
- Library deletion scope: publication удаляет только свой managed file и запись;
  release удаляет свои positions и publications, затем release и recordings,
  потерявшие последнюю связь с релизом; artist — включённые в scope releases,
  ставшие недостижимыми recordings, затем artist. При удалении artist релиз
  входит в scope только если удаляемый артист — его основной исполнитель.
  Такой релиз удаляется вместе с positions и publications, даже если у него есть
  другие исполнители; подтверждение явно перечисляет эти релизы и предупреждает
  об остальных исполнителях. Если удаляемый артист не основной, релиз, его
  позиции, публикации и credits сохраняются, но больше не показываются в каталоге
  удалённого артиста. Recording, используемый сохраняемым чужим релизом, также
  сохраняется, в том числе когда он встречается и в удаляемом релизе. Гостевое
  участие не включает чужую песню, её позиции или публикации в scope. Пока
  остаются такие ссылки, сохраняется техническая запись артиста; само по себе
  это не возвращает его в общий список. Повторное добавление артиста через обычный
  provider → matching снова показывает сохранённые связи; отдельной команды
  восстановления нет. Удаление последней позиции recording удаляет его из
  медиатеки; при наличии позиции в другом релизе recording сохраняется.
  Это не удаляет provider-записи или исходные аудиофайлы.
  До запуска UI показывает точный scope; операция асинхронная.
- Перед удалением library object подтверждение перечисляет точный фактический
  scope и зависимости. Удаление публикаций и library rows выполняется сервисной
  операцией: принадлежащие приложению файлы безопасно удаляются прежде строк БД.
  Неупорядоченное удаление domain rows запрещено; соответствующие foreign keys
  используют `RESTRICT`, а не cascade как замену workflow.
- При удалении релиза или артиста успешная часть фиксируется отдельно: записи
  успешно удалённых публикаций удаляются сразу. Ошибка или конфликт следующего
  файла не отменяет эту часть; релиз/артист остаётся до завершения остальных
  зависимостей.
- В разделе cleanup интерфейса показывается предупреждение о настройке удаления
  исходников; отдельный дополнительный диалог подтверждения не добавляется.
  Удаление подключённого source root доступно рядом с ним и сохраняет установленные
  защиты и подтверждение.

## Интерфейс

- Русский и английский — полные языки интерфейса, включая ошибки, состояния и
  доступные имена. Изначально выбирается первый поддерживаемый предпочитаемый
  язык браузера, иначе английский. Пользовательский выбор сохраняется локально;
  доступен режим «Как в системе». Переключение не сбрасывает формы/операции.
  Музыкальные данные, пути и идентификаторы не переводятся.
- Тема `system/light/dark` — персональная browser setting в `localStorage`,
  default `system`; если хранилище недоступно, выбор действует до закрытия
  страницы. Системная тема реагирует на изменение системного предпочтения.
- Desktop-приоритет: при ширине от 1400 px интерфейс сочетает компактное
  представление с удобством и читаемостью, не оставляя неоправданно много пустого
  пространства. Ниже этой ширины плотность выбирается свободнее. Mobile-first
  требование не вводится.
- Ошибка обязательного поля показывается inline, связана с полем доступной
  связью, фокусируется первое ошибочное поле; draft сохраняется. Заголовок,
  получивший фокус от маршрутизации, не получает видимого outline, при этом
  доступная фокусировка сохраняется.
- Runtime-настройки используют смешанное сохранение: списки, переключатели,
  checkbox и radio сохраняют валидный выбор автоматически, а ручной текстовый
  и числовой ввод — только явной кнопкой «Сохранить» рядом с полем или связанной
  группой полей. Пауза ввода и потеря фокуса не сохраняют текст. Общая фиктивная
  кнопка сохранения уже применённых переключателей не показывается. Проверки и
  подтверждения изменения output/tools и других действий с последствиями
  сохраняются; autosave не позволяет применить невалидную конфигурацию.
- Несохранённый текст настроек, в том числе невалидный, хранится только в
  браузере в пределах текущей вкладки: переживает переходы и перезагрузку;
  обычное закрытие вкладки завершает эту сессию. Черновик не записывается в БД
  и не становится действующей настройкой до успешного явного сохранения.
  Секреты в browser storage не записываются. При недоступном хранилище ввод
  удерживается в памяти страницы с предупреждением об ограничении восстановления.
  Срок жизни — обычная сессия
  вкладки, а не долговременный черновик: приложение не обещает восстановление
  после её закрытия или гарантированное стирание данных средствами браузера.
  Собственная функция браузера «Восстановить закрытую вкладку/сессию» может
  восстановить и session storage; такой черновик всё равно не применяется без
  проверки актуального сохранённого значения и явного сохранения.
- При уходе с несохранённым текстом настроек UI предупреждает и позволяет остаться,
  уйти с сохранением браузерного черновика либо явно отбросить его; валидный ввод
  также можно сохранить. Невалидный ввод не препятствует уходу с черновиком и не
  выдаётся за сохранённую настройку. При закрытии/перезагрузке страницы используется
  доступное браузеру предупреждение о возможной потере несохранённых данных.
- Изменение настройки с другого устройства не затирается старым черновиком.
  UI использует актуальное сохранённое значение и выявляет конфликт с исходным
  значением черновика; при конфликте доступны «Взять сохранённое» и «Продолжить
  редактирование». Замена актуального значения исправленным черновиком требует
  явного подтверждения. Наличие конфликта не лишает оператора возможности
  исправить и сохранить свой ввод.
- В сопоставлении на desktop от 1400 px inspector выбранной позиции постоянно
  доступен в нижней части рабочей области; список позиций прокручивается отдельно.
  Для просмотра evidence не требуется прокручивать весь длинный релиз. Inspector
  не меняет геометрию строк и не закрывает последние позиции или действия.
- Папки выбираются на сервере, не загружаются с браузера. Пикер позволяет
  навигацию вверх/по breadcrumbs, ввод пути и переход по Enter; отмена не меняет
  выбранный путь. Проверка папки сопровождает выбор, MusicBrainz проверяется при
  сохранении/переходе Setup. Scan сам запускает обработку найденных файлов.
- Интерфейс использует обычные пользовательские действия, а не демонстрационные
  кнопки управления fixtures или внутренним состоянием. Единственный графический
  референс — самостоятельный [`docs/app-design-react/`](../app-design-react/);
  он задаёт визуальную форму, не отдельные продуктовые решения и не исполняется в
  production frontend.
- После Setup, если source roots нет, стартовый экран сообщает, что нужно добавить
  source, и предлагает действие добавления. При наличии хотя бы одного root
  приложение открывает «Входящие» напрямую, без промежуточной стартовой страницы.

## Архитектура и качество

- Утверждённый стек: Go 1.27; React 19/TypeScript, Vite, Node.js 24 LTS и npm;
  PostgreSQL 18; Bun ORM; PostgreSQL-backed River; Huma + chi; Task для команд
  monorepo. Репозиторий — GitHub monorepo. Object storage не предполагается.
- Backend разделён по техническим слоям: `api → service → persistence`, только
  persistence работает с Bun/PostgreSQL; интеграции, settings, jobs, migrations
  и static assets — отдельные технические слои. HTTP API и River worker работают
  в одном процессе и разделяют `*sql.DB`; DB transaction может атомарно сохранять
  состояние и River job. Миграции запускаются до workers и HTTP.
- Huma/OpenAPI — источник API-контракта; frontend client/hooks генерируются
  Orval, generated code вручную не меняется. Vite assets встраиваются в Go binary.
- REST — внутренний контракт bundled UI, не обещание публичной интеграционной
  совместимости. Обычный запрос к локальной БД при нормальной нагрузке отвечает
  менее чем за секунду; долгие операции быстро возвращают operation ID.
  Это latency-цель, не глобальный timeout.
- HTTP использует `ReadHeaderTimeout=5s`, `IdleTimeout=60s` и graceful shutdown
  до 10 секунд. Глобальные `ReadTimeout/WriteTimeout` не задаются; body limits и
  deadlines принадлежат operations, долгоживущий SSE не обрывается ими.
  `cmd/server` преобразует OS signals в parent context; HTTP, SSE и River
  завершаются общим lifecycle, `app.Run` не владеет signal handling.
- Каждый запрос получает `X-Request-ID`; JSON logs содержат request ID, method,
  path, status, duration и response bytes. Panic recovery пишет stack в server
  log и возвращает безопасный JSON 500 без внутренних деталей.
- `/health/live` проверяет HTTP process, `/health/ready` после startup проверяет
  PostgreSQL с deadline в одну секунду. Внешние providers не влияют на readiness;
  Docker image использует readiness healthcheck. Hashed `/assets/` кешируются
  как immutable на год, `index.html` и SPA routes используют `no-cache`.
- Пути и runtime-настройки хранятся в PostgreSQL. Настройки secrets не
  возвращаются открытым текстом. Серверные операции выполняются асинхронно и
  возвращают operation ID; SSE служит только сигналом перечитать snapshot.
- Целевые платформы: Linux и macOS amd64/arm64, Windows amd64; Windows arm64 не
  поддерживается. Backend artwork builds требуют libvips не ниже 8.14 с
  `pkg-config`. Технические параметры и принятые native ограничения относятся к
  реализации, не создают иных пользовательских гарантий.
- `quality_score` всегда сопровождается `quality_policy_version`; значения,
  рассчитанные разными policy versions, напрямую не сравниваются. При сравнении
  оба варианта оцениваются заново по текущей policy из сохранённых metadata или
  snapshot. Формула качества остаётся открытым вопросом.
- Качество проверяется через Taskfile (`build`, `test`, `lint`, `format`,
  `generate`, `verify`); CI выполняет полный verify и поддерживаемую платформенную
  матрицу. Локальный полный gate — `task verify`; его компоненты и правила запуска
  описаны в корневом `AGENTS.md`.
- Целевой бюджет локального тестирования — не более 60 секунд без времени
  компиляции и загрузок; setup fixtures и БД входит в этот бюджет. Тесты, которым
  не требуется поведение PostgreSQL, выполняются без БД; настоящая БД остаётся
  для SQL-контрактов, транзакций, ограничений и гонок. Полный frontend JSDOM suite
  выполняется один раз в Linux verify job, не повторяется в native platform matrix;
  матрица сохраняет TypeScript-проверку, production builds и native/Go tests.
- Продуктовые проработки определяют цель, сценарии, ограничения, затронутые
  модели/операции/components и критерии готовности до реализации. Неутверждённые
  решения не выводятся из строгой реализации, исторического отчёта или макета.

## Открытые вопросы

Следующие вопросы остаются открытыми; этот перечень не выбирает варианты и не
разрешает реализацию по предположению:

- Распространение и наследование tags, `explicit`, ISRC за пределами
  утверждённого `track override → recording` для title/duration. Разрешение
  явного пустого tag override уже определено в разделе метаданных.
- Поведение удаления/обновления provider-записи, на которую ссылаются записи
  другого provider; versioning/propagation provider metadata.
- Полнота MusicBrainz provider cache и фоновые обновления/синхронизация.
- Алгоритм/hash, хранение и расписание индикатора metadata diff; неизвестные и
  ошибочные состояния. Отдельное уведомление о новых provider values защищённых
  полей остаётся необязательной идеей.
- Алгоритм и lifecycle автоматического расчёта громкости; аудиоконтекст для
  альбомных измерений.
- Поведение частичной перепубликации при смене output directory отложено до
  появления потребности; единая папка всех CURRENT-позиций релиза после такой
  смены сейчас не является критерием приёмки. Автоматическая перепубликация
  при output reset не выполняется. Source-free audio preparation требует
  отдельной проработки.
- Интервалы/default периодической проверки зарегистрированных publications и
  новые пользовательские состояния для неё.
- Формула `quality_score`; она требует отдельной проработки.
