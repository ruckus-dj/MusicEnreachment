# Зафиксированные решения

## Статус документа

Этот документ содержит только решения, явно подтверждённые владельцем
проекта. Незаполненные разделы и открытые вопросы не являются решениями и не
должны превращаться в реализацию без отдельного согласования.

## Продукт и доступ

- Продукт: web-приложение для организации персональной медиатеки.
- Runtime: серверное приложение, предназначенное прежде всего для NAS или
  другого постоянно работающего локального сервера. Пути источников и публикаций
  относятся к файловой системе сервера, а не компьютера с браузером.
- Интерфейс: управление через браузер, desktop-first; mobile-first подход и
  отдельный desktop executable не требуются.
- Доступ: персональный или для небольшой группы пользователей.
- Авторизация: на текущем этапе отсутствует в самом приложении. Её
  ответственность лежит на внешнем `auth-proxy`.

## Интеграции

- MusicBrainz должен поддерживать как публичный сервис, так и self-hosted

## Отложенные решения

- Object storage пока не предполагается.

## Миграции и типы API

- Используется `bun/migrate` с versioned SQL-миграциями.
- SQL-миграции обязательно встраиваются в Go-бинарник через `go:embed`.
- Коллекция миграций загружается из `embed.FS` через `Migrations.Discover`;
  распаковка SQL на диск не требуется.
- Транзакционные миграции используют пары файлов `.tx.up.sql` и `.tx.down.sql`.
- `Migrator` с `WithMarkAppliedOnSuccess(true)` применяет миграции при старте
  приложения, до запуска River workers и HTTP server.
- Текущий deployment предполагает один процесс, выполняющий миграции. Перед
  запуском нескольких реплик требуется отдельная сериализация миграций; такой
  deployment не входит в область проекта.
- Huma OpenAPI является источником истины API; TypeScript-типы для frontend
  генерируются из этой спецификации с самого начала проекта. Task запускает
  экспорт и Orval через npm.
- Orval генерирует TypeScript-клиент, React Query hooks и mock-сценарии из
  OpenAPI.

## Структура кода

- Monorepo содержит отдельные верхнеуровневые директории `backend/` и
  `frontend/`.
- В `backend/` используется стандартный Go layout с `cmd/` и `internal/`.
- Go-пакеты организованы по техническим слоям, а не по предметным областям.
- Сгенерированные из OpenAPI TypeScript-типы находятся внутри frontend.

## Конфигурация и первичная настройка

- Рабочие настройки приложения задаются только через UI и хранятся в базе
  данных; конфигурационных файлов и переменных окружения для них нет.
- Единственное допустимое исключение из переменных окружения — параметры
  подключения к PostgreSQL.
- При первом запуске пользователь проходит Setup Manager, который сохраняет
  минимально необходимые настройки.

## Внешние инструменты

- Поставка `ffmpeg`, `ffprobe` и `fpcalc` внутри Docker-образа необязательна.
  Если они включены, это неизменяемый fallback: обновления не заменяют бинарники
  образа, а более новая скачанная и успешно проверенная версия имеет приоритет.
- UI должен позволять вручную проверить актуальность этих инструментов и
  обновить их; также требуется периодическая проверка обновлений.
- Версия установленного инструмента определяется через `--version`.
- Обновления получают только как готовые бинарники из утверждённых доверенных
  источников.
- Готовый `fpcalc` загружается из AcoustID Chromaprint GitHub Releases.
- Утверждённые источники готовых бинарников:
  - `fpcalc`: https://github.com/acoustid/chromaprint/releases;
  - `ffmpeg` и `ffprobe` для Windows/Linux: https://github.com/BtbN/FFmpeg-Builds/releases;
  - `ffmpeg` и `ffprobe` для macOS: https://ffmpeg.martin-riedl.de/ — только
    релизные билды, snapshots запрещены.
- Setup Manager при первом запуске требует persistent tools-directory, который
  позднее можно изменить через UI.
- После выбора каталога приложение автоматически получает и проверяет готовые
  бинарники инструментов; установка обновлений после этого выполняется из UI.

## Процессы и развёртывание

- HTTP API и River workers на текущем этапе запускаются в одном Go-процессе.
- Bun и River используют общий `*sql.DB` через официальный River driver
  `riverdatabasesql`. Это позволяет передавать встроенный `*sql.Tx` из `bun.Tx`
  в `River.InsertTx` и атомарно сохранять состояние приложения вместе с
  постановкой job. Отдельный минимальный `pgxpool` используется только River для
  PostgreSQL `LISTEN/NOTIFY` через `riverdatabasesql.NewWithPgxListener`.
- По умолчанию Go-приложение отдаёт собранные Vite static assets.
- Nginx может быть добавлен перед приложением в конкретном развёртывании, но не
  нужен для базового запуска и не является переключателем runtime-логики.
- Базовый `docker-compose.yml` поднимает PostgreSQL вместе с приложением, но
  приложение также поддерживает подключение к внешней PostgreSQL.

### HTTP runtime и диагностика

- REST API является внутренним контрактом bundled web UI, а не обещанием
  публичной интеграционной совместимости. При развёртывании на NAS браузер всё
  равно обращается к production HTTP server по сети либо через auth-proxy.
- Обычный REST request к локальной БД при нормальной нагрузке должен отвечать
  менее чем за одну секунду. Длительные операции создают River job и быстро
  возвращают operation ID; эта цель latency не является глобальным HTTP timeout.
- HTTP server использует `ReadHeaderTimeout=5s`, `IdleTimeout=60s` и graceful
  shutdown до 10 секунд. Глобальные `ReadTimeout`/`WriteTimeout` не задаются,
  чтобы не ломать route-specific payloads и долгоживущий SSE; body limits и
  deadlines определяются конкретными operations.
- OS signals преобразуются в parent context в `cmd/server`; HTTP server, SSE и
  River завершаются через общий lifecycle. `app.Run` не владеет signal handling
  и может корректно останавливаться в тестах.
- Все запросы получают `X-Request-ID`. Structured JSON logs содержат request ID,
  method, path, status, duration и response bytes. Panic recovery пишет stack в
  server log и возвращает безопасный JSON 500 без внутренних деталей.
- `/health/live` проверяет HTTP process, `/health/ready` с секундным deadline
  проверяет PostgreSQL после завершённого startup. Недоступность внешних metadata
  providers readiness не ломает. Docker image использует readiness healthcheck.
- Vite assets под `/assets/` получают immutable cache на год; `index.html` и SPA
  routes используют `no-cache`, чтобы deployment подхватывал новые hashed assets.
- Docker image пока сохраняет default root user ради простой совместимости с NAS
  volumes. Deployment может задать `user: UID:GID` в Compose и самостоятельно
  обеспечить права mounts. Source directories в любом случае должны
  подключаться read-only; переход image на обязательного non-root пользователя
  не входит в текущий фундамент.

## Поддерживаемые платформы

- Для production и локального запуска целевые платформы — Linux и macOS в
  вариантах `amd64` и `arm64`, Windows только `amd64`.
- Windows `arm64` пока не поддерживается: утверждённые releases Chromaprint

- Другие OS и архитектуры не входят в планируемую поддержку.

## Источники и публикации

- Входные аудиофайлы находятся в локальных директориях или на подключаемых
  дисках; сервис работает с ними как с путями файловой системы.
- Источник по умолчанию read-only. По отдельной настройке исходный файл можно
  удалить после успешной публикации.
- Публикация является управляемой сервисом копией: в неё включаются выбранный
  аудиоисточник, обогащённые метаданные, обложка релиза и тексты треков.
- Сервис полностью управляет публикациями: создаёт их, удаляет, заменяет и
  переорганизует при изменении правил каталогов или имён. Исходники по
  умолчанию не изменяются и не удаляются.
- Для конкретной версии релиза и конкретного трека в этом релизе допускается
  только одна опубликованная копия. Несколько подходящих источников не должны
  приводить к дублирующей публикации.

### Инвентарь и обработка источников

- `source_root` — логически настроенный входящий каталог. Он не является
  медиатекой и не определяет managed output; изменение его server path запускает
  полное сканирование только source inventory.
- `source_location` существует только для пути, обнаруженного последним успешно
  завершённым scan. Если доступный root полностью просканирован и путь не найден,
  строка удаляется. При недоступном root или незавершённом scan существующий
  inventory не изменяется.
- `device` и `inode` не сохраняются и не участвуют в идентичности. Путь хранится
  точно в виде, полученном от файловой системы; PostgreSQL не эмулирует её
  case/Unicode semantics.
- Для каждого `source_root` выбирается режим `in_place` или `staged`. В staged
  mode source один раз последовательно копируется в общий work-directory,
  инструменты анализируют временную копию, после чего она удаляется.
  Work-directory является явным server path/bind mount/volume и не размещается
  неявно рядом с бинарником или в container overlay.
- Глобальная настройка «вычислять SHA-256 для новых источников и переиспользовать
  точные совпадения» влияет только на последующие анализы. В staged mode digest
  считается в потоке copy, в in-place mode — отдельным последовательным чтением.
  Переключение не запускает backfill, merge или split существующих variants.
- Каждый фактический путь хранится отдельным `source_location`. При известном
  одинаковом SHA-256 несколько locations ссылаются на один `media_variant`.
  Variant с digest хранится без locations как долговременный кэш анализа и
  matching; orphan variant без digest удаляется.
- Scan использует generation reconciliation: изменения inventory фиксируются
  только после полностью успешного обхода. Изменение файла во время анализа
  обнаруживается сравнением stat до и после чтения; такой результат отбрасывается
  и повторяется позднее.
- Directory symlinks по умолчанию не обходятся, выход через symlink за пределы
  root запрещён. Hardlinks не распознаются специально и рассматриваются как
  независимые paths/variants, пока включённый SHA-256 не докажет точное равенство.
- `media_variant` может быть источником нескольких `collection_track`, в том
  числе относящихся к разным `collection_recording` и разным MusicBrainz
  Recording MBID. Публикационные теги определяются конкретной позицией релиза, а
  не исходными тегами общего variant.
- Для writable output-directory приложение во время проверки пути определяет
  фактические case и Unicode normalization semantics временными probe-файлами.
  Publication planner использует результат для обнаружения коллизий имён.

## Правила метаданных и ручного управления

- Хранится только актуальное состояние; история ручных и автоматических
  изменений не требуется.
- Оператор может вручную изменить состояние или скопировать его из провайдера
  либо источника в любой момент.
- Для метаданных выбирается приоритетный источник; по умолчанию это
  MusicBrainz.
- Достаточно уверенное совпадение с приоритетным источником применяется
  автоматически. Недостаточно уверенное совпадение требует подтверждения
  оператора.
- Релиз и треки можно публиковать вручную без сопоставления с провайдером,
  используя ручные либо исходные теги.

### Matching и целостность provider-связей

- Внутри provider cache конкретный `provider_release_track`, его release и его
  recording всегда принадлежат одному provider. Это не ограничивает локальные
  сущности: local release/track/recording могут одновременно иметь независимые и
  неполные связи с несколькими providers.
- Track lists разных providers не обязаны совпадать по составу или позициям.
  Отсутствие provider track означает отсутствие конкретной связи и не удаляет
  local track; лишняя provider position не добавляется автоматически.
- Matching formula возвращает единственный нормализованный `confidence` в
  диапазоне `[0, 1]`. Fingerprint, tags, duration, MBID и остальные признаки
  являются evidence/входами формулы; отдельный persisted `score` не используется.
- `confidence` хранится только у текущих кандидатов. Подтверждённая связь не
  копирует confidence и хранит только `decision_method`: `automatic` или
  `manual`, а для automatic также версию policy принятия решения.
- Пересчёт matching policy заменяет текущих кандидатов и может изменить или
  снять automatic link. Manual link защищён от автоматического перевыбора, пока
  оператор явно не изменит его или не вернёт сущность в automatic mode. Ручной
  выбор не изменяет рассчитанный confidence кандидата.

### Технические диапазоны и качество

- Размеры и длительности не имеют произвольных верхних продуктовых лимитов.
  SQL-проверки запрещают только отрицательные или структурно бессмысленные
  значения; многочасовой или гигабайтный source остаётся допустимым.
- Sample rate хранится целым числом Hz, а не enum. UI форматирует, например,
  `44100` как `44.1 kHz`; неизвестное заранее положительное значение допустимо.
- Один большой audio source не исключается из scan. CUE или ручные границы могут
  связать разные временные сегменты одного `media_variant` с несколькими tracks;
  без CUE/ручного решения приложение не делит файл автоматически.
- `quality_score` является производным от технических характеристик и всегда
  сопровождается `quality_policy_version`. Значения разных policy versions не
  сравниваются напрямую: перед решением оба варианта оцениваются по текущей
  policy из сохранённых metadata/snapshot. Формула качества будет согласована
  отдельной продуктовой задачей.
- Выбранный artwork candidate обязан принадлежать тому же collection release;
  физическая схема обеспечивает это составным FK, а выбранный candidate нельзя
  удалить до явного снятия выбора.
- FK cascade не является механизмом файлового удаления managed publication.
  Publication row изменяется или удаляется только service operation после
  безопасной staged/validated файловой операции; прямое удаление domain entity
  не должно оставлять неуправляемый artifact в output-directory.

## Предполагаемый поток обработки

Порядок ниже описывает целевую цепочку операций, но их поставка будет
поэтапной:

1. Сканирование новых и изменённых файлов источников.
2. `fpcalc` и технический анализ источника: теги, контейнер, кодек, битрейт и
   прочие доступные данные `ffprobe`.
3. Опциональный запрос AcousticID с получением потенциальных MusicBrainz
   Recording ID.
4. Объединение треков в релизы по тегам, MBID или иной определяемой логике.
5. Поиск совпадений, загрузка метаданных провайдеров и их кэширование в БД.
6. Публикация релиза: структура директорий и обложка.
7. Публикация трека: исходный формат либо remux в MKA, в зависимости от
   настройки, вместе с текстами.

Публикация трека выполняется при улучшении качества источника либо по явному
ручному действию. Автоматически заменять существующую публикацию источником
того же или худшего качества нельзя; оператор может вручную выбрать любой
подходящий источник.

## Процесс продуктовой проработки

Каждая новая продуктовая задача до начала реализации должна пройти отдельную
полноценную проработку. Она фиксирует пользовательскую цель, сценарии,
ограничения, изменения модели данных, операции/API, затронутые компоненты,
критерии готовности и план проверки. Решения из одной такой проработки не
считаются автоматически применимыми к другой задаче.
